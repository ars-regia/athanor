- Run `git remote set-head origin --auto` once, and base every worktree on `origin/iso-v0` and report its commit. Why: a local `origin/HEAD` can still name `main`, the pre-rename tree, and work built on it looks plausible and is wrong.
- Change `scripts/verify.py`, `forge/config/packages.json` and Markdown under `docs/` with an exact-match replacement script, never through a format-on-save hook, then check `git diff --numstat`. Why: these files are not formatter-clean, and a whole-file reformat buries the real change.
- Inside the Claude Code sandbox, run git writes and `gh` outside it, then check `git branch --show-current`. Why: `git switch -c` can move the index and worktree without HEAD, and `gh` answers 401 without keyring access.
- Never `git add` untracked `.bashrc`, `.gitconfig`, `.mcp.json`, `.idea`, `.vscode` or the agents directory under `.claude` seen inside the sandbox. Why: they are the sandbox's `/dev/null` mounts, not files of the checkout.
- On Athanor hosts put cargo targets, toolchains and large scratch under `/var/tmp`. Why: `/tmp` is tmpfs, and a multi-gigabyte target there has exhausted host memory.
- When something waits on the maintainer (an environment approval, a review, a settings apply), give the paste-ready command, `gh ... -R <repo>`, every time it is reported, never only the fact that it waits; a settings link only where no API exists, and `gh secret set NAME` reading from the prompt. Why: the maintainer decided it on 2026-10-14, after being told an approval was pending without the command to give it.
- Merge a sync pull request of a rebase integration branch (`chore(rebase): merge iso-v0 into rebase/<name>`) with `--merge` in place of `--squash`, under the same card and approval as any other merge. Why: the maintainer decided it on 2026-10-22, after the squash of #673 and #703 left `iso-v0` out of the branch's ancestry and made each sync re-resolve about a hundred add/add conflicts.
- On a base whose rules (`gh api repos/<repo>/rules/branches/<base>`) hold no `merge_queue` rule (`rebase/*`, `main`, and `iso-v0` until the maintainer applies ADR-0137's ruleset), before a merge card and again before the merge, check that the checks ran on the current base: the head contains the base head (`git merge-base --is-ancestor <base sha> <head sha>`), or every workflow run behind the head's checks (the run id in each check's `detailsUrl` in `gh pr view <n> --json statusCheckRollup`) is a `pull_request` run created more than a minute after the base head landed (`event` and `created_at` of `gh api repos/<repo>/actions/runs/<id>`, against the base commit's committer date, which GitHub sets when it merges). A pull request with a check that has no workflow run, or on a base that also takes pushes, such as `rebase/*`, where the committer date does not mark when the head landed, takes the first way only. Otherwise merge the base into the branch and wait for the new checks; the card and any approval on the old head are void. Why: a run keeps the base of the event that created it, through a queue or a re-run, and #1000 merged on checks that predated #992, so `iso-v0` failed the toolkit-surfaces job until #1012 (maintainer decision, 2026-11-05). A base with a `merge_queue` rule needs no such read: the queue runs `pr.yml` on `merge_group`, on the base each pull request lands on, and merges only what passed there (ADR-0137, maintainer decision, 2026-11-06).
