# Engineering standards and repository hygiene

Snapshot: 91aefb9f. Scope: Cargo workspace (members, exclusions, editions, MSRV, profiles, lints, duplicate dependencies via `cargo metadata --offline`, `.cargo/config.toml`, `deny.toml`, `supply-chain/`); tests and the workflows that run them, including fuzzing; `scripts/verify.py` (design, checks, a full local run, its CI tolerance, language); build tooling (root, forge and system Justfiles, `flake.nix`, `forge/build`, `forge/config/rpmmacros`, `scripts/`, `forge/scripts/`), with `shellcheck` run read-only on the 91 tracked `.sh` files; repository hygiene (root files, `.gitignore` files, `experimental/`, tool residue, Italian text, `ermete` names, licence declarations and headers, README); cross-crate conventions (errors, logging, runtimes, D-Bus prefixes, config paths). Not covered: semantic review of individual test bodies beyond sampling, `athanor-shell-rs` internals (frozen), the kernel tree under `forge/specs/azoth` beyond its language, anything requiring a build, a network call or a container. Security-relevant code paths are touched only where they bear on engineering process; their substance belongs to the SEC dimension.

## Summary

The repository has the shape of a disciplined project (a 17-check verifier, decision records, a workspace dependency table, cargo-deny and cargo-vet config, a hardened `.cargo/config.toml`) but most of these controls do not bind. The Rust security workflow triggers only on `main`/`develop`, never on the default branch `iso-v0`, and suppresses its own failures; no pull request runs lint, `verify.py` or `cargo test`, and branch protection requires only the kernel gate. The cargo-vet store holds one fabricated audit and `deny.toml` is the untouched template with seven unexplained advisory ignores. Thirteen crates with tests never have them run in CI. Shipped RPM builds replace the workspace's compiler-flag policy through `RUSTFLAGS` in `rpmmacros`, dropping `-D unsafe_code`, RELRO/BIND_NOW and frame pointers, and turning fat LTO into thin. `just clean` deletes the tracked `Cargo.lock` and `flake.lock`. `verify.py` is red at the snapshot (5 of 17 checks, 25 problems) and the red checks are tolerated simply by being left out of the CI invocation. Below that: 69 crates in two or three versions, 18 of 30 binary members that ship nothing, decisions recorded as accepted but not executed (niri-ipc deletion, SPDX headers, a forbidden-names check), the registry-owner rule broken in five places the checker cannot see, and Italian text in code, comments, runtime error strings and agent rules.

## Findings

### ENG-01 The Rust CI gate never runs on the default branch, and the rest of CI runs only after merge

- Severity: high
- Category: process
- Where: .github/workflows/rust-security-audit.yml:3-8, :105, :135, :239; .github/workflows/call-lint.yml; .github/workflows/athanor-forge-orchestrator.yml (triggers); .github/settings/branch-protection.json; .github/settings/rulesets.json
- Evidence: `rust-security-audit.yml` triggers on push and pull_request to `[main, develop]` only; `iso-v0` is the default branch, so clippy, cargo-deny, cargo-vet, Kani and the bare-metal build never run on the code being shipped. Inside it: `cargo vet check || echo "Cargo vet skipped due to crates.io 403 API block"` (:105), `continue-on-error: true` on the Kani job (:135), `${{ matrix.cmd }} > ebpf.log 2>&1 || true` followed by a grep for "error" (:239), clippy invoked with `-A clippy::undocumented_unsafe_blocks -A clippy::multiple_unsafe_ops_per_block -A dead_code -A unused_variables`, `chown ... || true` cleanup, step names reduced to `???` by emoji mojibake, `permissions: issues: write`, and an unpinned `git clone` of gtk4-layer-shell. `call-lint.yml` (Python unittest suites plus `verify.py workflows kickstart boundary cmdline registry licence ci coverage`) is called only from the orchestrator, which triggers on push to `main`/`iso-v0`, schedule and dispatch, never on `pull_request`. Branch protection for `iso-v0` requires only the "Kernel gate" status check, `required_pull_request_reviews` is null, `enforce_admins` is false, `rulesets.json` is `{}`.
- Standard: project standing rule "No `|| true`, no `continue-on-error`"; OpenSSF Scorecard Branch-Protection, CI-Tests and SAST checks; OpenSSF Best Practices "test_continuous_integration".
- Recommendation: Retarget `rust-security-audit.yml` to `iso-v0` (or to the default branch via `pull_request` with no branch filter), delete the `|| echo`, `|| true` and `continue-on-error` constructs and make each tool's exit status the job result; remove the blanket `-A` flags. Add a `pull_request` trigger for `call-lint.yml` (lint plus the verify checks) and add those jobs, plus a Rust test job (ENG-03), to the required checks of `iso-v0` in `branch-protection.json`; require one review and set `enforce_admins: true`.
- Needs a decision: yes: should the Kani and bare-metal eBPF jobs survive at all? Options: (a) make them real and blocking, (b) delete them with the crates they target (see ENG-08). Recommended: (b) for the eBPF build, (a) for Kani only if a harness exists.

### ENG-02 Supply-chain controls are placeholders: fabricated cargo-vet audit, template cargo-deny, orphaned Trivy ignores

- Severity: high
- Category: fake-implementation
- Where: supply-chain/audits.toml; supply-chain/config.toml; supply-chain/imports.lock; deny.toml; .trivyignore; system/Justfile (`security-scan`)

- Standard: CLAUDE.md "Niente finte implementazioni nella sicurezza" (a placeholder in a security path is a bug); cargo-vet audit semantics (an audit is a signed human attestation); OpenSSF Scorecard Vulnerabilities and Dependency-Update checks; SLSA source and build provenance expectations.
- Recommendation: Delete the fabricated libc audit. Rewrite `deny.toml` from scratch for this repository: every ignore with a `reason`, SPDX 3 identifiers (`GPL-3.0-only`, `GPL-3.0-or-later`, ...), `multiple-versions = "deny"` with explicit `skip` entries, `wildcards = "deny"`, `unknown-git = "deny"`, and run `cargo deny check` with all four sections. Either run Trivy in CI against the published images with `.trivyignore` translated and each entry justified, or delete `.trivyignore`.
- Needs a decision: yes: keep cargo-vet or rely on cargo-deny plus advisory database only? Options: (a) adopt cargo-vet with imported audits, (b) drop it. Recommended: (b) until a second maintainer exists to perform audits; cargo-deny alone, made strict, is honest.

### ENG-06 Compiler-flag and lint policy is split across four places, and shipped RPMs ignore the workspace's

- Severity: high
- Category: contradiction
- Where: .cargo/config.toml (`[build]` and `[target.'cfg(target_os = "linux")']`); forge/config/rpmmacros:55-82; Cargo.toml `[profile.release]`; forge/Justfile (`audit`); .github/workflows/rust-security-audit.yml; forge/test/shell/rig.sh; system/athanor-greeter/src/main.rs:1; system/athanor-ebpf-loader/src/main.rs:1; system/athanor-mesh-bus/src/main.rs:1-9; system/athanor-hypervisor-daemon/src/main.rs:1
- Evidence: `.cargo/config.toml` sets `-D unsafe_code`, `-W clippy::undocumented_unsafe_blocks`, `-W clippy::multiple_unsafe_ops_per_block`, `-C link-arg=-Wl,-z,relro,-z,now`, `-C relocation-model=pic`, `-C force-frame-pointers=yes`, identically in `[build]` and in the Linux target table; the `[build]` copy is dead because target rustflags take precedence. `rpmmacros` defines `%rustflags -C target-cpu=x86-64-v3 -C opt-level=3 -C codegen-units=16 -C strip=symbols -C link-arg=-fuse-ld=mold` and `%__spec_build_pre` exports `RUSTFLAGS="%{rustflags}"`, `CARGO_PROFILE_RELEASE_LTO="thin"`: a `RUSTFLAGS` environment variable replaces every config-file rustflags, so shipped binaries are built without `-D unsafe_code`, without the explicit RELRO/BIND_NOW link flags and without frame pointers, and the workspace's `lto = true` becomes thin. The macro comments are Italian and contradict the values ("codegen-units=1" against 16; one says "necessario per Ponytail Ultra"). Lint policy differs per entry point: config warns on undocumented unsafe; `forge/Justfile audit` denies it with `-D warnings`; the security workflow allows it plus `dead_code` and `unused_variables`; `rig.sh` uses `-D warnings`. In-crate: 20 `allow(unsafe_code)`, crate-wide `#![allow(clippy::all, warnings)]` in greeter and ebpf-loader, nine allows on mesh-bus, five on hypervisor-daemon. 165 unsafe blocks or functions against 92 `// SAFETY` comments (excluding shell-rs). There is no `[workspace.lints]`.
- Standard: Cargo reference, "build.rustflags" precedence (env > target > build); Fedora Rust packaging (`%build_rustflags` carries the distribution hardening); Rust API Guidelines and clippy `undocumented_unsafe_blocks` rationale; CLAUDE.md "Formal, idiomatic solutions".
- Recommendation: Make one source of truth. Move lint levels to `[workspace.lints.rust]` / `[workspace.lints.clippy]` with `lints.workspace = true` in every member, so they apply regardless of `RUSTFLAGS`; delete the `[build]` duplicate in `.cargo/config.toml`; build `%rustflags` in `rpmmacros` by appending to Fedora's `%build_rustflags` (which already carries relro/now and frame pointers) instead of replacing it, keep the LTO choice in `Cargo.toml` only, and translate the comments. Replace crate-wide `allow(warnings)` with targeted allows, each with a reason (`#[expect(..., reason = "...")]`), and require a `// SAFETY:` comment by making `undocumented_unsafe_blocks` deny at workspace level.
- Needs a decision: yes: fat or thin LTO for release RPMs? Options: (a) fat with `codegen-units = 1` as `Cargo.toml` says, (b) thin with 16 as `rpmmacros` does. Recommended: (b), written once in the workspace profile, since build time on the CI runners is the binding constraint.
