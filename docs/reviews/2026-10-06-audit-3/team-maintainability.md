# Team maintainability: can 5-10 people with coding agents maintain and rebuild Athanor from the repository

Snapshot: 91aefb9f. Scope: agent entry points (CLAUDE.md, AGENTS.md, nested guidance, `.claude/`, `.serena/`), `docs/operations/`, `.github/` governance files and `.github/settings/*.json`, the documentation structure against Diátaxis, the decision and spec processes, planning discoverability, the local gates against CI (`python3 scripts/verify.py` was run in full on the snapshot), and the branch, release and version model. Not covered: the live GitHub backlog (no `gh`), the content correctness of individual specifications beyond their status and cross-references, workflow security (pinning, permissions) except where it decides what a contributor's PR must pass, and the Rust code itself.

## Summary

Decision A2-34 sets the goal (everything in the repository, a 5-10 person team on Claude Code), and the snapshot has real foundations for it: `docs/operations/` (secrets, GitHub settings as code, ownership, branching) is concrete and well sourced, decision records are one file each with a checked index, and `verify.py` has 17 structural checks including `coverage`, `ci` and `decisions`. The team model fails today on five points:

1. The agent entry point is Claude-only, mostly Italian, and partly false or machine-specific; there is no `AGENTS.md`, so Codex, Gemini CLI and Cursor get nothing, and the `.claude/rules` it relies on are stale and cite tools that are not in the repository (TEAM-01, TEAM-02, TEAM-03).
2. There is no single local gate that equals CI. The product branch fails 5 of 17 `verify.py` checks, CI runs 8 of them, the only required check on PRs is `Kernel gate`, and three documents list three different command sets (TEAM-04, TEAM-05).
3. The specification process is not written down: 19 of 31 documents are drafts or await approval, code ships on unapproved revisions, and specs cite specs that live only on other branches or in ignored directories (TEAM-10).
4. The branch, release and version model would mislead a newcomer: the default branch is named after a milestone, `main` is frozen yet trusted and targeted by three workflows that therefore never run, there are no tags, and 41 packages say 1.0.0 (TEAM-13).
5. There is no newcomer path (no tutorial "build and boot the image", no docs index, no system overview), and the operating model in `docs/operations/` is still mostly marked _(Proposal)_ (TEAM-09, TEAM-06).

### TEAM-04 No single local gate equals CI; the product branch fails the full verifier, and the only required PR check is the kernel gate

- Severity: high
- Category: process
- Where: .github/workflows/call-lint.yml:40-41; .github/settings/branch-protection.json (`required_status_checks.checks` = `Kernel gate` only); .github/workflows/kernel-build.yml:11-13, :263-277; .github/workflows/shell-surfaces.yml:25-45, :52; .github/workflows/rust-security-audit.yml:4-7, :105; .github/PULL_REQUEST_TEMPLATE.md:10; .github/CONTRIBUTING.md:10-15; docs/operations/contributing.md:39-48; CLAUDE.md:40-50; forge/Justfile:108; system/Justfile:91; scripts/cosmic-comp-rebase/tests/, scripts/runner/tests/, scripts/session-memory/tests/

CI runs only `verify.py workflows kickstart boundary cmdline registry licence ci coverage` (call-lint.yml:41), the 8 that pass. The PR template asks the author to confirm "`just lint` and `python3 scripts/verify.py` pass locally" (line 10), which is impossible on the product branch; contributing.md CT3 says "Compare the full `verify.py` run with the product branch: no new failure", which needs a baseline that is not stored anywhere. The three documents list three different command sets: `.github/CONTRIBUTING.md` 3 commands, `contributing.md` CT3 15 checks (missing `ci` and `coverage`), `CLAUDE.md` 6 checks. `just lint` is run by no workflow, covers only `forge/` and `system/` shell scripts (not `scripts/`), and passes with "shellcheck not found, skipping" when the tool is absent. Three Python test directories (`scripts/cosmic-comp-rebase/tests`, `scripts/runner/tests`, `scripts/session-memory/tests`) are run by no workflow. No workflow on `iso-v0` runs `cargo test` for the workspace: Rust tests run only for shell crates inside `forge/test/shell/rig.sh` (shell-surfaces, path-filtered) and in 6 spec `%check` sections; `cargo clippy` and `cargo deny` run in `rust-security-audit.yml`, which triggers on `main` and `develop` only, and there `cargo vet check || echo "Cargo vet skipped ..."` (line 105) hides a failure. (2) Add a `pr.yml` workflow on every `pull_request` that runs `just check` (or the same script) and make its job a required check next to `Kernel gate`. (3) Make the product branch green: fix the 25 problems or move each into an explicit, issue-linked allow-list file that `verify.py` reads, so "no new failure" is mechanical. (4) Point `.github/CONTRIBUTING.md`, the PR template, `contributing.md` CT3 and `AGENTS.md` at `just check` and delete their own command lists. (5) Retarget or delete `rust-security-audit.yml`, `fuzzing.yml`, `nix-vanguard.yml` (TEAM-13) and remove the `|| echo` on `cargo vet`.
- Needs a decision: yes: whether the verifier's current failures are fixed before the gate becomes required, or allow-listed with issues. Options: (a) allow-list with an issue per entry, gate required now (recommended: stops regression immediately); (b) fix first, then require (leaves PRs ungated meanwhile).
