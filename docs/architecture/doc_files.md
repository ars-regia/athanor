# Athanor file manager

Status: **revision 1 draft, 2026-10-05: the maintainer's decisions applied; text not yet reviewed. Amended on 2026-10-06 by maintainer decision A2-14 (#159): until 1.0 Athanor builds only `athanor-files-view` for the file chooser, and Nautilus is the file manager of 1.0 with a declared risk. Section 7 records the amendment and overrides the text above where they disagree.** It is the specification that `doc_software.md` revision 3, decision 7, names: Athanor's own file manager, which replaces the interim Nautilus. It designs the programs and crates, the confinement of the window, the file operations and their data safety, the sandboxed archive and thumbnail helpers, search, trash, recent files and bookmarks, opening files, removable media, the `org.freedesktop.FileManager1` interface, what the file chooser portal may reuse, the first release's scope and exclusions, the tests and the order of construction. Section 6 records the maintainer's decisions of 2026-10-05; each rule that carries one names it.

## 2. Decisions

**FM1. One application for files.** `athanor-files` browses, opens, copies, moves, renames, trashes, extracts and finds the user's files and removable drives. It is an application, not a shell surface: it runs only when used, in windows of its own, on libadwaita, and it replaces Nautilus only at the last step of FM21. Formatting and partitioning belong to `doc_disks.md`; the file chooser dialog belongs to `doc_portal.md` (FM17).

**FM2. Programs and crates.**

| Crate                                   | Unit or path                        | Role                                                                                                                                      |
| --------------------------------------- | ----------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------- |
| `forge/specs/athanor-files`             | started per session by GApplication | the window, application id `os.athanor.Files`                                                                                             |
| `system/athanor-files-ops`              | none, a library                     | the operations engine of FM5 and FM6, the archive writer of FM8 and the thumbnail cache of FM10; no GTK type                              |
| `system/athanor-files-view`             | none, a library                     | the GTK4 and libadwaita widgets: directory model, list and grid views, path bar, sidebar; used by the window and, later, the file chooser |
| `athanor-files-helper` (in the package) | `/usr/libexec/athanor-files-helper` | the sandboxed parser: `archive` mode (FM8) and `thumbnail` mode (FM10); no GTK, no D-Bus                                                  |

- **Reused, not rewritten:** `athanor-unit` (`sandbox::restrict_writes`, `sandbox::deny_tcp`, `sandbox::ensure_single_threaded`, `text`, `dirs`, `journal`), `athanor-i18n`, `athanor-search` (`files.rs`, FM11), `athanor-preview` (the per-request render helper of LA6, FM10), `athanor-services` (its `udisks` module, DK3, FM14) and `athanor-compositor-client` (the launch path of BR2 and the security context of FM3).
- **Two libraries,** for the reason CC2 and LA1 give: the engine must be testable with no display (FM20), and the view is shared with the file chooser of `doc_portal.md`.
- **New dependencies:** `libadwaita` 0.9.2 (MIT; it depends on `gtk4` ^0.11 and `glib`/`gio` ^0.22, the workspace's versions) and the pure-Rust archive crates of FM8: `zip` 8.6.0 (MIT), `tar` 0.4.46 and `flate2` 1.1.10 (MIT or Apache-2.0), `bzip2` 0.6.1 (MIT or Apache-2.0; its default backend is the Rust `libbz2-rs-sys`), `lzma-rust2` 0.21.0 and `sevenz-rust2` 0.23.0 (Apache-2.0), `ruzstd` 0.9.0 (MIT). Versions, licences and features from the crates.io API, 2026-10-05. No other.
- **Single instance.** `GApplication` with the id `os.athanor.Files`: a second start opens a window in the running process. The process stays alive while an operation runs, after its last window closes, and ends when the last operation ends (FM6).
- **Renderer:** GTK's default. It is an application, not a resident surface, so ST5's thresholds do not bind it; FM20 sets its own.

**FM3. The window's confinement.** Decision 1: Landlock and no TCP now; a filtered bus when the launch broker exists. In this order, at start, before GTK initialises and before any thread starts, the Tokio thread of the `udisks` model included (`athanor_unit::sandbox::ensure_single_threaded`), so every thread runs under the ruleset:

1. **Off the main socket.** When the Wayland socket the process received offers `wp_security_context_manager_v1`, it is the session's main socket, which happens when the process was started by D-Bus activation (FM16) or from a terminal. The process creates a security context for itself through `athanor-compositor-client` (engine `os.athanor.shell`, app id `os.athanor.Files`, its unit name as instance id), with the listening socket under `$XDG_RUNTIME_DIR/athanor/`, points `WAYLAND_DISPLAY` at it, and closes the main connection. When the context cannot be created the process exits with an error at err priority, as BR2.6 fails closed. Started from the bar, the dock or the launcher, it already sits behind a context and skips this step.
2. **Landlock** (`athanor_unit::sandbox::restrict_writes`, ABI 3): read access everywhere the user can read; write access only beneath `$HOME`, `/run/media` (where udisks2 mounts drives), `/tmp` and `/dev/dri`. `$HOME` holds everything the window writes of its own: GTK's and dconf's files, `$XDG_STATE_HOME/athanor-files/`, the thumbnail cache, `recently-used.xbel`, the bookmarks file, `mimeapps.list` and the home trash.
3. **No TCP** (`athanor_unit::sandbox::deny_tcp`, ABI 4).

- **What Landlock is here:** defence in depth, not the boundary. The window parses no untrusted format beyond what GIO and GTK read (names, the first bytes for `shared-mime-info`'s content sniffing, the cache's own PNG files, which only the user's processes write); every archive, document and image is parsed by a helper in a transient unit (FM8, FM10).
- **Declared limits,** the same as BR2's, which end for the window at step 7 of the session-daemons construction (`doc_session_daemons.md` SD22; the bus and main-socket limits, SD8 and SD9). Until then the window reaches the session bus, so a compromised window can ask the user manager to start any process (`StartTransientUnit`), and it can connect by path to the main Wayland socket. Landlock cannot protect the places where an attack would persist inside `$HOME` (autostart entries, shell profiles, user units, `~/.local/bin`, D-Bus service files, `mimeapps.list`): Landlock rules only grant, so a directory beneath an allowed one cannot be denied. Writes outside the four roots fail, among them other users' shared folders and drives mounted by `/etc/fstab` outside `/run/media`, such as the `/var/mnt/<label>` mounts of `doc_disks.md` decision 4; the window reports the refusal (FM6).
- **The broker (decision 1).** From step 7 of the session-daemons construction (`doc_session_daemons.md` SD22) the window's launches go through the launch broker (FM4, SD7) and the window's bus is filtered through `xdg-dbus-proxy` (0.1.8, installed) to the names it uses: udisks2, localsearch, gvfs's trash, the notification service and its own (SD9). That closes the `StartTransientUnit` escape above.

**FM4. Opening files and "Open with".**

- **The default application** for a file comes from GIO's lookup (`gio::AppInfo::default_for_type`), which reads `athanor-mimeapps.list` before Fedora's lists because the session's first desktop name is `Athanor` (`doc_software.md:328`). "Open with" lists `gio::AppInfo::all_for_type` and offers "Always use for this type", which writes the user's `mimeapps.list` through GIO.
- **Every launch is a transient unit,** as BR2.3: never a child of the window, so the application does not inherit the window's Landlock ruleset. Decision 9: the application inherits the window's restricted socket and receives the window's close descriptor through `ExtraFileDescriptors`, so its context outlives the window; it carries the file manager's app id in the compositor, as applications opened by Software do (`doc_software.md:92`). From step 7 of the session-daemons construction (`doc_session_daemons.md` SD22), each application gets a context of its own, with its own app id, through the broker (SD7).
- **`DBusActivatable` is ignored** and the `Exec` line runs, as BR2.5.
- **Nothing executes from the file manager.** An executable file, a script or a desktop entry outside the XDG application directories is opened with its type's default (a text editor for a script or a desktop entry), never run, and the window offers no "Run". Activating a desktop entry from a folder is not offered either.
- **A launch that fails** shows a toast that names the application and logs at err priority, as LA10.

**FM5. File operations and data safety.** Decision 2: operations run in the window's process, on worker threads, recovered by the crash journal below. The engine lives in `athanor-files-ops`, written on `std` and `rustix`, with GIO only where GIO is the standard: trash, content types, application associations.

- **Copy of a file:** written to a temporary name in the destination folder, `.<name>.athanor-partial-<random>`, then `fsync` of the file, `renameat2` to the final name with `RENAME_NOREPLACE` (or over the existing file only when the user chose Replace, FM6), then `fsync` of the folder. Content is copied with `copy_file_range`, which may share extents on btrfs (unverified, S4). Permissions are kept without setuid, setgid and sticky bits; modification time is kept; ownership, SELinux labels and extended attributes are not copied, so the destination's policy labels the file.
- **Move within one filesystem:** `renameat2` with `RENAME_NOREPLACE`; a conflict is answered first (FM6).
- **Move across filesystems:** a copy of the whole tree as above, then a check that every destination file has the source's size, then removal of the source, file by file, only after the destination is synced. An interruption at any point leaves the source whole.
- **Folders** are created first and their times set last. A symbolic link is copied as a link with the same target and never followed. A device node, FIFO or socket is skipped and listed in the operation's report. Hard links are copied as separate files (declared).
- **Before an operation starts**, the destination's free space is compared with the total to copy; a shortfall stops it before the first byte, with both numbers shown.
- **A crash journal.** Each running operation writes its destination folders and its temporary names to `$XDG_STATE_HOME/athanor-files/operations/<id>`. At the next start the window removes the partial files of every unfinished operation, keeps every completed file, and tells the user which operation did not finish. With `panic = "abort"`, this is what makes a crash during a copy recoverable.
- **Delete** is permanent and asks every time, naming the count and the first names. It is offered for items in the trash, on filesystems without a usable trash (FM7) and through Shift+Delete.
- **Errors** (permission, Landlock refusal, read-only filesystem, a name the target filesystem refuses such as `:` on exFAT, a vanished source) stop the item, not the operation: the user chooses Skip, Skip all, Retry or Cancel. A cancelled operation leaves the completed items, removes its partial file and, for a move across filesystems, leaves every source not yet removed.

**FM6. Conflicts, progress and undo.**

- **A file onto a file:** Replace, Skip or Keep both (`name (2).ext`), each with "Apply to all". The dialog shows both sizes and modification times. Replace never deletes the old file before the new one is complete: the new file is renamed over it (FM5).
- **A folder onto a folder:** Merge (the files inside then follow the rule above), Skip or Keep both. There is no "Replace folder": it deletes a whole tree on one click, the data-loss case `doc_software.md:246` names.
- **A file onto a folder, or a folder onto a file:** Skip or Keep both.
- **Progress:** an operations button in the header bar with each running operation, its bytes, items and remaining time, and Cancel. Operations run one at a time per destination filesystem and in parallel across filesystems. When the last window closes during an operation the process stays alive; at the end a desktop notification reports the result.
- **Undo and redo** keep one operation, as Nautilus 49 does (section 1): rename, move, copy (the copies go to the trash), trash (the items are restored), new folder (removed while empty), extract (the created items go to the trash), compress (the archive goes to the trash). A permanent delete cannot be undone, and the confirmation says so. Undo is refused, with the reason, when the files changed since.

**FM7. Trash.**

- **Follows the freedesktop Trash specification 1.0** (2014-01-02; `specifications.freedesktop.org/trash/latest/`, checked 2026-10-05) through GIO: `gio::File::trash` moves the item and writes its `.trashinfo`; the Trash view lists `trash:///` (served by `gvfsd-trash`) with the original location and deletion date; Restore puts an item back and asks when the original location is taken; Empty Trash asks first.
- **On a removable drive**, the trash is the drive's own `.Trash-<uid>` (or `.Trash/<uid>` where the specification allows it), as GIO implements it. When the drive offers no usable trash (read-only, or the directory cannot be created), the window offers a permanent delete with its confirmation, never a silent one.
- **No automatic emptying** in the first release: `org.gnome.desktop.privacy remove-old-trash-files` belongs to gnome-settings-daemon, which the image does not run; the setting is not shown.

**FM8. Archives: the helper parses, the window writes.** Decisions 3, 8 and 10; FM9 carries decision 4.

- **Actions:** "Extract here" and "Extract to…". The result is one folder named after the archive, unless the archive holds exactly one top-level entry, which is extracted as itself. A name taken already is resolved with Keep both. Browsing an archive's contents without extracting it is not offered.
- **The helper** is `athanor-files-helper archive`, started per extraction as a transient user unit, `systemd-run --user --pipe --quiet --wait --collect`, with the properties of `athanor-preview-render` (LA9): `ProtectHome=yes`, `InaccessiblePaths=-/var/home -/var/roothome`, `ProtectSystem=strict`, `NoNewPrivileges=yes`, `PrivateNetwork=yes`, `PrivateIPC=yes`, `TemporaryFileSystem=/tmp /run`, `RestrictAddressFamilies=AF_UNIX`, `RestrictNamespaces=yes`, `SystemCallFilter=@system-service ~@network-io`, `MemoryMax=512M`, `MemorySwapMax=0`, `TasksMax=4`, `TimeoutStopSec=1`. It also restricts itself with Landlock (no write anywhere, `deny_tcp`) after loading its libraries.
- **Formats read** (decision 3): pure-Rust parsers only, so the helper holds no C parser. Zip through `zip` 8.6.0 with its default features off and only `deflate-flate2` (on `flate2`'s default `miniz_oxide` backend), `bzip2`, `lzma` and `xz` (the last two on `lzma-rust2`); tar, alone or compressed with gzip, bzip2, xz or zstd, through `tar` 0.4.46 with `flate2`, `bzip2`, `lzma-rust2` and `ruzstd`; 7z through `sevenz-rust2` 0.23.0 with its default features off and only `bzip2`, which reads LZMA and LZMA2. Default features are off because those of `zip` pull the C `zstd` crate and AES, and those of `sevenz-rust2` pull AES (crates.io feature lists, 2026-10-05). An entry compressed with another method, zstd or PPMd inside a zip included, stops the extraction with "This archive uses a compression method that is not supported" and names the method. RAR is not read in the first release: "RAR archives are not supported".
- **The archive arrives on standard input,** opened by the window (verified seekable, section 1). The helper has no access to the destination, the home or the bus. It returns on standard output a stream of records in a format of its own, `ATAR1`: for each entry its kind (file, folder, symbolic link, hard link), its path as bytes, its permission bits, its modification time, its link target, then its data in chunks; then an end record or an error record.
- **The window writes.** The engine of FM5 reads the stream and checks every record again: a compromised helper can only send a stream the window refuses. It writes beneath a staging folder `.<name>.athanor-partial-<random>` inside the destination, through `openat2` relative to the staging folder's descriptor with `RESOLVE_BENEATH | RESOLVE_NO_SYMLINKS | RESOLVE_NO_MAGICLINKS`, and renames the staging folder to its final name when the stream ends. A failed or cancelled extraction removes the staging folder. The crash journal of FM5 covers it.
- **Why the window writes:** the writing code is the copy engine the window already trusts, with its progress, conflicts, undo and journal; the helper needs no write access at all, so its unit carries no bind of the user's folders. `doc_software.md` decision 7 says "a helper that may write only the destination folder"; decision 10 makes this stricter rule the rule, and section 3 changes that wording (`doc_software.md:305`).
- **Creating** (decision 8): "Compress…" on a selection writes a `.zip` or a `.tar.xz`, the user's choice, with `.zip` preselected. Writing parses nothing untrusted, so it runs in the engine of FM5, in the window, as an operation with its progress, Cancel, crash journal and undo (FM6).
  - **No link is ever followed.** The engine walks the selection with `openat2` and `RESOLVE_NO_SYMLINKS`, reads each entry's kind with `statx` and `AT_SYMLINK_NOFOLLOW`, and builds the tar stream with `tar`'s `Builder` set to `follow_symlinks(false)` (docs.rs, `tar` 0.4.46, checked 2026-10-05). A link inside the selection never brings the content of a file outside it into the archive.
  - **Paths** are relative to the selection's parent folder, so every entry sits under a name the user selected; none is absolute or holds a `..` component; names are stored as their bytes.
  - **`.tar.xz` keeps permissions and links:** regular files with their permission bits, setuid, setgid and sticky cleared; folders; symbolic links as links, their target stored exactly as it is and never resolved; modification times. Ownership is stored as user and group 0 with empty names, so the archive names no local account. A link whose target is absolute or leaves the archived tree is stored and listed in the operation's report, because it will point elsewhere wherever the archive is extracted. Hard links are stored as separate files, as FM5 copies them. Device nodes, FIFOs and sockets are skipped and listed; extended attributes, ACLs and SELinux labels are not stored. The stream is compressed by `lzma-rust2`'s `XzWriter` (docs.rs, 0.21.0, checked 2026-10-05) at xz's default preset, 6.
  - **`.zip` keeps files and folders:** their permission bits in the Unix external attributes, with the same bits cleared, and their modification times, compressed with Deflate. Symbolic links are skipped and listed with "Links are kept only in .tar.xz", so a `.zip` never carries a link for another program to follow when it extracts.
  - **Written like a copy:** to `.<name>.athanor-partial-<random>` in the destination, renamed to its final name with `RENAME_NOREPLACE` when complete; a name taken already is resolved with Keep both. When the destination lies inside the selection, the walk skips the partial file. A full destination or a cancel removes the partial file.
  - **Encrypted archives** are not created (FM19).

**FM9. What an archive may not do.** Each refusal stops the extraction, removes the staging folder and names the reason, except where a rule says the entry is skipped.

- **Paths:** an absolute path, a `..` component, a NUL byte, an empty component, more than 64 components, a component over 255 bytes or a path over 4096 bytes. Paths are byte strings; names that are not UTF-8 are written as they are, as on any Linux filesystem.
- **Kinds:** device nodes, FIFOs and sockets are skipped and listed. Ownership is never set. Setuid, setgid and sticky bits are cleared; permissions are limited to the user's read, write and execute.
- **Symbolic links** (decision 4): a link is created only when its target, resolved lexically against the link's own folder, stays inside the extraction root; otherwise it is skipped and listed. During extraction no link is ever followed, because every write resolves with `RESOLVE_NO_SYMLINKS`.
- **Hard links** may only point at an entry already extracted from the same archive; they are written as copies of it, so a later entry cannot write through them.
- **Sizes,** proposals the first measurement confirms: the written bytes, counted as written and never taken from the archive's declared sizes, must leave 1 GiB free on the destination; at most 1,000,000 entries; when the written bytes pass 1 GiB and exceed 1000 times the archive's size, the extraction pauses and asks "This archive expands far beyond its size. Continue?". No archive inside the archive is extracted.
- **Time:** the helper is stopped when it sends no data for 30 s. There is no total time limit, so a large archive can take as long as its size requires.
- **Encrypted entries** stop the extraction with "Encrypted archives are not supported" (FM19).

**FM10. Thumbnails.** Decision 5: Athanor's own runner; no thumbnailer runs outside a helper unit.

- **The cache** follows the Thumbnail Managing Standard 0.9.0 (`specifications.freedesktop.org/thumbnail/latest/`, checked 2026-10-05): the personal cache at `$XDG_CACHE_HOME/thumbnails/` in the `normal` (128), `large` (256), `x-large` (512) and `xx-large` (1024) folders, a file named after the MD5 of the file's URI, `Thumb::URI` and `Thumb::MTime` written in every PNG, written to a temporary name and renamed, failures recorded under `fail/athanor-files/`. Other programs' cached thumbnails are read like ours.
- **Images and PDFs** go through `athanor-preview` and its helper `athanor-preview-render` (LA6), unchanged. This also gives the PDF thumbnail of `doc_software.md` acceptance item 16 without `papers-thumbnailer`.
- **Every other type** with an installed `.thumbnailer` entry goes through `athanor-files-helper thumbnail <entry>`, in a transient unit with the properties of FM8. The helper runs the entry's `Exec` line inside its unit, with the input handed in on standard input and the output written in the unit's private `/tmp`, decodes the resulting PNG, and returns a bitmap on standard output in the `ATPV1` format of `athanor-preview-render`. How the input is named to the thumbnailer is spike S3.
- **The window encodes** the PNG it writes to the cache from that bitmap, so no PNG a thumbnailer produced reaches the cache unread. Decoding a PNG already in the cache stays in the window: only the user's own processes write that folder.
- **Limits:** files over 64 MiB get no thumbnail (the input bound of LA6); thumbnails are made for visible items first, and at most two helpers run at once.
- **Removable drives** get thumbnails like the home.

**FM11. Search.** Decision 7: by name, plus localsearch's index.

- **By name,** in the current folder and below: a walk on a worker thread that skips hidden entries unless they are shown, never follows a symbolic link, stays on the folder's filesystem, and shows results as they come, newest first, at most 2000.
- **From localsearch,** through `athanor-search`'s `files.rs`: name and content matches from the index, with its bounds, its 1 s deadline and its cleaning of every string. The two lists merge without duplicates. With localsearch stopped or absent its part is absent and nothing says it failed (LA10); while it indexes, one line says so.
- **What the index covers** is localsearch's upstream default (`doc_software.md` decision 7); the file manager adds no folder to it and offers no setting for it in the first release.

**FM12. Recent files and bookmarks.**

- **Recent** lists GTK's `RecentManager` (`$XDG_DATA_HOME/recently-used.xbel`), only `file://` items that still exist. The file manager adds what it opens. With `org.gnome.desktop.privacy remember-recent-files` false it neither shows nor adds, and the sidebar hides the entry.
- **Bookmarks** live in `$XDG_CONFIG_HOME/gtk-3.0/bookmarks`, the file GTK's own file chooser reads and watches (section 1), so a bookmark added here appears in every GTK dialog. The file manager writes it to a temporary name and renames it, and reloads it when another program changes it. Bookmarks to non-`file://` locations are kept in the file but not shown (FM15).
- **The sidebar,** in order: Recent, Home, the XDG user folders that exist (`xdg-user-dirs` 0.18), bookmarks, removable drives (FM14), Trash.

**FM13. Drag and drop, cut, copy and paste.**

- **Formats:** GTK4's `GdkFileList`, `text/uri-list`, and `x-special/gnome-copied-files` with its `copy` or `cut` line, which Nautilus and GTK applications read.
- **The default action of a drop** is a move within one filesystem and a copy across filesystems; Ctrl forces a copy, Shift a move. Dropped files from another application are copied. A drop is an operation of FM5 with its conflicts and undo.
- **Cut** marks the items until they are pasted or the clipboard changes. Pasting text that names paths is not taken as files.
- **Dragging out** to a Flatpak application relies on GTK's use of the document portal for file transfers (unverified, S6).

**FM14. Removable drives.** Through the `udisks` model of `athanor-services` that `doc_disks.md` writes (DK3): one mount path, which the file manager, the disk utility and the control center share. The file manager uses the model and changes none of its sequences.

- **The sidebar** lists the filesystems the model reports on drives udisks marks `HintSystem=false` (class R of DK5) and on images the disk utility attached (DK14), never a block udisks marks `HintIgnore`, each with its label, its size and a "Safely remove" button. Mounting is a click.
- **Mount options are udisks's,** never chosen here: udisks adds `nodev,nosuid` to every mount (`doc_disks.md` section 1, `udiskslinuxfilesystem.c:1154`), and every mount udisks makes carries the global `noexec` default of the image's `mount_options.conf [defaults]` (`doc_disks.md` DK20 B, decided by the maintainer on 2026-10-05; `doc_kernel_profile.md` D23 keeps `noexec` off user-writable locations and names udisks mounts as its explicit exception). The file manager never passes `exec`. "Allow running programs from this drive" is the disk utility's switch for one mount (DK12), reached from the drive's context menu. With FM4, nothing on a removable drive runs from the file manager.
- **A blocked stick does not appear.** A USB mass-storage device that USBGuard blocks has no block device, so no row, no mount and no automount; the window shows nothing for it. The session notice "Allow once / Allow always" and the disk utility's "Blocked" row are where it is allowed (`doc_disks.md` DK21); once allowed, it appears here as any removable drive.
- **Automount while the file manager runs** (`doc_disks.md` decision 6 and DK16). When `org.gnome.desktop.media-handling automount` is true (true on the desktop, section 1) and the process is alive (a window open or an operation running), a filesystem that appears is mounted through the model, with the options above, when its block is marked `HintAuto` and not `HintIgnore`, its drive is not a system device, and no udisks `Job` lists the drive in its `Objects`, so a format or an image write of the disk utility is never mounted under it. No window opens by itself. A drive inserted while the file manager is not running is mounted by `athanor-sessiond` under the same conditions and through the same model, queued while the session is locked (`doc_session_daemons.md` SD11); the file manager finds it already mounted. Until step 5 of that document's construction (SD22) such a drive stays unmounted and mounts when opened, which was the declared limit of earlier revisions.
- **Encrypted volumes.** Unlocking asks the passphrase in an `AdwPasswordEntryRow` and hands it to the model's unlock as DK11 does: one `Zeroizing` copy for the call, dropped when it returns. Nothing is stored, and every unlock asks again (`doc_disks.md` decision 3).
- **No new privilege.** Every action is one udisks method under udisks's own polkit actions, at udisks's defaults (`doc_disks.md` decision 5): the active local session mounts, unlocks and powers off removable drives without a password. This document adds no polkit rule, setuid program or system unit, and does not touch `system/athanor-bus-api/src/polkit.rs`.
- **Safe removal** is the model's "Safely remove" sequence (DK12): unmount every filesystem, lock every LUKS volume, then power off or eject; it never forces. When a filesystem is busy, the failure of DK8 names the processes udisks reports and offers Retry.
- **The disk utility** (DK16): the drive's context menu offers "Open in Disks" and "Format…", which start `athanor-disks --drive <udisks drive object path>` through the launch path of FM4. Disk images open with their default application, which `athanor-mimeapps.list` sets to the disk utility. Formatting, partitioning, SMART and disk images are `doc_disks.md`'s.

**FM15. Network locations.** Decision 6: none now, confined mounts of Athanor's own later. The first release browses no network location: no "Connect to server", no `smb://`, `sftp://`, `ftp://`, `dav://` or `mtp://`, and mounts that GIO reports with a non-local root are not shown. `admin://` is never offered: it would start `gvfsd-admin`, which writes as root, and gvfs's rule lets wheel members start it without a password (section 1). gvfs's network backends are not used later either, because each is a network parser running unconfined with the user's rights; network locations return through a revision of this document as mounts of Athanor's own, each a program in a unit that reaches only its host, such as an SFTP client.

**FM16. `org.freedesktop.FileManager1` and `os.athanor.Files`.**

- **The window owns `org.freedesktop.FileManager1`** at `/org/freedesktop/FileManager1` with `ShowFolders`, `ShowItems` and `ShowItemProperties`, each `(as uris, s startup_id)`; `startup_id` is used as the `xdg_activation_v1` token of the window it opens or raises. Nautilus' two extension properties are not implemented. Only `file://` URIs are accepted; others are ignored and logged at warning priority. At most 64 URIs per call.
- **D-Bus activation** through `org.freedesktop.FileManager1.service` with `SystemdService=athanor-files.service`, shipped only at the last step of FM21, together with the removal of Nautilus, so two activation files never claim the name. A process started this way holds the main socket and leaves it before GTK starts (FM3, step 1). Whether D-Bus activation starts the window outside the broker, and so outside its policy entry and filtered bus, is spike S7 of `doc_session_daemons.md`.
- **Any session peer can call it,** as LA9 says of `Show`: a call opens or raises a window and runs nothing.
- **`os.athanor.Files`** is the GApplication's own name and its `Activate` and `Open` actions, standard for GApplication; nothing else is exported.

**FM17. What the file chooser may reuse.** `doc_portal.md` designs the FileChooser backend and its dialog. This document provides `athanor-files-view`: the directory model with sorting and hidden files, the list and grid views, the path bar with an editable location, the sidebar of FM12 and FM14, and the thumbnails of FM10 through a callback the host supplies. The view holds no operation, launch or archive code, so the portal's process gains none of them. A chooser that runs in the portal's process applies that process's confinement, not the file manager's.

**FM18. Untrusted names, accessibility and languages.**

- **File names are untrusted text.** They are shown as plain text, bounded as BR4 and LA9 bound untrusted text, but control and bidirectional characters are shown as visible escapes instead of being removed, because two different names must never look alike; a name that is not UTF-8 is shown with its invalid bytes escaped and operated on by its bytes. Rename refuses `/` and NUL and warns about a leading `-`, a leading `.` (hidden) and a trailing space.
- **Accessibility:** every item, view and dialog is reached with the keyboard alone, carries an accessible name and state, and works with Orca, as `doc_software.md`'s first criterion asks. Type-ahead selects by name in the current folder.
- **Languages:** strings through `athanor-i18n`; right-to-left layouts mirror; dates and sizes follow the locale.
- **Visual language:** libadwaita's materials untouched; the accent and the colour scheme come from libadwaita's own reading of the portal Settings, as for every libadwaita application.
- **Hidden files** follow `org.gtk.gtk4.Settings.FileChooser show-hidden` (false on the desktop, 2026-10-05), shared with GTK's dialogs.

## 5. Acceptance

"CI" runs on every change; "athanor-ref" is the reference laptop, on a fresh install of the image, judged by the maintainer.

1. (CI and athanor-ref) A 2 GiB folder moved from the btrfs home to an exFAT stick and back arrives whole, with the same checksums, and the source is gone only after the destination is complete.

3. (CI and athanor-ref) A file pasted onto a file of the same name offers Replace, Skip and Keep both; Replace leaves the new content, Keep both leaves both, Skip leaves the old one; a folder onto a folder offers Merge, Skip and Keep both, never Replace.

5. (athanor-ref) An archive extracted from the window runs in an `athanor-files-helper` unit visible in `systemctl --user list-units` during the extraction, and that unit has no access to the home, the network or the session bus (the sandbox tests of FM20).
6. (athanor-ref) The file manager shows thumbnails of a PNG, a JPEG and a PDF, and of an OpenDocument file through the gsf thumbnailer, and the journal holds no glycin warning that a loader ran without its sandbox.

## 6. Decisions taken

Decided by the maintainer on 2026-10-05.

1. **How far the window is confined** (FM3). Landlock writes beneath `$HOME`, `/run/media`, `/tmp` and `/dev/dri` and no TCP now; a bus filtered through `xdg-dbus-proxy` once the launch broker of `doc_session_daemons.md` exists (SD22 step 7). Reason: the boundary that matters surrounds the parsers (FM8, FM10), and the filtered bus needs a broker that every application needs.
2. **Where file operations run** (FM5). In the window's process, on worker threads, with the crash journal. Reason: the journal leaves nothing half-written after a crash, and a separate service would add an interface whose only gain is surviving that crash.
3. **Which library reads archives** (FM8). Pure-Rust parsers; no RAR in the first release. Reason: a memory-safe parser inside the sandboxed unit gives two independent layers for every archive, and libarchive's RAR reader had recent memory-safety flaws.
4. **Symbolic links inside archives** (FM9). A link is kept when its target stays inside the extraction root; no link is followed while extracting. Reason: `RESOLVE_NO_SYMLINKS` already closes the escape of the CVEs in section 1, and skipping every link breaks source trees and application bundles.
5. **Thumbnails** (FM10). Athanor's own runner: `athanor-preview` for images and PDFs, installed thumbnailers in helper units, the cache written by the window. Reason: GNOME's bubblewrap sandbox cannot start under the window's Landlock ruleset.
6. **Network locations** (FM15). None now; confined mounts of Athanor's own later. Reason: each gvfs backend is a network parser running with the user's rights.
7. **Search** (FM11). By name, plus localsearch's index through `athanor-search`. Reason: the bounded query code exists and localsearch is confined.
8. **Creating archives** (FM8). `.zip` and `.tar.xz`, against the draft's recommendation of `.zip` only; `.tar.xz` keeps permissions and links, and neither format is written by following a link. Reason: Linux users need an archive that keeps modes and links, and `.zip` remains the format for sending files to any system.
9. **Which socket an opened application gets** (FM4). The file manager's restricted socket now; a context of its own through the launch broker later. Reason: both keep the application behind a context, only the app id differs, and no new interface is needed now.
10. **Who writes an extracted archive** (FM8). The helper parses and streams, the window writes; this amends the wording of `doc_software.md` decision 7 (section 3). Reason: the helper needs no write access at all, and the writing code is the copy engine the window already trusts.

**Open doubts the decisions left open.**

- Decisions 1 and 9 are met by the launch broker of `doc_session_daemons.md` (SD7 to SD9) at its step 7 (SD22); until then, the limits declared in FM3 and FM4 stand.
- Decision 3: spike S5 shows whether the pure-Rust readers run under the helper's system-call filter and memory limit against the bomb corpus.
- Decision 9: spike S1 shows whether an application keeps its windows on the inherited socket after the file manager exits.
- The automount and the `noexec` default inherited from `doc_disks.md` decision 6: spike S7.

## 7. Amendment of 2026-10-06: the chooser's view until 1.0, Nautilus with a declared risk

Maintainer decision A2-14 (#159), from specification audit 2 of 2026-10-05. It overrides sections 1 to 6 where they disagree.

- **What is built before 1.0.** Only `system/athanor-files-view` (FM2, FM17): the directory model, the list and grid views, the path bar with an editable location and the sidebar, as the library the FileChooser backend of `doc_portal.md` needs. It holds no operation, launch or archive code (FM17), so it is built and tested without the window. Its sidebar shows bookmarks (FM12) and, once the `udisks` module of `doc_disks.md` DK3 exists, drives (FM14); its thumbnails come through the host's callback (FM17), which `doc_portal.md` decides.
- **What waits until after 1.0.** The window `athanor-files`, `athanor-files-ops`, the helper `athanor-files-helper` and FM21's steps 1 and 3 to 5, with the acceptance of section 5. The design stays as written; it is reopened by a revision of this document after 1.0, which first meets the scope budget of `doc_shell.md` SH3: a written "why not upstream" (decision 7 of `doc_software.md` gives it: archives are parsed inside Nautilus's own process) and a maintenance owner, whom the maintainer names. Until then nothing removes `nautilus` from `athanor-desktop-ui`.
- **Why.** Audit 2 measured the cost: an essential file manager is of the bar's order, about 13,000 lines of Rust, and parity with Nautilus takes months (`doc_software.md` decision 7). The chooser's view is needed for 1.0 anyway, because the portal's FileChooser backend has no dialog without it (`doc_software.md` decision 7, "three conditions"); the rest of the file manager is not.
- **Nautilus for 1.0, with a declared risk.** Nautilus 49 is the file manager of 1.0, unconfined, running with all of the user's rights. What that leaves open, stated rather than hidden:
  - it extracts archives in its own process, through gnome-autoar and libarchive (section 1), so a parser flaw in a downloaded archive runs as the user;
  - it reaches the network and the whole session bus, and may write the places where an attack persists: autostart entries, shell profiles, user units, and its own scripts folder `~/.local/share/nautilus/scripts`;
  - it loads the `nautilus-extensions` installed on the system (section 1).
  In the threat model of audit 2 (maintainer decision A2-9, #151) unconfined user code is the user, so this is the same class as any program the user runs, and the maintainer accepted it until 1.0 (A2-14). The risk ends when `athanor-files` replaces Nautilus after 1.0.
- **Acceptance for 1.0.** The view's tests run with the portal's FileChooser backend (`doc_portal.md`); on a fresh install Nautilus opens every default application of `doc_software.md` decision 7 from a file of its type, as acceptance item 16 of that document asks.
- **Changes to other documents.** `doc_software.md` section 9 (the Files and Archives rows: Nautilus through 1.0); `doc_portal.md` builds its chooser on `athanor-files-view` before 1.0 (owed to that document). The DK16 rows of `doc_disks.md` that this document implemented wait with the window; `doc_disks.md` section 7 points them at GNOME Disks.
