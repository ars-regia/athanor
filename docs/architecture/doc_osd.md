# Athanor on-screen display

Status: **revision 1 draft, 2026-10-05: the maintainer's decisions applied; text not yet reviewed.** It is the specification of the on-screen display of `doc_shell.md` (SH1), which leaves together with the polkit agent of stage 4 (section 6, decision D7): the transient overlay that confirms what a hardware key did, and the end-of-session dialogs (log out, restart, shut down) that the lock and prompts specification hands to it (decision D12). The overlay covers volume and microphone mute, screen and keyboard backlight, the keyboard layout, airplane mode, the touchpad switch and the media keys; Caps Lock and Num Lock are excluded from 1.0 (M3). It designs the program that owns the overlay, the dialogs and the keys, the path a key takes from cosmic-comp to a service, the models it reuses from `doc_control_center.md`, its surfaces, placement, accessibility and visual language, its privileges, the tests, the order of construction, and the single step in which cosmic-osd leaves the image. At that step `athanor-osd` also draws monitor identification and the headset and headphone choice dialog, so nothing cosmic-osd does is lost (OD19, M6).

## 2. Decisions

**OD1. One program owns the keys, their feedback and the end-of-session dialogs** (M1, D12). A new program, `athanor-osd`, receives each key's action, carries it out through the models of `athanor-services`, and shows the result; it also draws the log-out, restart and shut-down dialogs (OD18), the numbers that identify monitors and the headset or headphone choice dialog (OD19). The program that acts is the program that shows, so the overlay shows the value the service confirmed, with no second process to keep in step.

- **Resident and hidden**, as the launcher and the control center: one process per session, started by `athanor-osd.service` in `athanor-session.target` by preset, with no surface mapped while nothing is shown.
- **Its own models**, as CC2 requires of each process: it starts the audio, battery, network and media models of `athanor-services` on its own runtime through `athanor-controls`' bridge (`bridge.rs:28-51`), and the compositor client's keyboard-layout and output models.

**OD2. Crates.**

- `forge/specs/athanor-osd`: the program. It depends on `athanor-services`, `athanor-controls` (the bridge and the catalogue only, no page), `athanor-compositor-client`, `athanor-style`, `athanor-i18n`, `athanor-unit`, `gtk4` and `gtk4-layer-shell`. No new library and no new external crate.
- **The logic has no GTK type** (SH4): the step arithmetic, the bounds, the decision whether a change is shown (OD5), the coalescing of announcements (OD11), the timeout, and the dialogs' countdown, inhibitor filtering and choice of logind call (OD18) live in a module of the program tested without a display.
- `athanor-compositor-client` stays the only crate that knows COSMIC. It gains three functions: `add_binding_once(key, action, marker)`, which adds a binding to cosmic-comp's `custom` shortcuts once per user and respects a binding the user has made for the same key; `set_touchpad_override(on)`, which writes `input_touchpad_override` in `com.system76.CosmicComp`, as `cosmic-osd touchpad` does today (cosmic-osd `src/components/app.rs:1507-1530`); and `next_layout_group()`, which calls `set_group` on the keyboard-layout protocol it already carries, as cosmic-settings-daemon does (`src/wayland.rs:70-80`).
- `athanor-services` gains what CC4 already promises and what the overlay needs (OD6). These are additions to the control center's models, not a second copy of them.

**OD3. The key path: cosmic-comp catches, `athanor-osd` acts.** cosmic-comp keeps catching the keys, because it owns input and the end state keeps it. Each key's command becomes a call to `athanor-osd`.

- **Rebinding.** In the retirement step (OD15), at its first start for a user, `athanor-osd` rebinds each system action below with `set_system_action_once` (LA8). An action the user has set to a command of their own stays theirs, and its key then shows no overlay.

  | `VolumeRaise`            | XF86AudioRaiseVolume  | `VolumeUp`                  |
  | `VolumeLower`            | XF86AudioLowerVolume  | `VolumeDown`                |
  | `Mute`                   | XF86AudioMute         | `ToggleMute`                |
  | `MuteMic`                | XF86AudioMicMute      | `ToggleMicMute`             |
  | `BrightnessUp`           | XF86MonBrightnessUp   | `BrightnessUp`              |
  | `BrightnessDown`         | XF86MonBrightnessDown | `BrightnessDown`            |
  | `KeyboardBrightnessUp`   | none (OD3, bindings)  | `KeyboardBrightnessUp`      |

  | `InputSourceSwitch`      | Super+Space           | none: `athanor-shelld`'s `NextInputSource` (`doc_languages.md` LN9); the overlay shows the result from the `KeyboardLayout` event |

- **Bindings COSMIC does not make.** With `add_binding_once`, `XF86KbdBrightnessUp` and `XF86KbdBrightnessDown` are bound to the keyboard-brightness system actions, `XF86KbdLightOnOff` to a command calling `CycleKeyboardBrightness`, and `XF86WLAN` and `XF86RFKill` to a command calling `ToggleAirplane`.
- **The command** is `gdbus call --session --dest os.athanor.Osd1 --object-path /os/athanor/Osd1 --method os.athanor.Osd1.<Method>`, the form LA8 uses for the launcher. Each press costs one `/bin/sh` and one `gdbus` process; spike O1 measures it against ST5's 50 ms.
- **D-Bus activation.** `athanor-osd` ships a session-bus service file with `SystemdService=athanor-osd.service`, so a key pressed while the program is down starts it instead of being lost.
- **The name `cosmic-osd` stays as a client.** cosmic-settings-daemon starts the headset dialog by running `cosmic-osd confirm-headphones --device <id>` from `PATH` (cosmic-settings-daemon `audio-server/src/backend.rs:696-708`, epoch-1.8.0), and no unit of ours can change that while the daemon stays (stage 8). From the retirement step the `athanor-osd` package ships `/usr/bin/cosmic-osd` as a symbolic link to `athanor-osd`; started under that name, the program is a one-shot client that accepts only `confirm-headphones --device <id>`, `identify-displays` and `dismiss-display-identifiers`, makes the matching call of `os.athanor.Osd1` (OD19) and exits; any other argument exits with status 2 and one line on standard error. The package obsoletes cosmic-osd. OD19 gives the reasons and the admission. At step 8 of the session-daemons construction (`doc_session_daemons.md` SD22) the link loses `confirm-headphones`, since `athanor-sessiond` calls `ConfirmHeadset` itself (SD15).
- **Not taken here:** `ScreenReader` belongs to `doc_accessibility.md` and `DisplayToggle` to the display settings (OD14). Until those specifications rebind them, they keep COSMIC's commands; `DisplayToggle` has no default key (section 1).
- **The end state.** No key goes through cosmic-settings-daemon, `wpctl`, `playerctl` or cosmic-osd, so the stage that removes cosmic-settings-daemon (stage 8) has no key to move.

**OD4. The interface `os.athanor.Osd1`.**

- **Methods**, each without arguments and returning nothing: the fourteen of OD3's table that name a method here (`InputSourceSwitch` goes to `athanor-shelld`, LN9), plus `CycleKeyboardBrightness`, `ToggleAirplane` and `AskRestart` (the bar's power menu, OD18), and `IdentifyOutputs` and `DismissOutputIdentifiers` (OD19). Two methods take an argument: `ConfirmHeadset(u device)` opens the headset or headphone dialog for a PipeWire device (OD19), and `ShowKeyboardAid(s notice)`, which shows a sticky, slow or bounce key notice (`doc_accessibility.md` AX11); `notice` is one of a fixed set of names and anything else is refused. A method acts and shows, or opens a dialog that asks; it never returns state, so the interface reveals nothing a caller could not see on screen.
- **Admission.** Any peer on the session bus may call. Every method does what the person can already do from the keyboard, the bar or the control center, under the target service's own policy: logind admits `SetBrightness` from the active session (CC8), NetworkManager its radio switches, PipeWire its volume; the `Ask` methods only open a dialog, and nothing ends the session until the person confirms in it or lets its countdown run. A Flatpak application cannot reach the name, which `xdg-dbus-proxy` does not expose. The caller's cgroup is logged when it is not cosmic-comp's or the bar's, as BR1's informative check. `ShowKeyboardAid` and `ConfirmHeadset` are the exceptions. `ShowKeyboardAid` is admitted only from the cgroup of `athanor-a11y.service`, checked through the caller's pidfd as `athanor-shelld` checks its callers, because a notice from any other peer would misstate the keyboard's state. `ConfirmHeadset` is admitted only from the cgroup of `cosmic-settings-daemon.service` until step 8 of the session-daemons construction, and from the cgroup of `athanor-sessiond.service` from that step (`doc_session_daemons.md` SD15, SD22), by the same check, because it takes the keyboard (OD19); a peer that is not the daemon would otherwise be able to grab the keyboard with a dialog.
- **Rate.** More than 30 calls within one second from one sender are dropped beyond the thirtieth, with one journal line; a held key never reaches this, since it runs once (OD3).
- **Name.** `athanor-osd` owns `os.athanor.Osd1`; a second instance that cannot take the name exits. It owns no COSMIC bus name: nothing in COSMIC 1.8.0 addresses `com.system76.CosmicOnScreenDisplay` (OD19).

**OD5. What shows, and when** (M2).

- **A key always shows**, also when the value does not change: volume up at the ceiling shows the full bar, so the person sees that the key worked.
- **A change the hardware made shows** when no shell control asked for it: the keyboard layout changed by any means (including a layout shortcut of XKB options), the screen backlight changed by the firmware (OD6), the keyboard backlight changed by the embedded controller, the radios blocked by a hardware switch.
- **A change made in a shell control does not show:** a slider of the bar, the control center or Settings is its own feedback. A change made by another application (a mixer, `brightnessctl`) does not show either.
- **Media keys show** the action (play, pause, next, previous) with the player's name, not the track; the track belongs to the media controls (F-osd-14 is excluded, OD14).
- **One overlay at a time.** A new kind replaces the one on screen in place, within the same frame budget; a repeat of the same kind updates the value in place. An open end-of-session dialog hides the overlay until it closes.

- **Steps.** Volume moves by 5 % up to 100 %, or up to 150 % when CC5's opt-in is on; raising the volume of a muted sink unmutes it. Screen brightness moves by 5 % of the maximum and never below one raw step, as the battery model already does (`battery.rs:533-558`). Keyboard brightness moves by one hardware level; `CycleKeyboardBrightness` wraps from the highest level to off.
- **Each key acts on the state it sees.** A key press while a previous command is still running is applied to the value that command will set, so five quick presses move the volume by 25 %, not by 5 %. The battery model's brightness coalescing already behaves this way.

**OD7. The overlay's surface.** One layer-shell surface per output, created once, pinned and always mapped, as `doc_launcher.md` LA8 requires (cosmic-comp disconnects a client that destroys, unmaps and remaps, or rebuilds an unpinned layer surface). Hidden, it holds no content, an empty input region, no keyboard interactivity and a size of 1×1 on the background layer; shown, it takes the layer `overlay` and the interactivity named below.

- **Layer** `overlay`, so the overlay shows above a fullscreen video. **Keyboard interactivity** `none`, as the old shell's overlay already set it (`osd.rs:122-123`). **Exclusive zone** 0, which asks the compositor to move the surface clear of every surface with a positive exclusive zone, such as a bar at the bottom (`wlr-layer-shell-unstable-v1.xml:168-171`, wayland-protocols-wlr 0.3.12). **Input region** empty, so a pointer click passes through to the window beneath.
- **Drawn with Cairo** inside GTK4, as SH4 requires for resident surfaces.
- **While the session is locked** the compositor shows only the lock surface, so the overlay does not appear; the keys cosmic-comp still runs while locked act anyway. Feedback on the lock screen belongs to the lock specification.

**OD8. Placement.**

- **Output:** the output of the active workspace, as the bar's popups (BR4), read from the compositor client.
- **Position:** centred horizontally, anchored to the bottom edge with a margin of 48 px (eight steps of the grid), above any surface with an exclusive zone there (OD7). When the bar of that output is at the bottom and floats without an exclusive zone, the margin grows by the bar's thickness and its 6 px edge, read from `athanor-layout`.
- **The dock** is drawn in the top layer and may sit under the overlay while revealed; the overlay is in the overlay layer and is short-lived, so it wins.
- **Right-to-left:** the position does not change; the contents mirror (icon at the start edge, value at the end edge).

**OD9. Contents.**

- **A level:** an Adwaita symbolic icon, a bar from 0 to 100 % and the value as a number with `tnum`. Above 100 % the part beyond 100 is drawn in the warning colour of the visual language. Mute draws the bar in the insensitive colour with the muted icon.
- **A state:** an icon and a short label (airplane mode on, touchpad off, the layout's long name from `layout_names`, the player's action).
- **The icons** are those the bar and the control center use for the same states (`output_icon`, `input_icon` thresholds 34 and 67 in `audio.rs`), so the same state has the same icon everywhere.
- **Text** comes from the catalogue of `athanor-i18n`; numbers follow the locale.

**OD10. Visual language.**

- **Shape:** `radius.panel` (24); padding 18; width fixed at 300 px for a level so it does not jump with the number, a state as wide as its label within 120 to 420 px.
- **Surface:** opaque, the shell's neutral surface tinted by the accent as the visual language defines it; no blur. **Shadow:** `float`, because the overlay stands above windows (section 3 adds it to VL9's list).
- **Motion:** in and out with `motion.normal`, 200 ms, on the curve of VL9: opacity from 0 and a rise of 12 px. A value that changes on screen moves its bar in the visual language's 100 ms step. With reduced motion every duration is 0.
- **Timeout:** 2 s after the last change, restarted by each change, the cycle the old shell's overlay used with 1.8 s (`osd.rs:317-348`). A pointer never holds it, since the surface takes no input.
- **The four variants** (light, dark and their high-contrast forms) follow `athanor-style`, with text 4.5:1 and the bar 3:1 against the surface.

**OD11. Accessibility.**

- **No focus, ever, for the overlay** (OD7): it never moves the keyboard focus or the screen reader's position.
- **Announcement:** each shown change is announced with `gtk_accessible_announce` at polite priority (exported by libgtk-4 4.20.4, bound as `AccessibleExt::announce` behind feature `v4_14` in gtk4-rs 0.11.4, both checked 2026-10-05). The text is the content in words: "Volume 45 percent", "Muted", "Keyboard layout English (US)", "Airplane mode on".
- **Coalescing:** a run of changes of the same kind is announced once, 300 ms after the last, with the final value, so five quick presses read one number.
- **Large text** grows the surface with the font; the 300 px width is a minimum.
- **The AT-SPI tree** holds the overlay as a window with role `status` and the current text as its name while it is shown; it is removed from the tree while hidden.
- The end-of-session dialogs have their own rules in OD18.

**OD12. Privileges.**

- **The unit** `athanor-osd.service`, in `session.slice`, with the hardening of the bar's unit: `ProtectSystem=strict`, `ProtectHome=read-only`, `NoNewPrivileges`, `SystemCallFilter=@system-service`, `MemoryHigh` and `MemoryMax` from the budget (OD13).
- **Landlock at start**, as BR1: read access to `/sys/class/backlight`, `/sys/class/leds`, the icon and theme directories and the user's COSMIC shortcut and compositor configuration (through the compositor client); write access only to the two COSMIC configuration files the compositor client writes (the shortcuts and `input_touchpad_override`), to the one socket `$XDG_RUNTIME_DIR/com.system76.CosmicSettings` that connecting to cosmic-settings-daemon's audio service needs (OD19), and to what GTK needs.
- **No privilege of its own.** Every change goes through a service under that service's policy (CC8): logind for both backlights and for restart and shut down, the user's systemd for log out, PipeWire for audio, NetworkManager for the radios, the MPRIS player. No polkit action is added and none is changed.
- **No password, ever.** When logind needs authorisation for a power action, polkit asks `athanor-polkit-agent` (the lock specification's D12 interface); `athanor-osd` never shows a password field and never reads one.
- **Keys on the bus are trusted as keys:** the overlay cannot tell a key from a caller (OD4), which is acceptable because no method does more than a keyboard can, and the `Ask` methods only open a dialog.

**OD13. Crash, budget, idle.**

- **Crash policy** of SH8 and BR1: restarted by systemd after 1 s; after 5 failures within 10 minutes it stays down with one journal line. D-Bus activation (OD3) then fails as well, because systemd refuses to start a unit past its start limit: the keys do nothing until the next login, and the bench sees a failed unit. The bar's power menu then falls back to its own confirmation (section 3, BR3).
- **Recovery** (ST5): killed with `SIGKILL`, the next key press within 1 s of the kill shows its overlay. An overlay or a dialog on screen at the time of the kill does not reappear, and a dialog killed before its countdown ended ends nothing.
- **Memory:** at most 32 MB PSS at rest with no surface mapped, after an hour of use. This is a proposal; the first measurement confirms or corrects it.
- **Idle:** hidden, the program holds no timer and wakes only on a model's signal or a call; the backlight signal (OD6) replaces the battery model's re-reading on every wake. The dialog's countdown timer exists only while a dialog is open.

**OD18. The end-of-session dialogs** (D12; F-lock-26 to 29, 31, 32).

- **Three dialogs:** log out, restart and shut down, opened by `AskLogOut`, `AskRestart` and `AskPowerOff`: from the keys (OD3) and from the bar's power menu, which from the retirement step stops confirming these three itself (section 3). Lock and suspend keep the bar's own confirmation; "Restart to update" stays the update service's request (BR3, SH11).
- **The surface:** one layer-shell surface per output, shown on the output of the active workspace, layer `overlay`, keyboard interactivity `exclusive` while shown, so the keys reach the dialog; centred on the output. As OD7 says (`doc_launcher.md` LA8), the surface is created once per output, pinned and kept mapped: closed, it holds no content, an empty input region, no keyboard interactivity and a size of 1×1 on the background layer. A second call while a dialog is open replaces its kind in place.
- **Asking:** a question ("Shut down now?"), the confirming button named by the action, and Cancel, focused when the dialog opens, so a stray Enter backs out, as the bar's menu does (`power.rs:1-2`). Escape and Cancel close the dialog without a call.
- **Countdown** (F-lock-26): 60 s, as cosmic-osd's `COUNTDOWN_LENGTH`; the text reads "Shutting down in 52 seconds" with `tnum`, and at zero the dialog acts as if confirmed. There is no countdown while a blocking inhibitor is listed.
- **The calls:** log out stops `athanor-session.target` with mode `replace` on the user's systemd, as the bar does (`logind.rs:86-92`); restart is logind `Reboot(true)`; shut down is logind `PowerOff(true)`. The interactive flag lets polkit ask through the session's agent when the policy wants it.
- **Firmware setup** (F-lock-28): when `CanRebootToFirmwareSetup` answers `yes`, the restart dialog offers "Restart to Firmware Setup", which calls `SetRebootToFirmwareSetup(true)` and then `Reboot(true)`, as cosmic-osd does. The boot menu is not offered: Athanor's boot choice for a person is "Go back to the previous version" (`doc_bar.md:114`).
- **What would be interrupted** (F-lock-27): on opening a restart or shut-down dialog, `athanor-osd` reads logind's `ListInhibitors` and lists, by `who` and `why`, each inhibitor whose `what` contains `shutdown` and whose mode is `block`; with one listed, the confirming button reads "Restart Anyway" or "Shut Down Anyway", and the same call goes to logind, which asks polkit for the override (`auth_admin_keep`, section 1). Whether the programs that write the system and applications (rpm-ostree, bootc, Flatpak) hold such an inhibitor while they write is unverified (spike O6). On opening any of the three dialogs, `athanor-osd` also calls `SessionInhibitors` (PT10, `doc_portal.md`) and lists the log-out and user-switch inhibitors by application and reason in the log-out, restart and shut-down dialogs, beside logind's `shutdown` blockers; with any listed, the confirming button carries the same "Anyway" wording.
- **The password** (F-lock-32): asked by polkit through `athanor-polkit-agent`, only when logind's policy wants it; `athanor-osd` never reads it (OD12). On the image the active session powers off without one (section 1); a rule that always asks is not added, since this document adds and changes no polkit action.
- **Excluded, with reasons.** F-lock-29, hold-to-confirm: the dialog already takes two separate presses, Cancel is focused, and a hold gesture is a barrier for switch and motor access (ST7). F-lock-31, the prompt to force-close an unresponsive application: only the compositor knows that a client stopped answering its pings, and cosmic-comp 1.8.0 offers no event that says so to a client (unverified); the entry returns to this document when a compositor event exists, as one more dialog of the same program.
- **Visual language and accessibility:** `radius.panel` (24), padding 24, the opaque tinted surface, the `float` shadow, in and out in `motion.normal` (200 ms), zero with reduced motion; text from `athanor-i18n`, mirrored for right-to-left. The dialog is an `alert-dialog` whose name is the question; its opening is announced at polite priority, and the countdown only at opening and at 10 s left, not each second.

**OD19. Monitor identification and the headset dialog** (M6, F-osd-08, F-osd-09). When cosmic-osd leaves (OD15), `athanor-osd` draws both, so no feature of cosmic-osd is lost. What cosmic-osd 1.8.0 does, read from its tag epoch-1.8.0 and from the sources of the programs that call it (all checked 2026-10-05):

- **Identification in cosmic-osd.** It numbers the enabled outputs by connector name in alphabetical order from 1, shows nothing below two enabled outputs (`src/components/app.rs:474-516`), and draws on each output a layer-shell surface of layer `overlay`, anchored top, 48 px from the top edge, exclusive zone -1, keyboard none, empty input region, namespace `osd` (`src/components/osd_indicator.rs:183-228`): a square with the accent colour as background and the number in the on-accent colour at 45 pt, gone after 1 s (`osd_indicator.rs:158-160, 399-436`). Its triggers: the subcommands `identify-displays` and `dismiss-display-identifiers` (`app.rs:73-78`), and an output that disappears (`app.rs:972-990`).
- **Who calls identification: nobody in COSMIC 1.8.0.** The draft's first revision said cosmic-settings calls cosmic-osd for it. That is not so in this version: no string `identify` or `IdentifyDisplays` in the installed `/usr/bin/cosmic-settings` (cosmic-settings-1.8.0-1.fc43), and none in the sources of cosmic-settings, cosmic-settings-daemon, cosmic-comp, cosmic-applets, cosmic-session and cosmic-randr at epoch-1.8.0. Its own display page numbers outputs by connector name too (`cosmic-settings/src/pages/display/mod.rs:692-700`, over all outputs, not only the enabled ones: whether its tab labels use that position is unverified, spike O8). No call has to be answered and no route has to be planned; the entry points below serve the Settings app of stage 6 and any later cosmic-settings that calls them.
- **The headset dialog in cosmic-osd.** cosmic-settings-daemon's audio backend, on a device whose profile gains a headset route, more than 1 s after the session started and when that route was not chosen before, runs `cosmic-osd confirm-headphones --device <id>` (`audio-server/src/backend.rs:680-708`). The program draws a dialog on a layer surface of namespace `dialog`, keyboard interactivity `exclusive`, anchor none: two image buttons "Headphones" and "Headset", Headphones selected, a "Sound settings" button, Confirm and Cancel, and a 60 s countdown that at zero confirms (`app.rs:1404-1460`, `app.rs:673-684`, `app.rs:632-657`). Confirm calls the daemon's varlink audio service at `$XDG_RUNTIME_DIR/com.system76.CosmicSettings`, interface `com.system76.CosmicSettings.Audio`, method `select_headphone_profile` or `select_headset_profile` with the device id, ignoring the answer (`app.rs:105-119`; `audio-client/src/lib.rs:62-66, 96-103`); the daemon then sets the PipeWire profile and route (`audio-server/src/backend.rs:259-330`). No bus name takes part: the daemon runs the program by name from `PATH`.
- **The routing.** Nothing addresses `com.system76.CosmicOnScreenDisplay` in COSMIC 1.8.0 (it appears only as cosmic-osd's own application id, `app.rs:577`), so `athanor-osd` owns no COSMIC bus name and there is nothing to impersonate. The one thing outside our control is the command name the daemon runs; OD3's `cosmic-osd` client link answers it and turns it into a call of our own interface. The link is deliberate and narrow: three subcommands, every other refused.
- **New methods of `os.athanor.Osd1`** (OD4): `IdentifyOutputs()`, `DismissOutputIdentifiers()` and `ConfirmHeadset(u device)`. The first two are open to any peer, since the numbers are what the person sees on the screens anyway; `ConfirmHeadset` is admitted from the cgroup of the daemon that decides, only (OD4): cosmic-settings-daemon's until step 8 of the session-daemons construction, `athanor-sessiond.service`'s from that step (`doc_session_daemons.md` SD15), because the dialog takes the keyboard. Until step 8 the client link runs in cosmic-settings-daemon's cgroup, as a child of the daemon; from step 8 `athanor-sessiond` calls `ConfirmHeadset` itself and the link has no `confirm-headphones`.
- **Identification: trigger.** The method; and the set of enabled outputs changing, whether an output appears, disappears, is enabled or is disabled, read from the compositor client's output model and settled for 300 ms. cosmic-osd shows numbers only when an output disappears; showing them for a monitor just plugged in is the moment a person needs them, so it is added. Nothing is shown below two enabled outputs. The numbering is cosmic-osd's: enabled outputs in connector-name order, from 1.
- **Identification: surface.** One layer-shell surface per enabled output, created once, pinned and kept mapped as OD7 says (`doc_launcher.md` LA8) and hidden between calls, layer `overlay` while shown, anchored top and centred, 48 px from the top edge, exclusive zone -1 so that the number stays on the output whatever bar or dock sits there, keyboard interactivity `none`, empty input region; drawn with Cairo (OD7). The surface is a square of 96 px (a multiple of 6) in `radius.panel` (24), the accent as background and the on-accent colour for the numeral at the `display` size step of the visual language with `tnum`, in `motion.normal` in and out (zero with reduced motion), the `float` shadow. A second call, or a new change of the outputs, replaces the set in place and restarts the timer.
- **Identification: timeout.** 3 s after the last call, where cosmic-osd uses 1 s (`osd_indicator.rs:158-160`): one second is too short to read a number on a second screen and to look back. `DismissOutputIdentifiers` removes the numbers at once.
- **Identification: accessibility.** No focus. Each surface is a window of role `status` named "Display 2", present in the AT-SPI tree only while shown. One announcement at polite priority, from the surface on the active output, reads all of them: "Displays: 1 eDP-1, 2 HDMI-A-1", coalesced as OD11 coalesces. The connector names are in the text because a number alone tells a person who cannot see the screens nothing.
- **Headset dialog: trigger.** `ConfirmHeadset(device)`, called by the client link for `confirm-headphones --device <id>` until step 8 of the session-daemons construction (`doc_session_daemons.md` SD22), and by `athanor-sessiond` itself from that step (SD15). The daemon decides when (a new headset route, not at session start, not twice for one choice), and `athanor-osd` does not second-guess it. While the session is locked the compositor shows only the lock surface (OD7), so the call is dropped with one journal line and the daemon's own profile stays. A second call for another device replaces the dialog in place.
- **Headset dialog: surface.** The dialog of OD18: layer `overlay`, keyboard interactivity `exclusive`, centred on the output of the active workspace, pinned and kept mapped as OD18 says (`doc_launcher.md` LA8), `radius.panel`, padding 24, the opaque tinted surface, the `float` shadow, `motion.normal`. Contents: the question "What did you plug in?", two choices in one radio group, "Headphones" and "Headset with microphone", each with its Adwaita symbolic icon (`audio-headphones-symbolic`, `audio-headset-symbolic`), Headphones selected as in cosmic-osd, and the buttons Apply and Cancel. The initial focus is on the selected choice, so a single Enter applies the default and arrow keys move between the choices. Escape and Cancel close the dialog without a call. From the step where Settings ships (`doc_settings.md` SE26 step 6), the dialog carries a "Sound settings" button, as cosmic-osd's does. The button calls `os.athanor.Settings1.Show("sound")` and closes the dialog without applying a choice. Before that step it has no such button.
- **Headset dialog: timeout.** 60 s without any key or pointer input, as cosmic-osd's countdown; at zero the dialog closes **without** a call, where cosmic-osd confirms the default choice. A choice nobody made is not applied, and the daemon's own selection stands. No countdown is drawn, since nothing urgent is at stake; any input restarts the 60 s.
- **Headset dialog: accessibility.** An `alert-dialog` whose name is the question; the radio group is exposed as such with the selected choice announced; its opening is announced at polite priority; the dialog is mirrored for right-to-left; large text grows it.
- **What is called.** Apply makes one call to the daemon's varlink audio service: connect to `$XDG_RUNTIME_DIR/com.system76.CosmicSettings` and run `com.system76.CosmicSettings.Audio` method `SelectHeadphoneProfile` or `SelectHeadsetProfile` with the device id, a JSON object ended by a NUL byte, written with `serde_json` (workspace `Cargo.toml:110`) and `tokio`'s Unix stream, with no new crate. The call sits in the audio model of `athanor-services` as one command, since stage 8 replaces the daemon's role and with it the body of that command; `athanor-osd` holds no varlink code of its own (OD6). The varlink method and parameter names are those of zlink's proxy in `audio-client/src/lib.rs:96-103`; the exact wire names are unverified (spike O8). The answer is read, and an error is one journal line and a line in the dialog's status, where cosmic-osd ignores it. **From step 8 of the session-daemons construction** (`doc_session_daemons.md` SD15) Apply makes no varlink call: the same command of the audio model selects the profile and the port with libpulse, `athanor-osd` is otherwise unchanged, and the varlink body leaves with cosmic-settings-daemon. Whether the libpulse change equals the daemon's PipeWire route change on the reference laptop is spike S6 of that document.
- **A prerequisite.** The dialog is useless if the daemon's audio socket is not bound, and on the shipped image it is not (section 1: the unit's `ProtectSystem=strict` without write access to `$XDG_RUNTIME_DIR`, `cosmic-settings-daemon.service:21`). M5 chose not to patch that unit because its key role was leaving; its headset role stays until stage 8, so the retirement step carries the one-line fix, write access to the socket, and `ConfirmHeadset` does not open a dialog when the socket is absent (it logs once). Whether the daemon still spawns the dialog when its varlink thread has failed is unverified (spike O8). The prerequisite ends at step 8 of the session-daemons construction, when the dialog no longer depends on the daemon's socket (`doc_session_daemons.md` SD15).
- **Excluded:** drawing a monitor's name, size or arrangement, which is the display page's job (stage 6); a choice of output for the dialog; a dialog for any device other than the one the daemon names.

## 6. Decisions taken

Taken by the maintainer on 2026-10-05.

- **M1. Which process owns the overlay and the keys** (OD1, OD2). **A:** a new program, `athanor-osd`, that acts and shows. Reason: one process per surface (SH4), a crash of the bar does not take the feedback, and the value shown is the one its own model confirmed.
- **M2. When the overlay shows** (OD5). **A:** keys and changes made by the hardware, never changes made in a shell control. Reason: it shows what the person did without echoing what they are already watching.
- **M3. Caps Lock and Num Lock** (OD14, F-osd-10). **A:** request a lock-state event upstream and exclude the indicator from 1.0. Reason: polling the LED files contradicts the idle rule, and the state is already visible in the text typed.
- **M4. Coexistence with cosmic-osd** (OD15, OD17). **A:** hold the handover until cosmic-osd can leave, and ship both together. Reason: no patch on a package that is leaving, and no duplicate overlays for users.
- **M5. The cosmic-settings-daemon defect on the shipped image** (section 1, OD15). **B:** leave it to `athanor-osd`, which removes the volume keys' dependence on the daemon. Reason: the maintainer chose not to patch a unit whose key role leaves in the retirement step.
- **M6. Monitor identification and the headset dialog at the retirement step** (OD19, OD15, OD17, F-osd-08, F-osd-09). Decided by the maintainer on 2026-10-05 as a follow-up, **against this draft's recommendation** (which was to exclude both, leave them `missing` at the retirement step and give them to the display page of stage 6 and to stage 8). **A:** `athanor-osd` also draws both when cosmic-osd leaves, so there is no gap. Consequences recorded in OD19: the `cosmic-osd` client link, `ConfirmHeadset` admitted from the daemon's cgroup only, a small varlink call in the audio model, and the fix of cosmic-settings-daemon's unit in the retirement step, which M5 had left unpatched.
- **D7 (lock and prompts, joint). How cosmic-osd stops being the polkit agent** (OD15). **A:** cosmic-osd leaves with `athanor-osd` and `athanor-polkit-agent` in one step, with no patch. Reason: relying on registration order is a race, and one step removes the race and the duplicate overlays together.
- **D12 (lock and prompts). Who owns the end-of-session dialogs** (OD18). **A:** this document, with cosmic-osd's replacement; polkit asks the lock specification's agent for any password. Reason: the dialogs replace cosmic-osd's own, and keeping passwords in one trusted program keeps the dialogs free of secrets.
