# Athanor session lock and authentication prompts

Status: revision 1 draft, 2026-10-05: the maintainer's decisions applied; text not yet reviewed. It is the specification for stage 4 of `doc_shell.md`, SH1: the session lock, the polkit authentication agent and the password prompts, designed together because they share the greeter's authentication code and because they are the trusted path. It is also the specification `doc_shell_standard.md`, section 4, step 6 requires for "the session lock and the authentication dialogs". The maintainer took its twelve decisions on 2026-10-05; they are recorded in section 6 and written into the rules. The implementation plan of the keyring prompter's cryptography needs the maintainer's approval before any code (LP12). Amended 2026-10-06: the trusted path (LP13, D10) by maintainer decision A2-6 (#151), the keyring prompter (LP12, D11) by maintainer decision A2-7 (#151), and the threat model is now `doc_threat_model.md`'s, by maintainer decision A2-9 (#151).

## 2. Decisions

**LP1. What the lock and the prompts promise.**

- The lock hides the session's content on every output, keeps input from it, and opens again only after PAM accepts the user's credentials, or after logind's `Unlock` signal for its session (LP4).
- A login password is typed only by the user, travels from the widget that reads it to the process that runs PAM over one local socket, and goes nowhere else: no session-bus name, no file, no log, no environment, no keyring. Every buffer that held it is zeroized; no process that holds it can dump core or be attached with `ptrace` by the user (`PR_SET_DUMPABLE` 0). The keyring password is the one exception, and travels as LP12 says.
- What the lock does not promise is written in section 1: code running as the user can end it. The documents that show the lock say so.

**LP2. Programs and crates.**

| Crate                              | Unit                                                             | Role                                                                                                                                                                                                                          |
| ---------------------------------- | ---------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `system/athanor-auth`              | none, a library                                                  | the conversation model shared by the lock and the agent, and by the greeter from LP18 step 4: prompt kinds, the line protocol of LP8, zeroizing buffers, the fingerprint and error classification; no GTK type, no I/O policy |
| `forge/specs/athanor-lock`         | `athanor-lock.service` (user)                                    | the lock surface: ext-session-lock-v1, logind, the inhibitor, the screen of LP6                                                                                                                                               |
| `forge/specs/athanor-unlockd`      | `athanor-unlockd.socket` and `athanor-unlockd@.service` (system) | the root process that runs PAM for the lock, one per connection, on the model of polkit 127's helper (LP8)                                                                                                                    |
| `forge/specs/athanor-polkit-agent` | `athanor-polkit-agent.service` (user)                            | the session's polkit authentication agent and its dialog (LP11), and the keyring's `org.gnome.keyring.SystemPrompter` (LP12)                                                                                                  |

- The lock and the agent are separate programs: the lock must survive a crash of the agent, and an agent dialog must never appear above the lock.
- Both are user units in `session.slice`, `PartOf=athanor-session.target` (*Amended 2026-10-06 (maintainer decision A2-20, #156):* `doc_session.md` SN3 proposes `PartOf=graphical-session.target` instead, so that the lock and the agent stop after the applications; a proposal awaiting the maintainer. The start and stop order is SN4 and SN5), so that `athanor-shelld` admits them by unit (NC8) and systemd restarts them (LP10). The lock no longer needs to be a child of the session: it finds the session through the `Display` property of `/org/freedesktop/login1/user/self` and verifies that the session's `Type` is `wayland` and its `User` is its own uid; if either fails it exits non-zero and is restarted.
- The step that enables `athanor-lock.service` removes `session_component "$$" cosmic-greeter &` from `athanor-desktop` (line 101) in the same change. cosmic-idle stays where it is until step 1 of the session-daemons construction (`doc_session_daemons.md` SD22), which replaces it with `athanor-idle`.
- The agent is enabled in the change that retires cosmic-osd (LP11), so the session never holds two agents and no unit ordering decides which one registers.
- **Shared logic.** The lock's state machine (unlocked, locking, locked, authenticating, unlocking) and the agent's request queue live in GTK-free modules of their crates, tested without a display, as SH4 requires.

**LP3. Locking on ext-session-lock-v1.**

- The lock binds `ext_session_lock_manager_v1` on the compositor's main socket; it is never launched on a security-context socket, where the global is absent.
- On a lock request it calls `lock`, creates one lock surface for every output, renders the first frame of each, and only then considers the session locked: on the `locked` event it calls `SetLockedHint(true)` on its session. On `finished` (the compositor refused) it logs at error, waits 1 s and asks again; it never reports the session as locked without `locked`.
- An output that appears while locked gets its lock surface at once; one that leaves loses it. Until the new surface commits, cosmic-comp draws nothing on that output (section 1).
- On a successful authentication, or on logind's `Unlock` for its session (LP4), it calls `unlock_and_destroy`, then `SetLockedHint(false)`. No other path calls `unlock_and_destroy`.
- Between locks the process stays resident with no surface, so that locking costs no start-up (ST5).

**LP4. When the session locks and unlocks.**

- **logind's `Lock` signal on the session's own object** is the single trigger. Every other source reaches it through logind: the shortcut Super+Escape and the bar's power menu run `loginctl lock-session`; `athanor-idle` calls `LockSession` after blanking (`doc_session_daemons.md` SD4, from SD22 step 1; cosmic-idle runs `loginctl lock-session` until then) (LP5); `loginctl lock-sessions` from an administrator reaches every session.
- **Before sleep.** At start the lock takes a logind inhibitor `sleep` in `delay` mode, who "athanor-lock", why "Lock the screen before sleep". On `PrepareForSleep(true)` it locks (if not locked already) and releases the inhibitor only when the `locked` event has arrived and a frame of every lock surface has been presented (`wp_presentation` feedback, spike L4), so that resume never shows the session for a frame. On `PrepareForSleep(false)` it takes the inhibitor again. logind suspends anyway after `InhibitDelayMaxSec` (5 s); a lock that misses that bound is a defect counted by the acceptance (section 5, item 3), and the screen stays locked at resume because `lock` was already sent.
- **logind's `Unlock` signal on the session's own object opens the lock** (D5), as cosmic-greeter, GNOME and Plasma do: `loginctl unlock-session` from the user over SSH, or from an administrator, ends a lock the user cannot reach. It grants nothing that code running as the user lacks (section 1). The lock writes one journal line at notice naming the signal; logind's own record of the caller stands beside it.
- **USBGuard follows the lock.** `usbguard-daemon.conf` ships `InsertedDevicePolicy=block`. A root system service, `athanor-usbguard-policy`, sets `apply-policy` only when seat0 has an active user session whose logind `LockedHint` is false, and `block` in every other case: the greeter, the lock, no session, a seat switch, a missing property or an error. It reads logind's Manager, Seat and Session objects and their `PropertiesChanged`, sets the parameter with `usbguard set-parameter` and checks the result, sets `block` before it reads anything, and exits non-zero (and restarts) if it cannot set `block`: it fails closed. It works because the lock sets `LockedHint` (LP3), which today's cosmic-greeter locker never does. It replaces `/usr/bin/athanor-usbguard-hook` and the call at `athanor-session:27-29` with their `|| true`, which are deleted with it. The sandboxing, the tests and the acceptance of the service belong to LP18 step 10, where the service is built. Until then the gap is declared: a device inserted at the lock screen is evaluated by `apply-policy`, so a keyboard (HID, allowed by the baseline) is accepted, and the unlock call of the hook fails silently for a user outside `wheel`. A device inserted while locked and blocked stays blocked after unlock until it is allowed (`doc_disks.md` DK21).
- **The start of a session** never locks, except after a crash (LP10).

**LP5. Idle.**

- Until step 1 of the session-daemons construction (`doc_session_daemons.md` SD22) replaces it, cosmic-idle decides when the screen blanks and suspends, and it locks by `loginctl lock-session` 500 ms after blanking. From that step `athanor-idle` decides, and calls logind `LockSession` 500 ms after the outputs go off (SD4). The lock adds no timer of its own, so there is one idle policy.
- **Factory values** are GNOME's (D6): blank, and so lock, after 5 minutes; suspend after 15 minutes on battery; never suspend on mains. The image ships them as the defaults of the schema `org.athanor.desktop.idle` (`doc_session_daemons.md` SD3): `blank-after` 300, `suspend-after-battery` 900 and `suspend-after-ac` 0, in seconds with 0 for never, read by `athanor-idle` from step 1 of SD22. A user's own setting overrides them. Until step 1 of SD22, no `com.system76.CosmicIdle` defaults file is shipped, so cosmic-idle 1.8.0 uses its compiled defaults: blank after 15 minutes, suspend after 15 minutes on battery and 30 on mains (section 1). On the maintainer's desktop the user's own keys hold `None` for all three timers, which disables them on that account only. Whether a fresh account blanks and suspends at the compiled values is checked by spike L7a.
- The control to change them belongs to the Settings specification (`doc_settings.md`); the idle daemon is `athanor-idle` of `doc_session_daemons.md` (SD4, SD5), which keeps two properties: the lock is triggered only through logind's `Lock`, and an idle inhibitor (CC8's "keep awake", a video player through `zwp_idle_inhibit_manager_v1` or `org.freedesktop.ScreenSaver`) stops the blank and therefore the idle lock, never a lock the user asked for and never the lock before sleep.
- A lid closed or a suspend key goes through logind's sleep and so through LP4's inhibitor; the lock does not watch the lid.

**LP6. What the lock screen shows.**

- **Background:** the Hearth wallpaper of the greeter, opaque and unblurred, the same on every output. The lock reads nothing from the user's files, so the trusted surfaces look alike and a user image cannot be made to imitate a different screen.
- **On the primary output** (cosmic-comp's primary, else the first): the time in the "display" type step, with `tnum`, and the date below it in the body step, in the user's locale and clock format; the user's avatar and full name from AccountsService; the password field (`gtk::PasswordEntry`) with the Caps Lock warning; the keyboard layout as a chip that switches the input source; the fingerprint state for a user with an enrolled finger (LP9); the notification count (LP7); the seal at the top end edge; the accessibility menu (see Accessibility below).
- **On the other outputs:** the time and date only. Typing on any output goes to the one password field.
- **The seal** shows the trust state the greeter shows, read from the same root-owned trust-state file (owner: the shield, `doc_bar.md` BR6 and package 1b-shield); until that file is bound, it shows "Not verified", as the greeter does.
- **Status:** battery level and network connected or not, read-only, through `athanor-services` (CC3); no network or Bluetooth control on the lock screen.
- **Power:** suspend, restart and power off, each through logind under its default polkit actions for an active local session, so nothing new is authorised: anyone at the keyboard can already press the power button. Restart and power off ask for confirmation in place.
- **What is never shown:** window titles, thumbnails, the clipboard, media controls and artwork (D4), notification bodies unless an application's rule says `all`, the user's files, any surface of the session.
- **Errors:** PAM's error text where PAM supplies one, else "Wrong password"; after a failure the field clears and stays insensitive for the delay PAM imposes (`pam_faildelay`, 2 s). When the account is locked out (LP8, D3), PAM's own message names the minutes left, and the field stays insensitive until then; no counter of attempts is shown before that.
- **Accessibility:** every control has an accessible name; the field is focused on lock; the lock is announced as "Screen locked" when a screen reader runs. The lock has its own accessibility menu (F-lock-20), opened by Super+Alt+A (`doc_accessibility.md` AX14), which starts the screen reader and toggles the other features: it reads and writes the keys of AX2 through GSettings (AX13), and `athanor-a11y watch` in the session acts on them, so no surface of the session is involved. The on-screen keyboard (F-lock-19) is offered at the lock only on a cosmic-comp build that passes section 5, item 11 (cosmic-comp#2702); until then the lock offers none and draws no keyboard of its own (`doc_accessibility.md`, AX12, leaves that choice here).

**LP7. Notifications on the lock screen.**

- The lock applies NC5's per-application `lock_screen` rule, read from `athanor-shelld` through `os.athanor.Notifications1`: `List` and `Rules(app)` to read, the `added`, `closed` and `RulesChanged` signals to follow. It needs `athanor-lock.service` admitted for those and nothing else, a change to NC8 (section 3).
- **Count only by default** (D4). An application whose rule is `none`, the default under this document's change to NC5, adds to a single line, "3 notifications", with no name or icon. An application the user set to `name` shows its icon and name per notification; one set to `all` adds summary and body. An application with `allowed` false is not counted.
- Nothing on the lock screen can be invoked, replied to or dismissed: actions wait for the unlocked session. The lock shows no media controls (D4).
- When `athanor-shelld` does not answer, the lock shows no notification and logs once; it never blocks locking on it.

**LP8. Unlocking through PAM.**

- **A root helper per connection** (D1). The lock never runs PAM itself. The lock connects to `/run/athanor/unlockd.socket`; systemd starts one `athanor-unlockd@.service` per connection (`Accept=yes`), and it exits after one transaction. This model is chosen because lockout needs a root writer (`pam_faillock` keeps its tally in root-owned `/run/faillock`, section 1), because polkit 127 took the same model for its own helper, because setuid helpers are being retired (polkit 127 removes the need for its own, and Athanor's units already set `RestrictSUIDSGID`), and because it keeps the lock Landlocked: a Landlocked process has no new privileges, and `pam_unix` as the user needs the setuid `unix_chkpwd`.
- **Approval.** The implementation plan of `athanor-unlockd`, `athanor-auth` and the agent's password path (PAM calls, buffer handling and zeroisation, the socket protocol and its parser, the peer check, the sandbox) is approved by the maintainer before any code is written.
- **Its surface is minimal**, and every item is checked by the helper's tests (LP17):
  - **Whom it authenticates:** the account of the peer's uid, read from `SO_PEERCRED` and nothing else. It never takes a user name from the client, never authenticates another account, never opens a session, never sets credentials.
  - **Who may ask:** a peer whose process sits in the lock's own cgroup, `/user.slice/user-<uid>.slice/user@<uid>.service/session.slice/athanor-lock.service`, matched exactly. The helper resolves the peer's process through a pidfd (`SO_PEERPIDFD`), reads its cgroup, and checks after the read that the pidfd still names a live process, so a recycled pid cannot pass. It also refuses a uid with no session of `Type=wayland` and `Active=yes`.
  - **One PAM service,** `athanor-lock` (and `athanor-lock-fingerprint` for LP9's second connection), fixed in the binary: `pam_start`, `pam_authenticate`, `pam_acct_mgmt`, nothing else.
  - **Confinement:** the sandbox of polkit 127's `polkit-agent-helper@.service`, line for line (section 1), plus `ReadWritePaths=/run/faillock` for the tally; `RestrictAddressFamilies=AF_UNIX` and `PrivateNetwork=yes`, so the only sockets it reaches are its client and the system bus (`pam_fprintd`, logind); `MemoryMax=32M`, `RuntimeMaxSec=300`.
- **The wire protocol** is polkit-agent-helper-1's line protocol, so that one client parser in `athanor-auth` serves the lock and the agent: the helper writes `PAM_PROMPT_ECHO_OFF <text>`, `PAM_PROMPT_ECHO_ON <text>`, `PAM_ERROR_MSG <text>`, `PAM_TEXT_INFO <text>`, then `SUCCESS` or `FAILURE`; the client writes one line per prompt. Lines are bounded at 4096 bytes in both directions; a longer line is a protocol error that ends the transaction with `FAILURE`. Both sides hold the response in `Zeroizing` buffers that cannot grow, as the greeter does.
- **Lockout is system-wide** (D3). The image enables authselect's `with-faillock` and sets `deny = 10` and `unlock_time = 300` in `/etc/security/faillock.conf`: ten wrong passwords in a row, anywhere (login, sudo, polkit, the lock), lock the account for five minutes. Every root writer of the tally can write it: greetd and sudo run unsandboxed as root, `athanor-unlockd` has the `ReadWritePaths=` above, and polkit's helper gets the same line in a drop-in (LP11). The feature is enabled in the change that switches the lock (LP18 step 3), not before, because cosmic-greeter's locker runs PAM as the user and cannot write the tally.
- **The PAM service file** `/usr/lib/pam.d/athanor-lock`:

  ```
  auth     requisite  pam_faillock.so preauth
  auth     include    system-auth
  account  include    system-auth
  ```

  The first line, without `silent`, makes PAM itself tell a locked-out user the minutes left and stops before the password is checked; system-auth's own faillock lines count the failure. The file never includes `pam_gnome_keyring` or `pam_oo7`: the keyring stays as unlocked as it was when the lock appeared, and the password is not handed to any daemon. system-auth carries no `nullok` (A2-23), so an empty password never unlocks.

- **Retries** are unbounded at the lock; the rate is PAM's (`pam_faildelay`, then the lockout). The lock never caches a password between attempts.
- **The greeter** keeps greetd as its transport. Its conversation model, bounded buffers and message classification move into `athanor-auth` (D2) in a change of their own, once the lock has run on the crate (LP18 step 4), with the greeter's tests unchanged; until then the lock and the agent use the crate and the greeter keeps its copy.

**LP9. Fingerprint.**

- **Opt-in by enrolment, for the lock and for polkit** (D8). A user with no enrolled finger sees nothing of it. Enrolment belongs to the Settings specification; this document only uses it.
- **At the lock,** for a user with enrolled fingers (fprintd 1.94.5), the lock runs a second transaction on a second helper connection, under the PAM service `athanor-lock-fingerprint`, in parallel with the password field. The first `SUCCESS` unlocks; the other connection is closed, which ends its transaction. The service copies authselect's own fingerprint stack (`/usr/share/authselect/default/local/fingerprint-auth:4-8`), so a locked-out account is not opened by a finger:

  ```
  auth     requisite  pam_faillock.so preauth silent
  auth     [success=done default=bad]  pam_fprintd.so
  auth     required   pam_faillock.so authfail
  auth     required   pam_deny.so
  account  include    system-auth
  ```

- **In polkit's prompts,** the image ships `/etc/pam.d/polkit-1`, which overrides the vendor file (section 1): the vendor's four `include system-auth` lines, preceded in `auth` by `auth requisite pam_faillock.so preauth` and `auth sufficient pam_fprintd.so`. pam_fprintd runs first and the password is asked after it ends, because polkit's helper runs one PAM conversation; the dialog shows its `PAM_TEXT_INFO` until then. The timeout and number of tries pam_fprintd takes before the password field appears are set in that line by the plan, after spike L8.
- **Login stays password-only.** authselect's `with-fingerprint` is never enabled, because it would add `pam_fprintd` to system-auth and so to greetd and sudo (section 1). Fingerprint never replaces the password at the greeter: greetd's session unlocks the keyring with the password (`auth.rs`, comment at line 266).
- The fingerprint state ("Touch the sensor", "No match, try again", "Too many attempts, use your password") is the text of `PAM_TEXT_INFO` and `PAM_ERROR_MSG` from the transaction, shown under the field. At the lock the password field is always available.

**LP10. When the lock crashes.**

- **What holds:** cosmic-comp keeps a lock whose client died; every output stays dark and the session stays locked (section 1).
- **Restart:** `athanor-lock.service` has `Restart=always`, `RestartSec=100ms` and `StartLimitIntervalSec=0`: it is never given up, unlike SH8's five failures in ten minutes (section 3), because a lock that stays down leaves a dark locked screen with no way to unlock. *Amended 2026-10-06 (maintainer decision A2-20, #156):* the lock is a guard of `doc_session.md` SN6, which owns its restart settings: it is never given up, its first restart comes after 100 ms, and the back-off of a crash loop and its reset after a healthy run are SN6's. The agent is a guard too (A2-20, #156).
- **Relocking:** at start the lock reads its session's `LockedHint`. If it is true, a previous instance locked and did not unlock, so it locks at once and the new client takes the defunct lock over. `LockedHint` is kept by logind, not by a file the user can delete.
- **Within 1 s** of a SIGKILL during a lock, the lock surface is back on every output (ST5).
- **When nothing helps:** Super+Alt+Escape ends the compositor and the session, and greetd shows the greeter; unsaved work is lost but nothing of the session is shown. This stays, because it is the only exit from a lock that cannot start (section 1, upstream's comment notwithstanding). greetd's automatic login runs once per boot, so ending the session does not log the user back in (unverified on the reference laptop: section 4, spike L3).
- **A crash of the helper** ends that transaction with `FAILURE` (an unexpected end of stream); the lock shows "Authentication failed, try again" and the session stays locked.
- **A crash of the agent** cancels its pending requests in polkitd, which fails them for the asking program; systemd restarts the agent, which registers again.

**LP11. The polkit authentication agent.**

- **One agent per session.** `athanor-polkit-agent` registers with `RegisterAuthenticationAgentWithOptions` for its session's `unix-session` subject (found as in LP2), with the user's locale from `LANG`, and fallback off. A failed registration is an error: the agent exits non-zero and is restarted, it never runs unregistered.
- **It replaces cosmic-osd's agent in cosmic-osd's retirement** (D7): the agent is enabled by preset in the one change that also enables `athanor-osd` and the end-of-session dialogs of `doc_osd.md` and removes cosmic-osd from the image and from `athanor-session.target` (`doc_osd.md`, OD17 step 5). No patch to cosmic-osd is carried. Until that change cosmic-osd stays the agent, and its failing setuid helper (section 1) stays reported, not patched.
- **The helper** is polkit's own. The agent connects to `/run/polkit/agent-helper.socket`; it never runs `polkit-agent-helper-1` itself. The forge carries polkit 127, rebuilt from Fedora 44's package, until the base image moves to Fedora 44 (D9), with `polkit-agent-helper.socket` enabled and a drop-in `polkit-agent-helper@.service.d/50-athanor-faillock.conf` that adds `ReadWritePaths=/run/faillock` (LP8). It ships in the retirement change above.
- **Confinement:** Landlock before any thread, `PR_SET_DUMPABLE` 0, `RLIMIT_CORE` 0, as the greeter; a unit with `ProtectSystem=strict`, `ProtectHome=read-only`, `PrivateNetwork=yes` (the helper is a Unix socket, D-Bus is a Unix socket), `NoNewPrivileges=yes`, `MemoryMax=96M`.
- **What the dialog shows:** the action's message and icon as polkit gives them; the requesting program, from `polkit.subject-pid` in the details: its executable from `/proc/<pid>/exe`, and when that is a Flatpak's `bwrap`, the application id from `/proc/<pid>/root/.flatpak-info`; the identity to authenticate as, among the identities polkit offers (with Athanor's `10-athanor-wheel-admin.rules`, the wheel members), preselecting the user when present; the fingerprint state while pam_fprintd runs (LP9); a "Details" expander with the action id and the command line for `pkexec`. A request whose subject cannot be read says "Unknown program" rather than guessing.
- **Where:** an overlay layer surface on the focused output with exclusive keyboard focus, a dimmed overlay on the other outputs, opaque, radius 24, 200 ms motion.
- **While locked** no dialog appears; requests wait in order and appear after unlock. polkitd's own request lifetime applies.
- **Requests in a row** queue; one dialog at a time.
- **Power actions** are drawn by the on-screen display's end-of-session dialogs (D12, `doc_osd.md`). When logind's action needs authorisation, polkit asks this agent, so those dialogs never read a password.

**LP12. Other password prompts.**

- **Network secrets** stay with the bar's NetworkManager secret agent (`doc_bar.md`, BR3; F-lock-23).
- **Keyring and Secret Service prompts** (unlocking a keyring, creating one, changing its password) are drawn by our own `org.gnome.keyring.SystemPrompter` in `athanor-polkit-agent` (D11): one trusted-prompt program, in the visual language, and covered by LP13's trusted path. It implements gcr's prompter interface and the secret exchange `sx-aes-1` (section 1), so the keyring daemon, gnome-keyring 48 today and oo7-daemon from Fedora 45, is unchanged (amended 2026-10-06, maintainer decision A2-7 (#151)). Where the exchange's cryptography comes from is decided (ADR-0085, L12): upstream oo7 exposes it. *Deferred on 2026-10-06 (A2-31, #151):* not at release 1.0; the prompter is built at the Fedora 45 milestone, with oo7-daemon as the keyring daemon, and whether oo7-daemon uses gcr's prompter interface and secret exchange is checked then; gcr3's `gcr-prompter` stays until then.
- **The keyring password** is the one password this document lets travel outside PAM, because the keyring daemon's protocol is the only way to unlock a keyring. The prompter reads it into a `Zeroizing` buffer that cannot grow, encrypts it under the key the exchange derives, sends it only to the keyring daemon's connection that opened the prompt, and zeroizes the plaintext, the derived key and its Diffie-Hellman secret when the prompt closes.
- **No cryptography of our own is the goal, and oo7 does not offer it today** (amended 2026-10-06, maintainer decision A2-7 (#151)). The decision asks the prompter to reuse oo7's exchange instead of choosing its own Diffie-Hellman over the 1536-bit IKE group, HKDF-SHA256 and AES-128; oo7's public API offers no such exchange (section 1), so, by ADR-0085 (L12), Athanor proposes upstream that oo7 expose the client side of the exchange and the prompter waits for it. The exchange is security code under the project's rule: no code is written before it exists upstream and the maintainer approves the implementation plan (the chosen source, its version and how it is pinned, how the prompter holds and zeroizes the plaintext, the derived key and the Diffie-Hellman secret, the test vectors taken from gcr's own tests, and interoperability tests against oo7-daemon and gnome-keyring 48). The exchange protects the password from a reader of the session bus, which a confined application cannot be (SD9); a process running as the user can claim the prompter's name, and against it the exchange gives nothing (`doc_threat_model.md`, TM1). No placeholder exchange ships at any step; until the approved prompter ships, gcr3's `gcr-prompter` stays.
- **Which program answers the name** when the agent is not running is spike L9: an activation of gcr3's prompter in its place would put a second prompter on the trusted path.
- **Application permission prompts** belong to the portal specification (F-lock-30).

**LP13. The trusted path.**

- **The problem.** Any program running as the user can draw a full-screen surface that looks like the polkit dialog, the keyring prompt or the lock, and read what is typed into it. polkit refuses a spoofed authorisation, but the password the user typed is then the attacker's, and on Athanor the user is an administrator.
- **What ships before the patch:** nothing that claims more than it does. The agent's dialog and the keyring prompt carry no "genuine" marker a client can imitate; the seal on the lock is the trust state, not a proof that the lock is real (SH12).
- **The trusted path is built on cosmic-comp's security-context indicator,** pop-os/cosmic-comp#1441 (amended 2026-10-06, maintainer decision A2-6 (#151), which replaces D10's own patch with no upstream proposal). #1441 is open and not merged. It draws a border, like the focus indicator, around the floating windows of clients whose security context matches a configured rule (sandbox engine and app id), in a configured colour (the pull request's description and files, read 2026-10-06). Under SD8 every launched application, of every class, connects through a security context and the agent does not, so with a rule on the engine `os.athanor.shell` a floating window that imitates a prompt carries the border and the real prompt does not. Fullscreen and tiled windows carry no border (L13). Athanor helps land #1441 and carries it in `forge/specs/cosmic-comp` until it lands, rebased per release as SH2's patch set is. The key combination the compositor never forwards to clients, which shows whether the focused surface carries the mark, is proposed upstream on top of #1441.
- **The guarantee holds against confined applications only** (`doc_threat_model.md`, TM2 and TM6). Against a confined application the border tells a floating imitation apart; a fullscreen or tiled imitation is the open gap L13. A process running as the user outside confinement is the user (TM1): it can connect to the main socket without a security context, or add a drop-in to the agent's unit, and no compositor mark defends against it.
- **If a decoration around the agent stays,** the compositor identifies the agent by its executable under `/usr` and its unit, or starts it itself, never by a socket handed to it: a socket placed where the user's units can reach it is a credential any unconfined process can take.
- **Until #1441 ships in the image**, the documents that present prompts teach the habit that survives spoofing: a password is asked only after the user started an action that needs it.

**LP14. Language and appearance.**

- The lock, the agent and the helper's messages follow the user's locale; PAM's own messages arrive translated by PAM. The cosmic-osd fixed `en_US` (section 1) does not carry over.
- Right-to-left mirrors the layout; the clock's digits stay left to right.
- The four variants of the visual language (light, dark, and their high-contrast forms) apply; the lock and the dialog never take the user's accent colour, so that a trusted surface does not change with a preference an application can read.

**LP15. Confinement and budgets of the lock.**

- `athanor-lock` confines itself as the greeter does (one thread, Landlock writes limited to `$XDG_RUNTIME_DIR` and the GPU nodes, then non-dumpable), before GTK starts. Its unit adds `ProtectSystem=strict`, `ProtectHome=read-only`, `PrivateNetwork=yes`, `NoNewPrivileges=yes`.
- **Renderer:** GTK's GL renderer, pinned as the greeter pins it (`main.rs:19`), because the lock must draw on the NVK and llvmpipe paths where the greeter was seen to draw black under Vulkan.
- **Memory:** at most 80 MB PSS resident with no surface and 120 MB locked on two outputs; the agent at most 64 MB. These are estimates; the first measurement confirms or corrects them (section 4).
- **Times** (ST5 on the reference laptop, 95th percentile): `locked` within 300 ms of logind's `Lock`; the answer to a key in the field within 50 ms; unlock within 300 ms of PAM's `SUCCESS`; the agent's first complete frame within 100 ms of `BeginAuthentication`.

## 4. Open doubts

Each spike is a short probe on the image as shipped, run before the step that needs it.

1. **L1. Screen capture while locked:** whether `ext-image-copy-capture` of a toplevel or cosmic's screencopy of a workspace returns window content while the session is locked. If it does, it is a defect fixed by a forge patch in `forge/specs/cosmic-comp`, as LP13's. Before step 3.
2. **L2. The input-method grab** (cosmic-comp#2702): whether it reproduces on cosmic-comp 1.8.0 with ibus as `doc_languages.md` configures it (its spike S2 is the same probe). If it does, LN12's patch lands before step 3.
3. **L3. Automatic login after Super+Alt+Escape** on the reference laptop: greetd's `initial_session` is documented to run once; confirm it does not log the user back in.
4. **L4. `wp_presentation` feedback** for lock surfaces on cosmic-comp 1.8.0, used by LP4 to release the inhibitor; if absent, the first frame callback after commit.
5. **L5. The lock's memory and times** on the reference laptop (LP15).
6. **L6. NVIDIA resume** (cosmic-comp#2096, #2522): blank lock surfaces after resume on the `-nvidia` image.
7. **L7a. The idle behaviour before SD22 step 1:** what cosmic-idle 1.8.0 does on a fresh account with no `com.system76.CosmicIdle` user keys. Per the correction of 2026-10-05 it is expected to use its compiled 15/15/30 minutes. Before step 3. **L7b. The idle defaults:** that `athanor-idle` reads the values of LP5 from the defaults of `org.athanor.desktop.idle` (SD3), and that a user's setting still overrides them. Before SD22 step 1, run with `doc_session_daemons.md`.
8. **L8. pam_fprintd's behaviour:** that it returns at once for a user with no enrolled finger and on a machine with no reader, so the opt-in costs nothing to others, and the timeout and tries that suit the polkit dialog (LP9). The reference laptop is believed to have no reader (unverified); the spike runs on a machine with one or with fprintd's virtual device. Before step 7.
9. **L9. The prompter's name:** whether gcr3's D-Bus activation file for `org.gnome.keyring.SystemPrompter` can start `gcr-prompter` when our agent is not running, and how the image makes the name activate our agent instead without removing gcr3, which gnome-keyring needs. Before step 6.
10. **L10. faillock under every writer:** that `pam_faillock` counts and locks out at login, sudo, polkit's helper with its drop-in and `athanor-unlockd`, and how cosmic-greeter's locker behaves if the feature is ever enabled under it (the reason step 3 enables it only with the switch).
11. **`nullok`.** Decided by A2-23: the image enables authselect `without-nullok`, so no account authenticates with an empty password at the lock, polkit or login; `verify.py pam` and a build-time assertion keep it so.

12. **L11. The prompter before Fedora 45** (added 2026-10-06). The base image ships gnome-keyring 48 and oo7-daemon replaces it with Fedora 45. Whether the prompter ships on the current base against gnome-keyring (both daemons speak the same `sx-aes-1`, which LP17 tests) or waits for the Fedora 45 base; and whether it later prefers oo7's `org.kde.secretprompter`, which needs no exchange at all, if oo7 commits to it as a stable interface (inferred by the audit, not verified). For the maintainer.
13. **L12. Where the exchange's cryptography comes from** (added 2026-10-06). Maintainer decision A2-7 (#151) asks for no cryptography of our own by reusing oo7's exchange, and oo7's public API does not offer it today (section 1): the exchange is private to oo7-daemon and is the receiving side, and the `oo7` crate exposes only AES behind its `unstable` feature, with Diffie-Hellman and key derivation kept `pub(crate)`. The options: (a) propose upstream that oo7 expose the client side of the secret exchange; (b) depend on `oo7` with the `unstable` feature, pinned, which today gives AES only, so Diffie-Hellman and HKDF would still need a source; (c) another audited library; (d) copy oo7-daemon's code into the prompter, which is our own cryptography and goes against A2-7. **Decided 2026-10-07 by the maintainer: (a), recorded as ADR-0085.** Athanor proposes upstream that oo7 expose the client side of the secret exchange; the prompter's implementation plan (LP12) waits for it, and no cryptography of our own is written in the meantime.
14. **L13. Surfaces #1441 does not mark** (added 2026-10-06). The border is drawn around floating windows only, so a confined application's fullscreen or tiled window that imitates the dialog carries no mark and LP13 does not tell it apart. Whether to extend the indicator to every window state, proposed upstream with #1441, or to state the gap as residual risk, is for the maintainer.

## 5. Acceptance

The tests of LP17 run in CI on every change; the surface cases and the VM tests run in the acceptance VM. The rest is judged by the maintainer on the reference laptop, athanor-ref, at each step's gate.

1. `loginctl lock-session`, Super+Escape and the bar's lock item lock every output within 300 ms at the 95th percentile, and logind reports `LockedHint=yes`.
2. A wrong password is refused with PAM's delay, the right one unlocks, and logind reports `LockedHint=no`; `journalctl` and `coredumpctl` hold no trace of either.
3. `systemctl suspend` with the session unlocked: after resume the first frame on every output is the lock, in 20 runs out of 20, and the inhibitor was released before the 5 s bound each time (journal).
4. SIGKILL of `athanor-lock` while locked leaves every output dark and locked, and the lock is back within 1 s, ten times in a row.
5. A process of another uid, a process of the user outside `athanor-lock.service`'s cgroup, and a process of the user with no active session are refused by `athanor-unlockd`; a client that sends a user name authenticates only its own account.
6. Ten wrong passwords at the lock lock the account: the lock shows PAM's message with the minutes left, `sudo` and a polkit prompt refuse the right password in that window, and the account opens again after 5 minutes.
7. `loginctl unlock-session` from an SSH session of the user opens the lock, logind reports `LockedHint=no`, and the journal holds the lock's line.
8. `pkexec true` shows the agent's dialog naming `pkexec` and the command, and succeeds with the right password: the first working polkit prompt of the image. `busctl` shows one registered agent, and cosmic-osd is absent from the image.
9. A Flatpak that triggers a polkit action is named by its application id; with the session locked, a polkit request does not appear until unlock.
10. With an enrolled finger, the lock and a polkit prompt accept the finger; the greeter and `sudo` ask only for the password; a user with no enrolled finger sees no fingerprint text anywhere.
11. **cosmic-comp#2702.** With an input method enabled and holding its keyboard grab (the test client of LP17 in CI, and ibus as `doc_languages.md` configures it on the reference laptop), the session locks; every key typed at the lock reaches the lock's field and the input method receives none, its log showing no key from the lock until after unlock.
12. Deferred to the Fedora 45 milestone (A2-31, #151). A keyring locked by the user is unlocked through our prompter: oo7-daemon, and gnome-keyring 48 while the base image ships it, accepts the password received through the secret exchange, and no other process on the session bus can read it (a monitor on the bus sees only the exchange's encrypted fields).
13. Notifications on the lock screen: an application left at the default adds only to the count; one set to `name` shows its name; one set to `all` shows summary and body; no media controls appear.
14. The 132 surface cases pass, in the four visual variants and in right-to-left, and each program passes the gate of `doc_shell_standard.md` (ST2) before it is enabled by preset.

## 6. Decisions taken

The maintainer decided on 2026-10-05; D1 was delegated by the maintainer, with the instruction to reason for the long term and choose.

- **D1. Where PAM runs for the lock:** a root service per connection, `athanor-unlockd@.service`, with the minimal surface of LP8. Lockout needs a root writer, polkit 127 took the same model, setuid helpers are being retired, and the lock stays Landlocked. The implementation plan of `athanor-unlockd`, `athanor-auth` and the agent's password path (PAM calls, buffer handling and zeroisation, the socket protocol and its parser, the peer check, the sandbox) is approved by the maintainer before any code is written.
- **D2. The greeter's conversation code:** moves into `athanor-auth`, in its own change after the lock is proven (LP18 step 4). One implementation to review, moved only once it has run in the lock.
- **D3. PAM service and lockout:** `with-faillock` system-wide, `deny = 10`, `unlock_time = 300` (LP8). Guessing is bounded everywhere a program running as the user would aim, with Fedora's own mechanism.
- **D4. Notifications on the lock screen:** count only by default, which amends NC5's default; no media controls (LP7). A count says something arrived without saying from whom.
- **D5. logind's `Unlock` signal:** honoured (LP4). Ignoring it adds no protection under the threat model of section 1.
- **D6. Factory idle values:** GNOME's, blank and lock at 5 minutes, suspend at 15 minutes on battery, never on mains (LP5). A shorter blank is the lock's first protection, and suspend on mains interrupts downloads and remote sessions.
- **D7. How cosmic-osd stops being the polkit agent:** its agent leaves with it, when `athanor-osd` replaces it, jointly with OSD decision M4 (LP11). No patch to carry and no step where two agents compete.
- **D8. Fingerprint:** opt-in by enrolment, at the lock and in polkit's prompts; login stays password-only (LP9). The maintainer chose against the draft's recommendation to keep polkit password-only.
- **D9. The polkit helper on Fedora 43:** polkit 127 carried in the forge until Fedora 44 (LP11). It is upstream's own answer, and it keeps the agent confined.
- **D10. The trusted path:** our own cosmic-comp patch only, with no upstream proposal, which amends SH2 (LP13). The maintainer chose against the draft's recommendation to propose it upstream first. **Amended 2026-10-06, maintainer decision A2-6 (#151):** built on cosmic-comp#1441, carried until it lands; the guarantee is stated against confined applications only; the agent, if decorated, is identified by its `/usr` executable and its unit; the reveal key is proposed upstream. This reverses "no upstream proposal" and the SH2 exception.
- **D11. Who draws the keyring prompts:** our own `SystemPrompter` ("now" when taken on 2026-10-05; deferred to the Fedora 45 milestone by A2-31, below), with gcr's secret exchange; its implementation plan needs the maintainer's approval before any code (LP12). The maintainer chose one trusted-prompt program over keeping gcr3's prompter until the trusted path. **Amended 2026-10-06, maintainer decision A2-7 (#151):** the prompter reuses the `oo7` crate's secret exchange and is tested against oo7-daemon; no cryptography of its own. oo7's public API does not offer that exchange today (section 1); how to meet the decision is decided by ADR-0085 (L12): upstream oo7 exposes the client side. *Amended on 2026-10-06 (A2-31, #151):* the keyring prompter waits for the Fedora 45 base with oo7-daemon (A2-7); no own prompter is built before then.
- **D12. End-of-session dialogs and power actions:** owned by the on-screen display specification; this document supplies only the authorisation through its agent (LP11). They are cosmic-osd's today and leave with it.
