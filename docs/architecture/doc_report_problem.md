# Athanor report a problem

Status: **revision 1, approved by the maintainer on 2026-10-08.** It takes `doc_settings.md` SE27 (revision 1, 2026-10-05, with decisions A2-19 and A2-33, #161) out of the Settings specification without change of substance, as the maintainer decided in the review of 2026-10-08 (`doc_settings.md` decision 12): the command ships in `athanor-kernel-profile` (ADR-0070), not in Settings, and Settings keeps only the About row that starts it.

## 1. Context

- **Why.** Athanor collects no telemetry, yet the gradual rollout of `doc_kernel_profile.md` D34 must learn when an update broke a machine. A2-19 (#161) asked for a report the user reads, edits and submits; A2-33 (#161) settled its packaging, label and retention, recorded in ADR-0070.
- **Where it lives.** One command, `athanor-report-problem`, beside `athanor-profile-check` in `forge/specs/athanor-kernel-profile`. Settings (`doc_settings.md` SE22, SE27) and the crash notice of `doc_session.md` SN8 only start it.

## 2. Decisions

**RP1. Report a problem** (A2-19, #161; with `doc_kernel_profile.md` D34). Athanor learns that an update broke a machine without collecting telemetry: the machine prepares a report, the user reads it, edits it and submits it. Nothing is sent by Athanor.

- **Two entry points, one program.**
  - The command `athanor-report-problem`, installed by the package that ships `athanor-profile-check` (`forge/specs/athanor-kernel-profile`), beside `athanor-profile-check`, as decided in A2-33 (#161).
  - A row "Report a problem" on the About page (`doc_settings.md` SE22), and the "Report a problem" button of the crash notice of `doc_session.md` SN8. Settings does not build the report itself: it starts the command's installed units by name (`doc_settings.md` SE6) and shows what the command wrote; the notice's button opens Settings at that row with the crash report it names, so Settings is the one caller. The exchange goes through `$XDG_RUNTIME_DIR/athanor-settings/report/`, already on SE6's write list: `athanor-report-problem@prepare.service` reads there the crash report's file name (a bare name in the crash-report directory, nothing else accepted) and writes the draft there; Settings shows it and writes the user's edited text back to the same file; `athanor-report-problem@open.service` encodes that file and makes the OpenURI call. Saving the draft and copying it are Settings' own actions (the portal file chooser, the clipboard), so SE6's write and read lists gain nothing.
  - The command's two units, installed by `athanor-kernel-profile` with the command, carry the enforcement in their unit files, so no caller can start the command without it. They have no network (`PrivateNetwork=yes`, `RestrictAddressFamilies=AF_UNIX`, `IPAddressDeny=any`), access to the session bus socket (which OpenURI needs), read access to `/proc`, `/sys`, `/usr/lib/os-release` and the crash-report directory, and write access to `$XDG_STATE_HOME/athanor/reports` and `$XDG_RUNTIME_DIR/athanor-settings/report` only.
- **What goes in.** Exactly these fields, in this order, and nothing else; a field that cannot be read is written as `unavailable`, never guessed.
  1. From `/usr/lib/os-release`: `NAME`, `VERSION_ID` and the image build identifier (`BUILD_ID` or `IMAGE_VERSION`, whichever the image sets; the exact key is checked at the first step).
  2. The kernel release (`uname -r`) and the active role names (as `athanor-profile-check` reads them from `athanor.role=`).
  3. The output of `athanor-profile-check` run without `--quiet`: its exit status, each `DRIFT <kind>.<name>: expected <repr>, found <repr>` line, and the closing `athanor-profile-check: <combination>: <held>/<total> settings hold` line (`athanor-profile-check:171-172`). When it exits 2 (profile unreadable) its stderr line goes in instead. Whatever the checker reports later (the mode and reasons of `doc_kernel_profile.md`) joins this output unchanged; the report adds no field of its own for them.
  4. Optional: the crash report the user picked (below), whole.
  5. A free-text description, empty at first, that only the user writes.
  - Not collected: the journal beyond the crash report's own 50 lines, hardware inventories, the list of installed packages, network configuration, accounts, any file of the user. The report is a function of the sources above; another source needs an amendment to this entry.
- **Redaction.** An allow-list first, then a scrub of what is free text.
  - **Allow-list.** The report contains only the named fields of the list above, each with a known shape: os-release values, the kernel release, role names, the checker's exit status and its closing line, and the `DRIFT` key (`<kind>.<name>`, which the profile's manifest fixes). Nothing else is collected, and a field that does not match its shape is written as `unavailable`.
  - **Free text** is what has no fixed shape: the `found` and `expected` values of a `DRIFT` line (a command line, a path), the crash report's journal lines, and the user's description. It passes through the scrub below, on exact values read from the machine plus patterns. The description is the user's own words and is scrubbed too, so a value typed by habit is caught.
  - The scrub replaces: the user name, the home path (resolved and unresolved) and the uid, including `user@<uid>.service` and `/run/user/<uid>`, by `<user>`, `~/...` and `<uid>`; the host name (static, pretty and transient) by `<host>`; the machine-id and the boot-id by `<machine-id>` and `<boot-id>`; filesystem, partition and LUKS UUIDs by `<uuid>`; IPv4 and IPv6 addresses by `<ip>`; MAC addresses (six colon- or hyphen-separated byte pairs) by `<mac>`; Wi-Fi SSIDs (the names NetworkManager knows) by `<ssid>`; and serial numbers (the DMI serials `/sys/class/dmi/id/*serial*`, `product_uuid`, `board_asset_tag` by value, and any `key=value` or `key: value` whose key contains `serial`) by `<serial>`. UUIDs are scrubbed in every form, DMI and filesystem alike: this is decided here, not left to the maintainer.
  - The scrub is best effort and says so on screen: it lists how many values it replaced per class. The user sees the redacted text, never the original, before anything leaves, and is the last reviewer: a value no pattern can know (a name inside a journal message) is the reason the draft is read first.
- **What the user does.** The draft is shown whole, in a text view in Settings or as a file for the command (`--edit` opens `$VISUAL` or `$EDITOR`). The user can edit any line and delete any block, including the crash report; the draft after the user's edits is exactly what is encoded. There are three actions, each taken by the user: open the issue in the browser, save the draft as a file, or copy it to the clipboard. The draft is also written, mode 0600, to `$XDG_STATE_HOME/athanor/reports/<UTC time>.txt` before anything is offered, and the 20 most recent are kept (A2-33, #161).
- **Size.** GitHub's documentation for creating an issue from a URL states that a URL "that exceeds the server limit" returns `414 URI Too Long` and gives no number (`docs.github.com/en/issues/tracking-your-work-with-issues/using-issues/creating-an-issue`, section on URL queries, read 2026-10-06). **The limit is therefore unverified.** The design does not depend on its value:
  - the percent-encoded URL has a budget of 6000 bytes, a conservative figure of ours (unverified), to be measured at step 1 against the live server and then fixed in the program as a constant;
  - when the encoded draft exceeds it, the body keeps the fields of items 1 to 3 and ends with the line "The full report is too long for this form: attach the saved report", naming the saved file by its name (not its path, which is under the home); the user is shown the shorter text that goes to the browser;
  - the saved file is always available to attach by dragging it into the issue, and the command offers to copy the full draft to the clipboard. The fallback needs no URL at all.
- **Mechanism.** The command opens `https://github.com/<repo>/issues/new?title=<>&body=<>&labels=problem-report` (A2-33, #161: the label `problem-report` exists in the repository; `title`, `body`, `labels` and `template` are the parameters GitHub documents for this URL; a label is applied only if the submitter may add labels) through `org.freedesktop.portal.OpenURI.OpenURI` on the session bus, which hands it to the user's browser.
  - `<repo>` is never written in RP1's code. Today the value is literal: `BUG_REPORT_URL="https://github.com/ars-regia/athanor/issues"` in `forge/specs/athanor-base-config/SOURCES/usr/lib/os-release:16`, so a fork's image would point to the upstream repository. Step 1 of RP2 makes the build write `BUG_REPORT_URL` from the repository variable of the pipeline (`<server>/<owner>/<repo>/issues`, with a default for the project), and RP1 only reads os-release. The command appends `/new` and accepts the value only if it is an `https` URL on `github.com` with two path segments followed by `issues`; otherwise it saves the draft and tells the user why it did not open a browser.
  - The title is `Problem report: <combination>, <held>/<total> settings hold` or, with no profile result, `Problem report: <NAME> <VERSION_ID>`; the user may edit it in the browser.
  - The URI is opened only after the user's action above; the command has no option that opens it on its own.
- **Templates.** The repository has no `.github/ISSUE_TEMPLATE` (checked at `da940ab8`: `.github` holds `PULL_REQUEST_TEMPLATE.md` and no issue template), so `body` is used as is. No issue form is planned (A2-33, #161), so `body` is the whole report; whether a form would ignore `body` stays a verification (RP-S2).
- **No network without the user's action.** The command and Settings make no request of their own: the only exit is the OpenURI call after the user's action, and the browser's request to github.com is the user's. Two things hold it, and they are different: the unit's `PrivateNetwork=yes`, `RestrictAddressFamilies=AF_UNIX` and `IPAddressDeny=any` **enforce** (an attempt fails), and the acceptance test **observes** (an attempt is seen). The journal records no connections, so the test does not rely on it: it runs the command under `strace -f -e trace=%network` and fails on any `socket(AF_INET` or `socket(AF_INET6`, and on any `connect` to an address that is not local (a `socket` call that the unit's restriction makes return `EAFNOSUPPORT` still appears in the trace, so an attempt fails the test even when it was blocked). Acceptance items 1 and 3 carry it.
- **Crash reports.** The report of item 4 is the file `doc_session.md` SN8 specifies: `$XDG_STATE_HOME/athanor/crash-reports/<UTC time>-<unit>.txt`, mode 0600, written by `athanor-sessiond` (unit, image version, time, `Result`, exit code or signal, `NRestarts` and the last 50 journal lines of the failed invocation; the 20 most recent kept). SN8's report is approved (`doc_session.md` revision 2, 2026-10-08) and not yet built: the crash report is optional input here, and this entry follows SN8's path and content if they change. The command takes the report the notice named (`--crash-report <file>`, passed by the notice's button), else lists the available ones and lets the user choose, else goes on without. Its journal lines pass through the redaction above and the user sees them.
- **Dependencies.** `doc_session.md` SN8 (#156) for item 4; without it the command works with items 1 to 3 and 5.
- **Needs:** `doc_settings.md` SE22 (About), SN8, `doc_kernel_profile.md` D34 and `athanor-profile-check`.

**RP2. Construction.** Each step merges on its own.

1. The command `athanor-report-problem` in `athanor-kernel-profile`, with RP-S1 measured and its constant fixed, and the build change that writes `BUG_REPORT_URL` into `/usr/lib/os-release` from the repository variable instead of the literal of `forge/specs/athanor-base-config`.
2. The entry points: the About row of `doc_settings.md` SE22 (Settings' step 4, `doc_settings.md` SE26) and the button of the crash notice of `doc_session.md` SN8, each with the step that builds its surface.

## 3. Changes to other documents

- `doc_settings.md` SE27, its step 4 in SE26, open doubts SE-S9 to SE-S11 and acceptance items 20 to 23 moved here on 2026-10-08, renumbered RP1, RP2, RP-S1, RP-S2, decision D1 and items 1 to 4.

## 4. Open doubts

1. **RP-S1. The URL budget.** GitHub documents a `414 URI Too Long` for an over-long new-issue URL and no number (RP1). Measure the live limit at step 1 of RP2 and fix the constant; until then 6000 encoded bytes is our unverified estimate.
2. **RP-S2. Issue forms and `body`.** Whether an issue form ignores `body`, verified so that a form added later cannot silently drop the report. No form is planned (A2-33, #161).

## 5. Acceptance

1. **CI** `athanor-report-problem --no-open` run under `strace -f -e trace=%network`, in the installed unit `athanor-report-problem@prepare.service` itself (a test drop-in changes only `ExecStart=`, to wrap the same command line in `strace`, so the test checks the unit file the package ships), exits 0 and writes a draft containing the fields of RP1 in order; with `athanor-profile-check` faked to exit 1, the `DRIFT` lines are in it. The test fails if the trace holds a `socket(AF_INET` or `socket(AF_INET6` (whatever its result) or a `connect` to a non-local address; a control run of the same harness with a program that opens a TCP socket fails it, which shows the test can see an attempt.
2. **CI** A fixture machine with a known user name, host name, home path, DMI serial and MAC address yields a draft containing none of them, and the redaction counts are shown. A fixture over-budget draft yields a URL of at most the constant of RP-S1 whose body ends with the "attach the saved report" line, and a saved file with the whole draft.
3. **CI** With a stub of `org.freedesktop.portal.OpenURI` on the session bus, the command calls it zero times until the confirming action and exactly once after it, with a URI that starts with the image's `BUG_REPORT_URL` plus `/new?`; with `BUG_REPORT_URL` set to a non-GitHub host it calls it zero times and says why.
4. **ref** On the acceptance VM `athanor-report-problem` produces a draft the user opens in the browser: the new-issue page opens on github.com prefilled with the shown text. The strace of item 1 shows no network call by the command, and the same holds for Settings' own process while the About row is used; the request to github.com is the browser's, after the user's action.

## 6. Decisions taken

- **D1. Packaging and form** (A2-33, #161; ADR-0070). (a) `athanor-report-problem` ships in `athanor-kernel-profile`, beside `athanor-profile-check`. (b) The issue URL carries `labels=problem-report`; the label now exists in the repository. (c) No issue form. (d) The 20 most recent drafts of `$XDG_STATE_HOME/athanor/reports` are kept.
- **D2. A specification of its own** (2026-10-08, `doc_settings.md` decision 12): the report leaves the Settings specification, unchanged in substance.
