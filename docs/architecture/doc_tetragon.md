# Athanor runtime events (Tetragon)

Status: **revision 1, amended 2026-10-06 with maintainer decision A2-32 (#153).** It is the specification that maintainer decision A2-10b (#153) asks for: Tetragon does real work and is not deleted. It designs the tracing policies the image ships, how the service is enabled and confined, how an event reaches the user as a notice and as a row of the shield's sheet, the limits on volume and on what is kept, the acceptance gate and the order of construction. Decision A2-32 (#153) answers the nine questions of revision 1's section 6, recorded in section 8, and adds the observe-only coverage of TG12 to TG16. A rule still marked _(Proposal)_ is one that A2-32 did not decide and awaits the maintainer.

## 2. Decisions

**TG1. What Tetragon is for in Athanor.** A local detector of four behaviours that the confinement of tier 2 and the image's protections of tier 3 are meant to make impossible or rare. It tells the user, on this machine only, when one happens. Decision A2-32 (#153) adds five areas of observe-only coverage from upstream's policy library (TG12 to TG16), which record what happened on the machine rather than detect a breach. It is not an enforcement layer at 1.0, not a substitute for TM3's `ReadOnlyPaths=` or for Flatpak's sandbox, and not a source of telemetry.

- Every shipped policy observes and never kills (`Post` only, no `Sigkill`, no `Override`). Enforcement is decided by A2-32 (#153), Q1: none at 1.0. After revision 2's noise measurement, TG4 gains a deny of exec from temporary directories for tier 2 only, through `lsmhooks` and the BPF LSM (the kprobe `Override` action needs `CONFIG_FUNCTION_ERROR_INJECTION`, which Azoth leaves off); revision 2 specifies it.
- Events never leave the machine (TG9). Nothing in this document moves the shield's badge (TG8).

**TG2. Where the policies and the daemon's settings live.**

- The policies are files of the package, under `/usr/lib/tetragon/tetragon.tp.d/`, one per behaviour, except persistence, which takes two files to respect upstream's selector limits (TG3): `athanor-persistence-create.yaml`, `athanor-persistence-write.yaml`, `athanor-exec-temporary.yaml`, `athanor-credentials.yaml`, `athanor-modules.yaml`, and the five files of TG12 to TG16: `athanor-network-temporary.yaml`, `athanor-sensitive-files.yaml`, `athanor-ptrace.yaml`, `athanor-bpf-load.yaml`, `athanor-mounts.yaml`. Each `metadata.name` begins with `athanor-`, which is how the export filter (TG7) and the relay (TG7) recognise them. Being under `/usr`, they are part of the verified image and change only with it.
- The daemon's settings are drop-ins of the package, one file per option, under `/usr/lib/tetragon/tetragon.conf.d/`, among them `tracing-policy-dir` set to `/usr/lib/tetragon/tetragon.tp.d`. `/etc/tetragon/` stays the administrator's, as upstream reserves it: a file there overrides ours, and an administrator who wants their own policies sets `tracing-policy-dir` in `/etc/tetragon/tetragon.conf.d/`. The package ships nothing under `/etc/tetragon/`: neither `tetragon.yaml` nor the empty `tetragon.tp.d` (A2-32 (#153), Q6).
- **The BPF objects follow the image.** The drop-ins set `bpf-lib` to `/usr/lib/tetragon/bpf/`, the directory that holds the objects, because the daemon joins it directly with each object's file name ([generickprobe.go](https://github.com/cilium/tetragon/blob/v1.7.1/pkg/sensors/tracing/generickprobe.go), `path.Join(option.Config.HubbleLib, loadProgName)`); the package installs the objects at `/usr/lib/tetragon/bpf` (the spec's `%{_sharedstatedir}/tetragon/bpf` becomes `%{_prefix}/lib/tetragon/bpf`). On ostree and bootc `/usr` is replaced with the image and `/var` is not, so objects left in `/var/lib` can outlive the binary they were built for, and after an update the daemon would load stale objects or refuse to start. The package ships a `tmpfiles.d` line `R! /var/lib/tetragon/bpf` to remove the copies that earlier packages left. State that must persist lives in two places only: `/var/log/tetragon` (the export file and its rotated backups, TG7) and `/var/lib/tetragon` (`StateDirectory=`, TG10). The pinned maps under `/sys/fs/bpf/tetragon` are rebuilt at every start and persist nothing. That the daemon writes nothing under `bpf-lib`, which is read-only under `ProtectSystem=strict`, is part of S1.
- The unit passes no option on its command line (`ExecStart=/usr/bin/tetragon`), so the drop-ins are the one place the settings are read from. The current `--config-dir=/etc/tetragon/tetragon.tp.d` and `--export-filename=` leave.

**TG3. Policy: writes to the persistence paths by a process outside the host's mount namespace.**

- **Reason.** TM2 promises that tier 2 cannot write the persistence paths of TM3; TM4 states where that promise leaks (a Flatpak with home access). This policy reports the leak when it is used, and reports a regression of SD8's `ReadOnlyPaths=` if one ships.
- **Tier.** TM2, and the leaks of TM4.
- **Hooks and the selector limits.** Upstream documents a bound of 5 selectors per hook and 4 values per `matchArgs` (8 for a `file` argument), and its code refuses a postfix of 128 characters or more (section 1), so one policy cannot carry an open-ended list. TG3 is two policies, each sized to the limits _(Proposal)_.
  - `athanor-persistence-create.yaml`: creation of an entry in a persistence directory, seen on the parent directory through the path-based LSM hooks, which exist because `CONFIG_SECURITY_PATH=y`: `security_path_mknod` (reached from `open` with `O_CREAT` on a new file), `security_path_mkdir`, `security_path_symlink`, `security_path_link` and `security_path_rename` (the new directory). Their `path` argument is the parent directory, matched with `Postfix` against the directory part of each TM3 row (`/.config/systemd/user`, `/.config/autostart`, `/.config/environment.d`, `/.local/share/applications`, and so on). A selector carries 4 directories and a hook 5 selectors: 20 directories per hook. The four directories named today fit in one selector.
  - `athanor-persistence-write.yaml`: a write to an existing start-up file, seen by `security_file_permission` with the write mask, its `file` argument matched with `Postfix` against `/.bashrc`, `/.bash_profile`, `/.bash_login` and `/.profile`: one selector, with room for four more.
  - **The list is bounded and a test enforces it.** A row added to TM3 adds a value here in the same change while there is room; the 21st directory or the 9th start-up file needs a further policy file. Step 2 adds a unit test that parses each shipped policy and fails when a hook has more than 5 selectors, a `matchArgs` more than 4 values (8 for `file`) or a postfix is longer than 127 characters, so a row that does not fit fails in CI and not at load time on a machine. The list follows TM3's table at the time of step 2, including the rows TM3 still marks as proposals.
  - `security_file_permission` fires on every read and write of the machine. The kernel-side prefilter below (`Mnt` `NotIn` `host_ns`) keeps most of them out of the export; the cost of the hook itself is spike S2.
- **Prefilter in the kernel.** `matchNamespaces` with `Mnt` `NotIn` `host_ns`. A process of the broker's `confined` class and every Flatpak application runs in its own mount namespace; the user's shell, an `unconfined` application and the user manager do not. Without this filter every save of a desktop entry by the user would be an event.
- **Classification in the relay** (TG7). A process whose cgroup is `app-flatpak-*.scope` or `app-athanor-*@*.service` (SD8) is tier 2 and raises a notice. A process in a container (toolbox, rootless podman) is tier 1 by TM5 and is recorded only. One of our own hardened units is recorded only. A process that has exited before the relay reads its cgroup raises a notice: the cautious default. How the relay tells a toolbox from a Flatpak when `/proc/<pid>` is gone is spike S3.
- **Gaps, stated.** A write to an existing file in a persistence directory (for example an autostart entry rewritten in place) is seen only if the file itself is named in `athanor-persistence-write`: `Postfix` matches the end of a path, so a directory cannot be matched for the files inside it. A tier 2 process that persuades a tier 1 process to write for it is not seen.
- **Expected noise.** Low. The skeleton files are written once, at account creation, by a host-namespace process. Our own units with a private mount namespace do not write these paths (SD17: `ProtectHome=read-only`).

**TG4. Policy: a program executed from a temporary directory.**

- **Reason.** Dropping a binary in `/tmp` or `/dev/shm` and running it is the common second stage of an exploit chain and of downloaded malware. On Athanor both directories are writable by every user and mounted without `noexec`.
- **Tier.** TM2 (a confined application that escapes far enough to exec on the host), and TM1 as information to the user.
- **Hook.** `security_bprm_check` with its `linux_binprm` argument (upstream example [security_bprm_check.yaml](https://github.com/cilium/tetragon/blob/v1.7.1/examples/tracingpolicy/security_bprm_check.yaml)). First selector: `Prefix` `/tmp/`, `/dev/shm/`, `/var/tmp/` and `/run/user/` (four values, the documented limit of a `matchArgs` operator, which this document keeps although the code does not count string values (section 1); the last two added by A2-32 (#153), Q3), with `matchNamespaces` `Mnt` `In` `host_ns`, action `Post` with `rateLimit: "1m"` and `rateLimitScope: "process"` (TG8). A second selector with the same filter and action is held for executing a `memfd` (spike S4); the hook has room for five.
- **What it misses, stated.** An interpreter given a file as an argument (`bash /tmp/x`, `python3 /tmp/x.py`) executes the interpreter, not the file; a script run directly through its `#!` line is seen.
- **Expected noise, and what is filtered or shown.** Medium for developers, near zero otherwise. Three places decide, in this order. The notice rule (shown, aggregated, off in developer mode) is decided by A2-32 (#153), Q2; the list of recorded patterns remains _(Proposal)_.
  - **Filtered in the kernel: anything that is not the host's `/tmp`.** The selector's `Mnt` `In` `host_ns` leaves out every process in its own mount namespace: Flatpak applications (a Flatpak's `/tmp` is private and is not the host's), bwrap, rootless podman and toolbox (tier 1 by TM5, and a container), and our own units with `PrivateTmp=`. What they execute from their own `/tmp` cannot be reached from the host and is not seen at all. A confined application that escapes far enough to execute from the host's `/tmp` is in the host mount namespace and is seen.
  - **Recorded, never a notice: known developer and packaging patterns, classified in the relay.** Binaries under `/tmp/.mount_*/` (an AppImage's mount: the user ran an AppImage) and under `/tmp/go-build*/` (`go run` and `go test`). Electron applications and Steam are not known to execute from these prefixes on the host; none is classified until spike S8 finds one, and it then joins this list by a change to the relay and not by a new policy. rpm and dnf use `/var/tmp/rpm-tmp.*` as an argument of `sh`, which is the interpreter case below and not an exec of the file (S8 confirms on `rpm-ostree` and `nix-daemon`).
  - **Shown: every other exec from the four prefixes.** A binary dropped straight in `/tmp`, `/dev/shm`, `/var/tmp` or `/run/user/<uid>/`, or a script run through its `#!` line. The relay suppresses the notice for this category while developer mode is on (`doc_software.md` SW2), records the events all the same, and aggregates them (TG8). The acceptance gate runs with developer mode off.

**TG5. Policy: credential changes towards root.**

- **Reason.** A local privilege escalation ends with a process holding uid 0 or new capabilities it did not have at exec.
- **Tier.** TM7. Tetragon does not defend tier 3, which belongs to `doc_kernel_profile.md`; it gives the user a record of an escalation that the other layers did not stop.
- **Hooks** _(Proposal)._ Three parts. Each carries kernel-side filters that keep root and namespaced callers out of the export.
  - The `setuid` family to root, from upstream's [privileges-raise.yaml](https://github.com/cilium/tetragon/blob/v1.7.1/examples/policylibrary/privileges/privileges-raise.yaml): `__sys_setuid`, `__sys_setreuid`, `__sys_setresuid`, `__sys_setfsuid` and the `gid` counterparts with an argument `Equal` `0`, each `Post`, with `matchCapabilities` `Effective` `NotIn` `CAP_SETUID` (`CAP_SETGID` for the `gid` calls). A caller that holds the capability is root, a setuid-root program or inside a user namespace, and is not reported; what remains is a process without the right to change its uid asking for uid 0. The hook fires on the call, so what it reports is an attempt, and the notice says so (TG8). That the capability check sees the caller's own effective set at this hook is part of spike S8.
  - `security_capset`. Upstream's rule posts every call whose new effective, inheritable or permitted set is non-zero (the same file, `NotEqual` `0` on arguments 2, 3 and 4); it is not limited to a gain, and it fires for every lowering of capabilities by a root daemon and every `capset` of a user-namespace sandbox. Ours posts the same calls with `matchNamespaces` `User` `In` `host_ns`, so processes inside a user namespace (rootless podman, Flatpak, bwrap, `unshare -r`) are not seen. The relay then keeps only a gain: a new effective set holding a capability that the process's capabilities at exec (`enable-process-cred`) did not hold.
  - A capability gained without an exec, through `matchCapabilityChanges` (`Effective`, `In`, `CAP_SYS_ADMIN`, `CAP_NET_RAW`) on a frequent hook such as `fd_install`, from upstream's [fd_install_cap_changes.yaml](https://github.com/cilium/tetragon/blob/v1.7.1/examples/tracingpolicy/fd_install_cap_changes.yaml), with two deviations. It sets `isNamespaceCapability: false` where upstream sets `true`, and it adds `matchNamespaces` `User` `In` `host_ns`. In `kernel.go`, `true` matches only while the process is outside the host user namespace, which is the opposite of what is wanted here: a gain inside a user namespace is normal (podman, Flatpak, bwrap) and is not reported. `false` ignores the user namespace, so the `host_ns` filter is what excludes it. This is the one rule that sees a kernel exploit that sets its own credentials, since that path makes no `setuid` call. Its cost on a busy hook is spike S5.
  - A raw hook on `commit_creds` is rejected: upstream notes it fires on every `execve` ([process-creds-changed.yaml](https://github.com/cilium/tetragon/blob/v1.7.1/examples/tracingpolicy/process-credentials/process-creds-changed.yaml)). Upstream's `create_user_ns` rule is left out: Flatpak and the browsers create a user namespace on every launch.
- **Classification in the relay.** `sudo`, `su`, `pkexec` and root daemons are what remains after the kernel filters on the `capset` and `fd_install` parts. The relay drops an event whose process had real uid 0 at exec (a root daemon), and one whose real uid was not 0 but effective uid was (`sudo`, `su`, `pkexec`) only when its binary is on an allow-list of the setuid-root programs the image ships, generated from the image at build time (step 3). A setuid-root binary that is not on the list raises a notice. The uids come from `enable-process-cred`.
- **Expected noise.** Not claimed to be none. The kernel filters and the relay remove the known sources (root daemons, `sudo`, user-namespace sandboxes); what remains on a healthy machine is measured, not asserted, in spike S8 and in the noise budget (step 6).

**TG6. Policy: kernel module loads.**

- **Reason.** With `MODULE_SIG_FORCE=y` an unsigned module is refused anyway. What remains useful is a record of which signed modules were loaded and of loads an unprivileged user triggered through autoloading (a socket family or a filesystem type nobody uses), a known way to reach rarely used kernel code.
- **Tier.** TM7.
- **Hooks.** As upstream's [monitor-kernel-modules.yaml](https://github.com/cilium/tetragon/blob/v1.7.1/examples/tracingpolicy/host-changes/monitor-kernel-modules.yaml) and [modules.yaml](https://github.com/cilium/tetragon/blob/v1.7.1/examples/policylibrary/modules.yaml): `security_kernel_module_request` (the requested name, with its return value), `security_kernel_read_file` with its second argument `Equal` `2` (reading a module), `do_init_module` (the module's name).
- **What is shown** (decided by A2-32 (#153), Q4). Recorded and counted, no notice, except for a module request whose process has a uid other than 0, which raises a notice. Each hook posts with `rateLimit: "1m"` and `rateLimitScope: "process"` (TG8).
- **Expected noise.** Tens of loads at boot, before any session; a few at hotplug.

**TG7. The event path: the export file and a system relay.**

- **The choice.** Tetragon writes its JSON export file; a small system service, `athanor-runtime-events`, reads it and serves each user their own events over the system bus; `athanor-sessiond` turns them into notices. Neither sessiond nor the bar reads Tetragon directly. The relay's names are confirmed by A2-32 (#153), Q8.
- **Why not the gRPC socket for the consumer.** The socket carries `AddTracingPolicy`, `DeleteTracingPolicy` and `ConfigureTracingPolicy` next to `GetEvents`; whoever can read events can also remove or disable the policies. The export filters do not apply to gRPC clients, so a reader gets the whole stream of every user's processes. sessiond is a user unit that reads only and is limited to `AF_UNIX` (SD17), and a user unit cannot hold a root-owned socket open. The socket therefore stays root-only, at `unix:///run/tetragon/tetragon.sock`, for `tetra` and the gate.
- **What gRPC would give, stated.** Server-side filters, no write to disk, and streaming without polling. It would cost a protobuf and gRPC dependency in the relay, the control-plane access above, and the loss of events while the relay restarts. The file keeps events across a relay restart and gives the administrator a record readable with `jq`.
- **The export settings** (drop-ins of TG2): `export-filename` `/var/log/tetragon/tetragon.log`; `export-allowlist` with `{"event_set":["PROCESS_KPROBE","PROCESS_LSM"],"policy_names":[...]}` naming our ten policies (TG2), so exec and exit events of every process are not written. `PROCESS_LSM` is there for TG13, the one policy on an `lsmhooks` hook. events.md lists the `event_set` types without it, but the filter compares an event's type with the `EventType` enum, which holds `PROCESS_LSM` ([eventType.go](https://github.com/cilium/tetragon/blob/v1.7.1/pkg/filters/eventType.go), [grpc-api.md](https://github.com/cilium/tetragon/blob/v1.7.1/docs/content/en/docs/reference/grpc-api.md)); the policy-name filter reads the policy name of an LSM event ([filters.go](https://github.com/cilium/tetragon/blob/v1.7.1/pkg/filters/filters.go), `GetPolicyName`); and upstream's Helm chart puts `PROCESS_LSM` in its default allow-list ([helm-chart.md](https://github.com/cilium/tetragon/blob/v1.7.1/docs/content/en/docs/reference/helm-chart.md)). Acceptance item 11 checks that such an event reaches the file; field filters that drop `process.arguments`, `process.environment_variables`, `process.cwd` and their `parent.` counterparts; `enable-process-ns` true (TG3's classification); `enable-process-cred` true (TG5's); `export-file-max-size-mb` 10, `export-file-max-backups` 3, `export-file-compress` false so the relay can finish reading a rotated file; `export-rate-limit` per TG8. The `rate_limit_info` records are not filtered by the allow-list (section 1), so they reach the file.
- **Access to the file** _(Proposal)._ `/var/log/tetragon` is created by `systemd-tmpfiles` as `root:athanor-runtime-events`, mode 2750, so files created in it take the group; `export-file-perm` is `640`. The relay runs as the system user `athanor-runtime-events` with no capability, and that user is the only member of the group: no human account is. Whether the rotation keeps the group and mode is spike S6.
- **The relay** (`system/athanor-runtime-events`, Rust, `zbus`). It follows the file by offset and inode across rotations, keeps only events whose policy name begins with `athanor-` (A2-32 (#153), Q7: an administrator reads the events of their own policies with `tetra` on the root-only socket) and the `rate_limit_info` records (they have no policy name; the exporter's limiter writes them past the filters), classifies the policy events (TG3 to TG6, TG12 to TG16), turns each `rate_limit_info` into one record of the category `events-dropped` with its count and no uid, attributes each policy event to a uid (the process's `uid`, else its `auid`; TG13 and TG14 add the owner of the file or of the target process, and the record then enters both uids' rings), and keeps per uid a ring of the last 200 records in memory. A record holds the time, a category code from a closed list (`persistence-write`, `exec-temporary`, `credential-raise`, `module-request`, `network-temporary`, `sensitive-file`, `ptrace-attach`, `bpf-load`, `mount`, `events-dropped`), the binary path and the target (a path; for `network-temporary` the destination address and port, for `ptrace-attach` the target's pid and binary, for `bpf-load` the program's type and name), and nothing else.
- **Its interface,** `os.athanor.RuntimeEvents1` on the system bus, built so that one user learns nothing of another's events (the one machine-wide record, `events-dropped`, is below).
  - `Subscribe()`, no argument. The relay takes the caller's uid from the bus daemon, never from an argument: `org.freedesktop.DBus.GetConnectionCredentials` on the sender's unique name returns `UnixUserID`, which the broker recorded from the kernel's peer credentials when the connection was made ([D-Bus specification](https://dbus.freedesktop.org/doc/dbus-specification.html#bus-messages-get-connection-credentials)). It stores the pair (unique name, uid) and forgets it when `NameOwnerChanged` reports the name gone.
  - A signal `Changed()`, with no payload, **unicast**: the relay sets the destination to the unique name of each subscriber of the uid concerned, so the broker delivers it to those connections only and no other user's connection sees it. It is never broadcast.
  - A method `Recent(cursor) -> (records, cursor)` that returns only the records of the caller's uid, the uid taken as above. The cursor is a per-uid counter, starting at 1 for each uid's ring, so its values say nothing about other users' volume. The records of `events-dropped` (no uid, no content) are served to every uid.
  - The bus policy lets only `athanor-runtime-events` own the name and lets every user call `Subscribe` and `Recent`. Records of uid 0 and of system users (a uid up to `SYS_UID_MAX` of `/etc/login.defs`, or `nobody`) are not served to any session at 1.0, with one exception: a TG13 or TG14 record that is also attributed to the owner of a home or of a target process (TG13, TG14) is served to that owner when the owner is a human account, even when the process's uid is 0. The relay writes each record of uid 0 or a system user to the journal, one entry with its own fixed `MESSAGE_ID` and the record's fields, and the event stays in the export file (A2-32 (#153), Q5). After revision 2's noise measurement, the TG5 records among them (`credential-raise`) are also served to the sessions of members of `wheel`; every other category of uid 0 and system users stays in the journal and the export file.
- **The relay's unit** passes TM8 with an empty capability set: `User=athanor-runtime-events`, `CapabilityBoundingSet=`, `NoNewPrivileges=yes`, `ProtectSystem=strict`, `ProtectHome=yes`, `PrivateNetwork=yes`, `RestrictAddressFamilies=AF_UNIX`, read-only access to `/var/log/tetragon`.
- **sessiond** calls `Subscribe()` at start and again whenever `os.athanor.RuntimeEvents1` gains a new owner (`NameOwnerChanged`), because a restarted relay holds no subscriptions. It calls `Recent` at start, after each new subscription, and on each `Changed` it receives, and raises the notice (TG8), writing a journal record with a fixed `MESSAGE_ID` for each notice it posts (the gate reads it, section 5). It needs no new filesystem access, so SD17's "reads only" holds.

**TG8. Notices, the shield's sheet, and limits.**

- **Notices** _(Proposal)_ through `org.freedesktop.Notifications`, as SD12 does: summary from our own translations by category ("An application wrote to a startup location", "A program ran from a temporary folder", "A program tried to gain administrator rights", "A kernel module was requested", "A program opened your private key or keyring", "A program tried to attach to one of your programs", "Some security events could not be recorded"); body the binary's and the target's paths as plain text with control and bidirectional characters stripped (SH12); one notice per category per 10 minutes per session, a later one saying how many events it covers. No action beyond dismissal at 1.0.
- **Categories and their strings.** A2-32 (#153) adds the categories of TG12 to TG16; the notices of `sensitive-file` and `ptrace-attach` are _(Proposal)_ (section 6). A notice is raised for `persistence-write` (tier 2, TG3), `exec-temporary` (TG4), `credential-raise` (TG5), `module-request` (a uid other than 0, TG6), `sensitive-file` (TG13's two cases), `ptrace-attach` (another user's process, TG14) and `events-dropped`. `network-temporary`, `bpf-load` and `mount` are recorded only. Each category has a translatable label for its row in the sheet's list: "Wrote to a startup location", "Ran from a temporary folder", "Tried to gain administrator rights", "Requested a kernel module", "Connected from a temporary folder", "Opened a protected file", "Attached to another program", "Loaded a kernel program", "Mounted or unmounted a file system", "Events not recorded".
- **The shield's sheet** gains a row "Security events", the count in the last 24 hours, opening the list of `Recent` records. The row never moves the badge: SH12 binds the badge to image verification, which these events are not. This is a change to `doc_bar.md` BR6 (section 3).
- **Volume limits, in layers** _(Proposal)_.
  - **Per policy, with an explicit scope.** Every `Post` carries `rateLimit: "1m"`. The default scope is the thread, so a process that is new at every exec is never limited; the scope is therefore set per policy. The limiter's key is the hook, the action, a scope value and, for each inspected argument, only its first 40 bytes as stored in the event, its length field included (`KEY_BYTES_PER_ARG` in [ratelimit_maps.h](https://github.com/cilium/tetragon/blob/v1.7.1/bpf/process/ratelimit_maps.h)); the scope value is the thread id for `thread`, the process's tgid for `process` and 0 for `global` ([basic.h](https://github.com/cilium/tetragon/blob/v1.7.1/bpf/process/types/basic.h), the rate-limit check). The key is therefore a prefix of the path, not the whole path: two paths of equal length that share their first bytes have the same key. A suppressed event is dropped in the kernel and counted nowhere. **The rule:** `global` is not used wherever a legitimate event can share a key with a hostile one, which for a path argument is wherever two processes can reach paths with a common prefix of that size. No shipped policy meets that condition, so no policy uses `global`: every policy uses `process`.
    - TG4 uses `process`. Under `global`, the owner's `go test` executing `/tmp/go-build123/b001/exe/pkg.test` would hide, for a minute, another process's exec of `/tmp/go-build123/b001/exe/evil.test`, a path of the same length with the same first bytes. Under `process` a loop of fork and exec is not collapsed across processes, because each exec is a new process: such a flood reaches the daemon's valve below, which is the risk A2-32 (#153), Q9b, accepts at 1.0, and the notice is aggregated per category (one per 10 minutes per session), so it does not reach the user as a stream.
    - TG3 changes to `process`. Its kernel filter admits toolbox and rootless podman as well as tier 2 (TG3's classification), so under `global` a toolbox user editing `~/.bashrc` would hide, for a minute, a Flatpak writing the same file, which is the event TG3 exists for. Under `process` each writer has its own key, and one process writing the same path in a loop is still limited.
    - TG5, TG6 and TG12 to TG16 use `process` as well. TG5's and TG6's arguments come from a small set (the uid `0`, a capability set, a module name), so a global scope would let one process's event hide another's identical one; a credential gain or a module request is rare enough that one event per process per minute bounds them. TG13's home files are the case the rule is written for (TG13).
  - **The daemon's `export-rate-limit` is a safety valve and not a budget:** 6000 events per minute, ten times what the layers above admit in normal use (to be measured at step 6), so that no policy's normal use reaches it. Each policy, TG12 to TG16 included, has its own event budget per minute, measured at step 6 and written into revision 2 (A2-32 (#153)); the valve is set from their sum. Beyond it events are dropped and counted in a `rate_limit_info` record.
  - **Dropped events are shown.** The relay keeps `rate_limit_info` (TG7): the count becomes an `events-dropped` record "N events not recorded" in every session's list and a notice, one per 10 minutes. A flood past the valve is therefore visible. Events collapsed by a policy's own `rateLimit` are not counted anywhere: upstream drops them in the kernel without a record. That is the per-policy limit working as intended, and it is why no policy uses the global scope. The count carries no uid and no content; it is served to every session because it says that the machine's record is incomplete, and it tells a user that someone did a lot, not who or what.
  - The relay's ring of 200 per uid and the notice limit above.
- **Residual risk, stated.** The limiter is one per daemon and drops without regard to policy or user. A user whose process executes many distinct paths under `/tmp` (TG4's argument is chosen by the caller) can produce more than 6000 distinct events a minute, and while it lasts any event, a TG5 escalation included, may be counted in `rate_limit_info` instead of recorded. That user can therefore blind TG5 for the length of the flood, but not silently: the dropped count and the notice appear, and the flood's first records are in the list. An escalation inside the flood is lost, not delayed. Tetragon 1.7.1 offers no budget per user or per policy at the export (section 1), so this design does not close the gap. A2-32 (#153), Q9b, accepts this risk at 1.0. TG12 to TG16 add sources of events behind the same valve; their budgets (above) keep their normal use below it.
- Needs: SD1, SD12.

**TG9. Privacy.** Events stay on the machine, consistent with `doc_kernel_profile.md` D34 and maintainer decision A2-19 (#161).

- The metrics server, the gops server and the health server are off: `metrics-server`, `gops-address` and `health-server-address` set empty. Tetragon opens no TCP or UDP listener (TG10).
- What is kept: the export file and its backups, at most 40 MB, readable by root and the relay; the relay's rings, in memory only, lost at reboot. The command line, the environment and the working directory of a process are never written (TG7's field filters). TG12 records destination addresses and ports, for programs run from temporary directories only; TG13 records that a file was opened, never its content.

**TG10. The service unit.**

- **Enabled by preset.** The package ships `/usr/lib/systemd/system-preset/80-athanor-tetragon.preset` with `enable tetragon.service`. Presets are read in lexical order of their file names and the first line that matches a unit wins, so this line is read before Fedora's `99-default-disable.preset` and its `disable *`. `systemctl enable tetragon.service` leaves `system/Containerfile:184`: `preset-all`, run in the same `RUN` and again in the NVIDIA stages, resets every unit to its preset, and with no preset line the result was "disabled" whatever was enabled before it. The image build's `preset-all` is what applies it; the package scriptlet is not relied on, because in a container build systemd is not running and `systemctl preset` does nothing. The image build asserts `systemctl is-enabled tetragon.service` after the last `preset-all`.
- **Capabilities** _(Proposal; the minimum is measured at step 1, since upstream publishes none)._ `CapabilityBoundingSet=` and `AmbientCapabilities=` `CAP_BPF CAP_PERFMON CAP_SYS_ADMIN CAP_SYS_PTRACE CAP_DAC_READ_SEARCH CAP_SYS_RESOURCE`. From the kernel's rules, unverified for Tetragon: `CAP_BPF` and `CAP_PERFMON` load tracing and LSM programs; `CAP_SYS_ADMIN` mounts the BPF and trace filesystems Tetragon checks at start (`main.go`: `CheckOrMountFS`, `CheckOrMountTraceFS`, `CheckOrMountCgroup2`) and reads other processes' namespace links; `CAP_SYS_PTRACE` and `CAP_DAC_READ_SEARCH` read `/proc/<pid>` of every process at start; `CAP_SYS_RESOURCE` covers the locked-memory limit on paths that ignore `LimitMEMLOCK=`. Dropped: `CAP_NET_ADMIN`, `CAP_SETUID`, `CAP_SETGID`, `CAP_DAC_OVERRIDE`, none of which our policies or settings use.
- **Sandbox.** Kept: `NoNewPrivileges=yes`, `ProtectSystem=strict`, `ProtectHome=yes`, `PrivateTmp=yes`, `ProtectKernelModules=yes`, `ProtectKernelLogs=yes`, `ProtectControlGroups=yes`, `LockPersonality=yes`, `RestrictSUIDSGID=yes`, `RestrictRealtime=yes`, `MemoryDenyWriteExecute=yes`, `LimitMEMLOCK=infinity`, `MemoryHigh=512M`, `MemoryMax=1024M`. Added: `StateDirectory=tetragon` (`/var/lib/tetragon`), `RuntimeDirectory=tetragon` (`/run/tetragon`, the socket), `ReadWritePaths=/sys/fs/bpf /var/log/tetragon` (`ProtectKernelTunables=yes` makes `/sys` read-only, and Tetragon pins its maps under `/sys/fs/bpf/tetragon`), `RestrictAddressFamilies=AF_UNIX AF_NETLINK` (unverified that nothing else is needed). Whether `ProtectKernelTunables=yes` also blocks a write Tetragon needs under `/sys/kernel/tracing` is part of step 1's measurement. `/usr/lib/tetragon` (`bpf-lib`, TG2) stays read-only: the objects are read, not written.
- **Ordering and restart.** `After=local-fs.target` without `network.target`, `WantedBy=multi-user.target`, `Restart=on-failure`, `StartLimitIntervalSec=2min` and `StartLimitBurst=10` as upstream's unit, `KillMode=control-group`.
- **No network listener.** `server-address` `unix:///run/tetragon/tetragon.sock`; `health-server-address`, `metrics-server` and `gops-address` empty.
- The unit passes TM8 through its allow-list. `scripts/verify.py` has no `services` check on this branch, so the check is a unit test of the repository (acceptance item 5) and a probe of the running unit (item 6).

**TG11. SELinux.** The image runs SELinux enforcing with the `targeted` policy (`doc_kernel_profile.md` D20 and D44). What Fedora's policy says about Tetragon, read on the maintainer's desktop on 2026-10-06 (`selinux-policy-targeted` 43.10-1.fc43 and `matchpathcon`; SELinux is disabled on that machine, so these are the installed policy's contexts and not a running system's):

- **There is no Tetragon domain.** No module and no file context names it: `/usr/bin/tetragon` is `bin_t`, `/usr/lib/tetragon` `lib_t`, `/var/log/tetragon` `var_log_t`, `/var/lib/tetragon` `var_lib_t`, `/run/tetragon` `var_run_t`, `/sys/fs/bpf` `bpf_t`. A service whose binary is `bin_t` is started by systemd in `unconfined_service_t` (the policy's default for services with no domain of their own; to be confirmed with `ps -eZ` at step 1, since the unit has never run on the image). **At 1.0 `tetragon.service`, and `athanor-runtime-events.service` with it (its binary under `/usr/bin` is `bin_t` as well), run unconfined by SELinux.** Their confinement is the unit's: the capability set, `NoNewPrivileges=yes` and the filesystem sandbox (TG10). SELinux does not block the daemon's use of `bpf`, `perf_event` and `lockdown`, so there is nothing to allow at first boot; for the same reason it gives no protection if the daemon is compromised.
- **The labels of the export file.** The daemon creates the file in `/var/log/tetragon`, whose default context is `var_log_t`, and the file inherits it. The relay, also `unconfined_service_t`, reads it by DAC alone: the group `athanor-runtime-events` and mode 0640 (TG7). No SELinux rule stands between them, and none stands between the file and a user: DAC alone refuses the user, who has neither the group nor the other bits.
- **A confined domain is the better end state and is not specified here.** It would need a local module like the ones the image already ships (`athanor_scx.cil`, `athanor_nix_daemon.cil` and `athanor_nvidia_modules_load.cil` in `/usr/share/selinux/packages` on the desktop): a type for each binary and for `/var/log/tetragon`, the permissions of the `bpf`, `perf_event` and `lockdown` classes, and a `dbus` `send_msg` rule for the relay's name. A2-32 (#153), Q9a, accepts `unconfined_service_t` for both units at 1.0; revision 2 specifies the module, once the VM shows the denials a confined domain would meet. D20 already requires zero AVC denials in Athanor domains in acceptance; item 1 of section 5 checks it for these two units.

**Coverage added by A2-32 (#153): TG12 to TG16.** Decision A2-32 asks that Tetragon be used to the fullest: observe-only policies from upstream's policy library that fit a desktop, each with its own event budget measured in revision 2 (TG8). Each policy below is based on an upstream example of v1.7.1 whose hook and argument types it reuses, follows TG1 (`Post` only) and TG8's limits, and stays within the selector limits of section 1, which the policy-limit test of TG3 enforces. Unless a section says otherwise a policy is recorded only: its records are in the user's list behind the shield's "Security events" row (TG8), with no notice. A notice is raised only where a user would plausibly not know what happened.

**TG12. Policy: network connections by a program run from a temporary directory.**

- **Reason.** A program dropped in a temporary directory and executed (TG4) usually fetches its next stage or reports to a controller. Where it connects is the next fact the user needs.
- **Tier.** TM1 and TM2, as TG4.
- **Why not every connection** _(Proposal; section 6)_. A2-32 (#153) names per-process network connections; this policy narrows them to programs run from temporary directories. Recording each connection of the machine is a flood: a browser opens hundreds a minute. A summary of the first connection of each process to each destination cannot be expressed either: `rateLimit` collapses repeated events within a time window and keeps no record of the destinations already seen, so a browser would still post one event per destination per minute. What Tetragon can express is a selection of the process by its binary, in the kernel (`matchBinaries`, operator `Prefix`, section 1). The policy therefore watches only the programs TG4 reports, and the rate limit summarises each of them per destination.
- **Hook.** `security_socket_connect` with its `sockaddr` argument (index 1) and the address length (index 2, `int`), as upstream's [security-socket-connect.yaml](https://github.com/cilium/tetragon/blob/v1.7.1/examples/tracingpolicy/security-socket-connect.yaml), whose selector keeps the families `AF_INET` and `AF_INET6` with the `Family` operator. One selector: that `matchArgs`; `matchBinaries` `Prefix` `/tmp/`, `/dev/shm/`, `/var/tmp/` and `/run/user/` (TG4's four prefixes); `matchNamespaces` `Mnt` `In` `host_ns`, as TG4. The hook covers TCP and connected UDP. It is preferred to `tcp_connect` (upstream's [tcp-connect.yaml](https://github.com/cilium/tetragon/blob/v1.7.1/examples/tracingpolicy/tcp-connect.yaml)) because its argument is the destination the caller asked for and holds nothing that changes at every connection, which the rate limit below compares.
- **Rate limit.** `rateLimit: "1m"`, `rateLimitScope: "process"`, by TG8's rule: under `global` one process's connection would hide another's to the same destination. The result is at most one event per process and destination (address and port) per minute.
- **What is shown.** Recorded only (category `network-temporary`): TG4 has already raised the notice for the exec. The record's target is the destination address and port.
- **What it misses, stated.** A datagram sent with `sendto` without `connect`; a program run through an interpreter (TG4's gap); a connection the program asks another process to make (a download through `curl` or a portal) is that process's.
- **Expected noise.** Near zero outside development. Flatpak applications, browsers, Steam and IDEs do not run from the host's temporary directories (S8 confirms). The known sources are `go run` and `go test` binaries under `/tmp/go-build*/` and AppImages under `/tmp/.mount_*/`, which the relay classifies as it does for TG4. An Electron application packaged as an AppImage runs from `/tmp/.mount_*/` for as long as it is open and posts a steady event per process and destination per minute; S8 measures it.

**TG13. Policy: opening sensitive files.**

- **Reason.** The password hashes and the sudo rules are what a local attacker reads or rewrites to keep root. A user's SSH private keys and login keyring are what malware with access to the home directory steals; TM4 states that a Flatpak with home access can read them.
- **Tier.** TM7 for the files under `/etc`; TM2 and TM4 for the files in a home directory.
- **Hook.** The LSM hook `file_open` with its `file` argument, as upstream's [lsm_file_open.yaml](https://github.com/cilium/tetragon/blob/v1.7.1/examples/tracingpolicy/lsm_file_open.yaml), which matches `/etc/shadow` with `Equal` on that argument; upstream's `matchBinaries`, which limits it to `cat`, is left out. It runs once per open, where `security_file_permission` (upstream's [filename_monitoring.yaml](https://github.com/cilium/tetragon/blob/v1.7.1/examples/tracingpolicy/filename_monitoring.yaml), and TG3's write rule) runs at every read and write. Its events are `PROCESS_LSM` (TG7's allow-list). The open is seen after the permission check: a user without access to `/etc/shadow` fails before the hook and is not seen.
- **Selectors.** Three, within the limits of section 1 (8 values for a `file` argument, a postfix of at most 127 characters), each with `Post`, `rateLimit: "1m"` and `rateLimitScope: "process"` (TG8's rule):
  - `Equal` `/etc/shadow` and `/etc/gshadow`.
  - `Prefix` `/etc/sudoers`, which matches `/etc/sudoers`, the files under `/etc/sudoers.d/` and the temporary file `visudo` writes beside them.
  - `Postfix` `/.ssh/id_rsa`, `/.ssh/id_ecdsa`, `/.ssh/id_ed25519`, `/.ssh/id_ecdsa_sk`, `/.ssh/id_ed25519_sk`, `/.local/share/keyrings/login.keyring` (gnome-keyring) and `/.local/share/keyrings/v1/login.keyring` (the file backend of oo7; the path is confirmed in S8): seven values. Under `global` the owner's own `ssh` opening a key would hide, for a minute and without a count, a Flatpak opening the same file; under `process` each opener has its own key.
  - The hook does not tell a read from a write, so the record says "opened".
- **Attribution and what is shown.**
  - A record of a file in a home directory is attributed to the owner of that home (the relay compares the start of the path with `realpath()` of each human account's home directory from the password database: the event's path is resolved with `d_path` ([basic.h](https://github.com/cilium/tetragon/blob/v1.7.1/bpf/process/types/basic.h), `copy_path`) and reads `/var/home/<user>`, while the password database says `/home/<user>`, and `/home` is a symbolic link to `var/home`) as well as to the process's uid, so a user sees who opened their key, whoever it was.
  - _(Proposal; section 6.)_ A notice is raised when the process's uid is not the owner's (another account, root included), or when the process is tier 2 by TG3's cgroup rule (a Flatpak with home access opening the key). Otherwise the record is recorded only: the user's own `ssh`, `ssh-add` and `git`, and the keyring daemon opening its own file.
  - The files under `/etc` can be opened only by root: their records are uid 0 and go to the journal and the export file (TG7, A2-32 (#153), Q5).
- **Expected noise.** Home files: `ssh` and `git` over SSH, from a terminal or from an IDE; a Flatpak IDE raises a notice by the tier 2 rule, and S8 measures how often. `gnome-keyring-daemon` or `oo7-daemon` on their own file, and backup tools. Browsers and Steam are not known to open these files (S8 confirms). Files under `/etc`: `sudo` opens `/etc/sudoers` at every call, and each authentication opens `/etc/shadow` (`unix_chkpwd`, `su`, `polkit-agent-helper-1`, the greeter's authentication, `passwd`, `accounts-daemon`); they are journal entries, not notices, and S8 counts them.
- **What it misses, stated.** Keys with other names (`~/.ssh/config` can name any file), `~/.gnupg`, the browsers' password stores, and a file read through a copy (a backup, a snapshot).

**TG14. Policy: ptrace attach.**

- **Reason.** Attaching to a process reads its memory and changes its code: an unlocked keyring daemon's secrets, a browser's sessions. It is how malware running as the user takes what file permissions protect.
- **Tier.** TM1 and TM2. On the maintainer's desktop `kernel.yama.ptrace_scope` is `0` (read 2026-10-06), so a process may attach to any process of its own uid; `doc_kernel_profile.md` sets the image's value.
- **Hook.** The `ptrace` system call, as upstream's [sys_ptrace.yaml](https://github.com/cilium/tetragon/blob/v1.7.1/examples/tracingpolicy/sys_ptrace.yaml) (`call: "sys_ptrace"`, `syscall: true`, `int` arguments). Upstream records the third argument; ours records the first two, the request and the target pid, both `int`. One selector: `matchArgs` index 0 `Equal` `16` (`PTRACE_ATTACH`) and `16902` (`PTRACE_SEIZE`, `0x4206`). `PTRACE_TRACEME`, by which a debugger's child asks to be traced, is left out. The hook fires on the call, so what it reports is an attempt, refused or not.
- **Rate limit.** `rateLimit: "1m"`, `rateLimitScope: "process"`, by TG8's rule: under `global` a debugger's attach would hide another process's attach to the same pid.
- **Attribution and what is shown.** When the caller is in the host's PID namespace (`enable-process-ns`), the relay reads the target's uid and binary from `/proc/<pid>`; the record's target is the pid and that binary. If the target belongs to another uid, the record is also attributed to the target's owner and raises a notice there _(Proposal; section 6)_. Attaching to one's own process is recorded only. A caller in its own PID namespace (a Flatpak, a container) names a pid the relay cannot resolve, and a target may have exited: such a record carries the pid only and is recorded only, for the caller.
- **Expected noise.** Debuggers and tracers (`gdb`, `lldb`, `strace`, IDE debuggers, Flatpak IDEs inside their sandbox) and crash reporters that attach to the crashing process (the browsers' and Steam's). All attach to the user's own processes and are recorded only.
- **What it misses, stated.** `process_vm_readv` and `/proc/<pid>/mem`, which read another process's memory without a `ptrace` attach.

**TG15. Policy: BPF program loads by a process other than Tetragon.**

- **Reason.** A BPF program in the kernel can watch or change what every process does, and a rootkit can use one. On the maintainer's desktop `kernel.unprivileged_bpf_disabled` is `2` (read 2026-10-06), so only privileged processes load programs.
- **Tier.** TM7.
- **Hook.** `bpf_check`, the verifier's entry for every program load, with its `bpf_attr` argument (index 1: the program's type, instruction count and name), as upstream's [policylibrary/bpf.yaml](https://github.com/cilium/tetragon/blob/v1.7.1/examples/policylibrary/bpf.yaml). That file's map, perf-event and `/sys/fs/bpf` hooks are left out: they fire far more often and say less than a program load. One selector: `matchBinaries` `NotIn` `/usr/bin/tetragon`, so Tetragon's own loads are not recorded.
- **Rate limit.** `rateLimit: "1m"`, `rateLimitScope: "process"`, by TG8's rule: under `global` one process's load would hide another's load of an identically described program.
- **What is shown.** Recorded only (category `bpf-load`). Loads are by uid 0, so they go to the journal and the export file (TG7, A2-32 (#153), Q5).
- **Expected noise.** `systemd` loads programs when it starts a unit that uses `DeviceAllow=`, `IPAddressDeny=`, `RestrictFileSystems=` or `SocketBindDeny=`: tens at boot, a few at each such unit start. The `sched_ext` scheduler of `doc_kernel_profile.md` at its start; rootful podman (the runtime's device controller); an administrator's `bpftool` or `bpftrace`. Flatpak, browsers, Steam and IDEs load seccomp filters, classic BPF that does not pass through `bpf_check`.

**TG16. Policy: mount and unmount calls.**

- **Reason.** A mount over a path changes what every process sees there: a mount over a configuration directory or a binary replaces it without writing to it. Mounts are also how removable media and network shares enter the session.
- **Tier.** TM1 and TM7.
- **Hooks.** `sys_mount` with its source and target (`string` arguments 0 and 1), as upstream's [sys_mount.yaml](https://github.com/cilium/tetragon/blob/v1.7.1/examples/tracingpolicy/sys_mount.yaml). Two further hooks follow the same pattern and are not in upstream's examples: `sys_umount` (the kernel's entry for `umount2`, its target as `string` argument 0) and `sys_move_mount` (its target path, `string` argument 3). The second is needed because util-linux 2.41, the version on the maintainer's desktop (read 2026-10-06), attaches mounts with the new mount API (`fsopen`, `fsmount`, `move_mount`), which `sys_mount` never sees. That both hooks load on Azoth is checked at step 2 (acceptance item 2). Each hook has one selector, `matchNamespaces` `Mnt` `In` `host_ns`.
- **Rate limit.** `rateLimit: "1m"`, `rateLimitScope: "process"`, by TG8's rule: under `global` one process's mount would hide another's of the same source and target.
- **What is shown.** Recorded only (category `mount`). Mounts by udisks2 and systemd are uid 0 and go to the journal and the export file (TG7, A2-32 (#153), Q5); a FUSE mount through `fusermount3` is attributed by TG7's rule.
- **Expected noise.** Filtered in the kernel: every mount inside a private mount namespace, that is each Flatpak and bwrap start (Steam's runtime included), rootless podman and toolbox, and every systemd unit with `PrivateTmp=` or `ProtectSystem=`. What remains: systemd's mount units at boot, udisks2 for removable media, `fusermount3` for GVfs, the document portal (`/run/user/<uid>/doc`, once per session), AppImages and `sshfs`, and an update's deployment. Browsers and IDEs are not known to mount on the host (S8 confirms).
- **What it misses, stated.** A detached mount made with `fsmount` and used through its descriptor without `move_mount`, and `mount_setattr` changes to an existing mount's flags.
