## 1. Context

What ships today, checked on the maintainer's desktop (image 0bd565cd) and in the repository:

- **No update ever runs by itself.** `80-athanor-system.preset` enables `bootc-fetch-apply.timer`, which does not exist. The override of `bootc-fetch-apply-updates.service` in `athanor-base-config` calls `bootc upgrade --stage`, a flag bootc 1.16 does not have.
- **Nothing is verified on the client.** `/etc/containers/policy.json`, owned by `containers-common`, is `insecureAcceptAnything`. The booted reference is `ostree-unverified-registry:ghcr.io/ars-regia/athanor-system:latest`. Athanor ships nothing under `/etc/containers`.
- **The signature cannot be matched.** `forge/scripts/sign_attest.sh` signs keyless (`cosign sign --yes`). CI verifies it with `--certificate-identity-regexp` and the GitHub issuer. `containers-policy.json` matches a Fulcio certificate only by `subjectEmail`, which a GitHub Actions identity does not carry.
- **The version says nothing.** The build sets no version label, so the image inherits the base's: two builds a day apart are both `43.20260916.0`.
- **A machine installed from the ISO boots a digest no signature covers.** The installer converts the image to OCI layout, which changes the manifest digest; the layers are the same. The first `bootc switch --enforce-container-sigpolicy` resolves the tag against the registry again and lands the machine on the signed digest without downloading a layer, which is what makes UT4 cheap.
- **`/run/athanor` has no owner.** The attestation key release creates it with default permissions and writes the released disk key into it. No `tmpfiles.d` entry declares it.
- **`athanor-secure-boot` cannot work.** It is a D-Bus service on `org.athanor.SecureBoot` with no bus policy file, so it cannot own its name; it reads one efivar; it was in `packages.json`. (Removed with its package by issue #148.)
- **Retention can remove signatures.** `forge/scripts/clean_ghcr.sh` keeps the two newest tagged versions per package, and a cosign signature is a tagged version of the same package.
- A nightly Orchestrator run without a source change publishes no new digest (`has_changes` stays false). Every merge that touches the image does.

What is available: `skopeo` 1.22 and `bootc` 1.16 are in the image; `bootc upgrade` has `--check`, `--download-only` and `--from-downloaded`; `bootc switch` has `--enforce-container-sigpolicy`; the workspace has `zbus` 5.18 on tokio, and `athanor_bus_api::polkit::check_polkit_auth_zbus(conn, sender, action_id, allow_user_interaction)`, which builds the subject from the bus sender.

## 2. Decisions

**UT1. One package, one binary, four units.** `forge/specs/athanor-update` ships the Rust binary `athanor-update` and:

| Unit | Runs | Does |
|---|---|---|
| `athanor-update-check.timer` | 15 minutes after boot, then every 6 hours, with a randomised delay | starts the check |
| `athanor-update-check.service` | `athanor-update check`, oneshot, root | re-derives the verification of the booted digest, checks the registry, downloads, publishes the state |
| `athanor-update-state.service` | `athanor-update check --offline`, oneshot at boot, root, `PrivateNetwork=yes` | the verification of the booted digest that UT5 requires before the network is up |
| `athanor-update.service` | `athanor-update serve`, root, D-Bus activated on `os.athanor.Update1` | the four requests of UT6, then publishes the state |

- Both services take one lock, `/run/athanor-update/lock`, so a request never races a download.
- The broken preset line and the override are deleted; the stock `bootc-fetch-apply-updates.timer` stays disabled by preset, because it applies and reboots.
- **Hardening is measured, and was.** Spike U1 ran each candidate against a real `bootc upgrade --download-only` and a real `--from-downloaded`. Both services ship with `NoNewPrivileges`, `ProtectHome`, `PrivateTmp`, `ProtectKernelTunables`, `ProtectKernelModules`, `ProtectControlGroups`, `ProtectProc=invisible`, `LockPersonality`, `MemoryDenyWriteExecute`, `UMask=0022`, `SystemCallFilter=@system-service @mount`, `RestrictAddressFamilies=AF_UNIX AF_INET AF_INET6 AF_NETLINK`, `RestrictNamespaces=~user` and `CapabilityBoundingSet=~CAP_SYS_MODULE CAP_SYS_BOOT CAP_SYS_RAWIO CAP_NET_ADMIN`. Two candidates are dropped: `RestrictSUIDSGID` makes bootc fail on its runtime auth file, and an allow-list `CapabilityBoundingSet` of any size breaks the `setpriv` bootc uses to start its skopeo proxy, so capabilities are subtracted, never enumerated. `ProtectSystem=strict` cannot apply: bootc writes the sysroot.
- **Only the check unit reaches the network.** The serve unit, the one unprivileged callers talk to, runs with `PrivateNetwork=yes`, which `--from-downloaded` tolerates. Neither that nor `IPAddressDeny=any` may go on the check unit: both stop the download.

**UT2. Release images carry a key-based signature beside the keyless one.** *(constraint 1)*

- The maintainer generates the pair offline with `cosign generate-key-pair`. The private key and its password enter the `signing-images` environment as `COSIGN_PRIVATE_KEY` and `COSIGN_PASSWORD`, and a copy goes to the offline kit with the other project keys. The public key is committed as `system/keys/athanor-image-1.pub`.
- **The signature must be the classic cosign attachment:** an OCI manifest at `<repo>:sha256-<hex>.sig` whose layers are `application/vnd.dev.cosign.simplesigning.v1+json`. It is the only format containers/image reads. cosign 3, the one the pipeline gets from nixpkgs, writes a Sigstore bundle at `<repo>:sha256-<hex>` instead, which every Athanor machine treats as no signature at all, and CI would not notice, because CI verifies with cosign. The key-based step therefore uses `skopeo copy --sign-by-sigstore-private-key`, through `retry.sh`, and a job of its own, without the key, then verifies that output the way a machine will (`system/verify-images.sh`): `skopeo copy --policy <the shipped policy>` of the published digest, pulled anonymously, not `cosign verify`. The job fails when the key is absent; tier images keep the keyless signature alone. Kernel images keep it alone too until the release signing step of ADR-0096 lands, and from then on are signed with the project key when released.
- The keyless signature and its Rekor entry stay: they are the public record of who built what. The key-based one is what a machine can check offline with a file on disk.
- Signed by digest: the three system images. The ISO is not an update source.
- **The key is alone in its job.** The key-based signature is made in a job of its own that does nothing else: it reads the three digests from a file the build job wrote, logs in, signs and ends. It is the only job that receives `COSIGN_*`. No image build, no SBOM tool and no other third-party binary runs beside the key, because an environment variable is readable by everything the job executes.
- **This key is the whole of client-side trust,** and there is no revocation. Whoever holds it can make any image these machines install as root. UT3's rotation is hygiene, not a response to compromise: an attacker holding key *n* can ship their own key *n+1*. A compromised key is recovered from out of band only, by a new ISO or by one documented command an administrator runs on each machine, and a machine that pulled an attacker's image before that is not recoverable remotely. If the key is ever known to be exposed, the project says so publicly and stops the pipeline. The recovery command is written and tested before the key signs its first image.

**UT3. The policy lives under `/usr` and is scoped to our images.** *(constraints 2, 3)*

- The image carries `/usr/share/athanor/containers/policy.json`, `/usr/share/athanor/containers/registries.d/athanor.yaml` with `use-sigstore-attachments: true`, and the public keys under `/usr/share/athanor/keys/`. They are rendered at image build by one script the RPM ships with its templates, because the registry is a build variable and a key rotation should be a file commit, not an RPM bump. The signing job and the acceptance harness call the same script.
- The container tools read only `/etc/containers`. The image build replaces `/etc/containers/policy.json` with a symbolic link to the file under `/usr` and links the `registries.d` entry; `verify.py shipped` checks both links.
- **`default` is `reject`,** because `bootc switch --enforce-container-sigpolicy` refuses to run against a policy whose top-level default is `insecureAcceptAnything`. Users lose nothing: `transports.docker[""]` and every other transport podman, buildah and skopeo use today (`docker-archive`, `oci`, `oci-archive`, `dir`, `containers-storage`, `docker-daemon`) are `insecureAcceptAnything`, which bootc does not inspect, and the acceptance proves `podman pull`, `podman load` and `podman build` still work. The three system image repositories override that with `sigstoreSigned`, a `keyPaths` list and `matchRepository`. The registry and owner come from the build's variables through a template; no literal `ghcr.io/ars-regia` enters the source.
- **Rotation:** key *n+1* ships in the `keyPaths` of an image signed with key *n*. Key *n* leaves one release after the first image signed with *n+1*. Two keys are therefore in force during a rotation, and the acceptance tests it.
- A local file that replaces the link shadows the policy. The check compares the policy in force with the shipped one by SHA-256 and publishes the result; the badge follows it (`doc_shell.md`, SH12).
- **What the policy does not do.** It constrains three repositories; every other registry name is accepted unsigned. `--enforce-container-sigpolicy` selects the host policy, it does not make an arbitrary reference trustworthy. An administrator with root can point the machine anywhere and is outside this threat model; the machine still refuses to call that state verified, with the reason `reference-out-of-scope`.
- **Local changes are outside the signature.** Packages layered, removed or replaced with `rpm-ostree` make bootc call the booted deployment incompatible: it reports no image and refuses `upgrade` and `switch`. The check then describes the booted deployment from `rpm-ostree status --json --booted` (the base image's reference, digest, version and creation time) and publishes it as not verified, with the reason `local-changes`, ahead of every other reason: what runs is the signed image plus files no signature covers. It downloads nothing, and the migration of UT4 waits without writing its stamp. Removing the local changes and rebooting restores the normal path.
- Two `registries.d` files that declare the same scope are a hard error in containers/image, so ours declares only the three repositories.
- **A missing or mistyped `registries.d` entry does not report itself:** a correctly signed image then fails with the same "A signature was required, but no signature exists" as an unsigned one. `verify.py shipped` checks the file, and the pipeline's own verification of UT2 catches it before an image is published.

**UT4. Machines follow a signed reference.** *(constraint 4)*

- **One mechanism for new and existing installs:** `athanor-update-migrate.service`, a oneshot with a stamp file, runs `bootc switch --enforce-container-sigpolicy` to the `stable` tag once the policy is in force and the network is up. No kickstart change is needed for existing installs; a new install from the ISO carries the signed `:stable` reference from its first boot (doc_update_delivery.md, UD2). On the dev VM it took 85 seconds and downloaded nothing; the reference became `ostree-image-signed:docker://…`, and later upgrades kept enforcing. It also moves a machine installed from media off the installer's digest onto the one the signature covers. A failure leaves the old reference, and the badge stays at the exclamation mark with the reason `policy-not-in-force`. A channel the registry has no manifest for yet (`manifest unknown`, before the first promotion of `stable`) is a wait, not a failure: the unit writes no stamp and exits 0, the state reads `channel-absent`, and `athanor-update-migrate.timer` starts the unit again every six hours; once the stamp exists the unit ends at it without asking bootc. Writing the stamp clears `channel-absent`. The check does not wait on the migration. Any other registry or network error still fails the unit. The migration runs once: a machine whose stamp exists and whose booted reference no longer enforces the policy, with no enforcing deployment staged, was switched afterwards without `--enforce-container-sigpolicy` or rolled back to its deployment from before the migration. The check publishes it with the reason `origin-not-enforcing` and asks the registry for nothing, since a download through that reference would not be verified. The state is reported, not repaired: the migration does not run again, and the remedy is a `bootc switch --enforce-container-sigpolicy` to the machine's channel (`latest` until `stable` is published). A repair the user starts from the shield, after a confirmation, is decided (2026-10-08) and not built yet; the machine is never switched without the user. The migration does not follow the project to another owner: a booted reference whose repository the policy does not name stays `reference-out-of-scope` (the Bridge, UD45 to UD50 of doc_update_delivery.md, was dropped by ADR-0103 D4). The stamp is written once a reference that enforces the policy has booted: a switch staged by an earlier run waits for the restart, one that vanished unbooted (a power cycle) is made again, and one that was deployed and did not boot is made once more, then not again for that digest. The migration never stages a held digest. A verified machine on a run-number tag or a digest reads `pinned-build` and is not moved (UD51).

**UT5. "Verified" is recomputed at every check from stored signature material.**

- After a download passes the policy, the check fetches the cosign signature object of that digest (`<repo>:sha256-<hex>.sig`, under 2 kB) with `skopeo copy` into `/var/lib/athanor-update/signatures/<digest>/`. That object is an attachment, not a signed image, and the strict policy would refuse it under its own repository scope. The fetch therefore names `--policy /usr/share/athanor/containers/attachments-policy.json`, whose default is `reject` with an `insecureAcceptAnything` scope for the three repositories, and which `verify.py shipped` checks; `--insecure-policy` is not used. What it fetches is trusted by nothing until the signature over it verifies.
- At every check, and at boot before the network is up, the binary verifies the stored payload with ECDSA P-256 (`p256` and `sha2`, real verification, no shortcut) against the keys named in the `keyPaths` of the shipped policy for that repository. The policy file is the single list of keys; the key directory is only where the files live. When the policy in force is not the shipped one, the reason is `policy-not-in-force` and no key is consulted. It then compares the payload's manifest digest with the booted one, and the repository of the payload's `critical.identity.docker-reference` with the repository the deployment follows; a mismatch is `no-signature`. The tag is not compared: cosign signs the tag it pushed and the machine follows another. The answer is never a stored boolean, and a key that left the image stops verifying by itself.
- The policy is what refuses a bad image; this check only drives the badge. When they disagree the badge is the exclamation mark.
- **Four ways to get the verification wrong, all excluded by test:** the signature object carries one layer per signature, in push order and with no key identifier in the payload, so the verifier tries every key against every layer; the signed bytes are the payload blob exactly as stored, checked against its descriptor's SHA-256, never a re-serialised JSON; the signature is base64 ASN.1 DER, read with `from_der`, with no hand-written parser; `critical.type` must be `cosign container image signature`, and a missing or unknown field is a refusal.
- **A moved tag is a downgrade the policy cannot see,** because a signature covers a digest and never a tag. The check therefore offers and downloads only a digest whose `org.opencontainers.image.created` is strictly newer than the booted deployment's. That label is inside the image configuration, so the signed digest covers it. An older digest is published as `older-than-booted`; it is not a badge state. bootc has no ordering of its own: with the tag pointed at an older image it says "Update available". The booted build time is `status.booted.image.timestamp` of `bootc status --format json`; the candidate's is the label from `skopeo inspect --config`, 54 kB and 70 ms. Neither `bootc upgrade --check`, which has no JSON output, nor `status.booted.cachedUpdate`, which was seen two tag moves stale, is used.
- **A machine installed from the ISO reads "not verified: installed from media"** until the migration of UT4 has run, which needs the network once and no update. Offline, it stays so.
- The statement is about the image the deployment refers to, not a measurement of `/usr` (`doc_shell.md`, SH12).

**UT6. Four requests; only the opt-out switch takes an argument.** *(constraint 5; third and fourth requests added on 2026-10-08, ADR-0094)*

| | `Apply()` | `GoBack()` | `SetAutomaticSecurityUpdates(b enabled)` | `Postpone()` |
|---|---|---|---|---|
| Polkit action | `os.athanor.update.apply` | `os.athanor.update.rollback` | `os.athanor.update.set-automatic` | `os.athanor.update.postpone` |
| Defaults (any / inactive / active) | `auth_admin_keep` / `auth_admin_keep` / `yes`, which are logind's for a reboot on this image | `auth_admin` for all three, never kept | `auth_admin` for every subject, never kept (no `_keep`) | `auth_admin` / `auth_admin` / `yes`: an active local session user postpones without an administrator (ADR-0094 point 3) |
| Does | refuses unless the state is `downloaded`; `bootc upgrade --from-downloaded`; `login1.Manager.Reboot(false)`; on a refusal, `ostree admin lock-finalization` | `bootc rollback`; records the digest it left as held; asks logind to reboot | writes the per-machine opt-out of UT13 in any state; turning it on re-locks an unlocked security digest, turning it off unlocks a waiting one; logs the caller's uid and the new value | refuses unless the state is `will-apply-at-next-shutdown` for a security-class digest whose lineage budget (UT13) is unused and unexpired; `ostree admin lock-finalization`; records the postpone and publishes `postponed-until <time>`; logs the caller's uid and the expiry |

- Bus name `os.athanor.Update1`, owned by root through `/usr/share/dbus-1/system.d/os.athanor.Update1.conf`. The policy allows `send_destination` only together with `send_interface=os.athanor.Update1` and the `send_member` of each method, plus `Introspectable.Introspect`. No property is exported. The activation file names `SystemdService=` and `User=root` and nothing else. Polkit decides who may call the four requests.
- The subject is the bus sender, through `check_polkit_auth_zbus`, with user interaction allowed. Never a PID from the caller, never `unix_process`.
- The `.policy` file is installed by the spec, which `verify.py polkit` requires, and its four actions are in the `os.athanor.*` namespace it checks.
- **`Apply()` never downloads.** With nothing downloaded it refuses, the timer downloads at its next run, and the shield's button says so. A root service does not open connections on an unprivileged caller's word.
- **The inhibitor check is logind's.** `Apply()` calls `Reboot(false)` and never `RebootWithFlags` with the skip-inhibitors flag. On systemd 258 a root caller is refused by a block inhibitor with `org.freedesktop.login1.BlockedByInhibitorLock`, which the helper reports as it is. `CanReboot` is not used: it answers polkit only and says "yes" with a block inhibitor held. When the reboot is refused after the unlock, the helper runs `ostree admin lock-finalization`, which restores the locked state; `will-apply-at-next-shutdown` therefore describes only the instant between the two calls, and a failure of the re-lock. *Amended on 2026-10-06 (A2-5, #150):* it also describes a security-class update scheduled for the next shutdown (UT13, A2-26, #150).
- **The held digest is needed and cannot come from bootc:** after a rollback, `bootc upgrade --check` says "No changes" while `--download-only` stages the digest the user just left.
- `GoBack()` targets the immediately previous deployment only and logs the caller's uid at notice.
- **A queued rollback is a return in progress** (2026-10-07; `doc_recovery.md`, R5). When `bootc status` reports `rollbackQueued` (greenboot queued the previous deployment after a failed health check, or someone ran `bootc rollback`), every check holds the booted digest, as `GoBack()` does, and downloads nothing: a staged deployment would become the default of the next boot in place of the return. `GoBack()` on such a boot holds and reboots without calling `bootc rollback`, which would swap the two deployments back. `bootc rollback` discards the staged deployment, and nothing stages a new one while the rollback is queued: `Apply()` answers that nothing is downloaded and the migration waits (`rollback-queued`).
- **`Postpone()` takes no argument and is called once per lineage.** The length is fixed by UT13, so a caller cannot choose it; once the lineage budget of UT13 is used or expired, including for a newer digest that inherited it, the call is refused with `os.athanor.Update1.Error.AlreadyPostponed`. A feature-class digest is refused with `Error.NotSecurityClass`, because its confirmation is already the user's choice. The notifier of UT11 calls it from the notice's "Postpone" action and the shield's sheet from its button; neither holds any other right.
- **One read beside the four requests.** `State()` takes no argument, asks no polkit and is open to every user. It reads the state file of UT7 with `athanor-trust-state`, requiring root as the owner, and returns the validated document re-serialised, so a caller never receives bytes the parser refused. A missing file is `os.athanor.Update1.Error.NoState`, a file not owned by root or writable by others is `Error.Untrusted`, and an unparsable one is `Error.Unreadable`. The call counts as activity for the idle exit and nothing more.
- **A console client.** `athanor-update go-back` calls `GoBack()` for an administrator at a text console, which is where a machine whose desktop does not start leaves the person. Run through `sudo`, the caller is root, whom polkit authorises without asking (`check_authorization_sync`: uid 0 is always authorised unless the call asks to always check), and the uid logged at notice is 0; from any other user it needs an authentication agent, which a console has none of, and the command tells the person to use `sudo`.
- **Held digest:** `/var/lib/athanor-update/held` names the digest the user left. The check skips it and offers only a newer one. No request releases it.

**UT7. One state file, written atomically.** *(constraint 6)*

- `tmpfiles.d` declares `/run/athanor-update` and `/var/lib/athanor-update`, both `0755 root root`. `/run/athanor`, which holds the released disk key, is not used.
- `/run/athanor-update/state.json`, `0644 root root`, written to a temporary name and renamed. Readers open it with `O_NOFOLLOW` and check the owner.
- Schema 1: the booted, downloaded and previous deployments (image, digest, version, build time); `verified` with a reason from a closed list (`signature`, `media`, `no-signature`, `key-not-in-policy`, `policy-not-in-force`, `reference-out-of-scope`, `local-changes`, `channel-absent`, `origin-not-enforcing`, `pinned-build`); the update state (`none`, `available`, `downloaded`, `will-apply-at-next-shutdown`, `refused`, `held`, `older-than-booted`); the policy in force (path, SHA-256, whether it is the shipped one); the four Secure Boot readings of UT8; the newest build time this machine has booted and the last successful check, both persisted under `/var/lib` so they survive a reboot; the last check's result as an error **code** (`none`, `network`, `registry`, `policy`, `storage`, `internal`) and at most a host name. No raw error text and no URL ever enters the file.
- Schema 2 (2026-10-08, ADR-0094) adds to schema 1 `automatic_security_updates: bool` (UT13) and `postpone`, an object or `null`, holding the lineage of UT13: `anchor` (the digest of the last security update applied on this machine, or `null` before the first), `first_notice_at` (wall time at which the security digest first reached `will-apply-at-next-shutdown`), `boots_remaining` (starts at 7) and `postponed` (bool). The expiry shown as `postponed-until <time>` is `first_notice_at` plus seven days; no further field and no new update state are needed. Readers that use `deny_unknown_fields` are updated to schema 2 in the same change.
- **World-readable is a deliberate trade.** The notifier reads the file without a privileged hop, and in exchange every local process learns the machine's patch level and that the user went back. There is no unprivileged alternative: `bootc status` refuses a non-root caller, and `rpm-ostree status --json` has no field for the finalization lock. Nothing else goes in: no user identity, no host name beyond the registry's, no path outside the two directories.
- A small crate, `athanor-trust-state`, parses the file and computes the badge of SH12. The update service, the bar and the notifier use it, so the rule exists once.
- **The shield asks `State()` instead of reading the file.** `athanor-bar.service` is sandboxed, and its user namespace maps only the user's own uid: root appears there as the overflow uid, so no owner check on the file can pass inside it. The bar keeps watching the directory for changes, calls `State()` at start and after each change with a timeout, and trusts the answer, a reply or an error, only when `GetConnectionUnixUser` of the sender the bus daemon stamped on it is 0; the bus daemon answers from outside the namespace. Any other sender, including a user process that took the name while the service was not running, gives the untrusted reason row. Neither accepting the overflow uid nor loosening the sandbox is allowed.

**UT8. Secure Boot is four readings, published separately.** *(constraint 7)* `SecureBoot`, `SetupMode` and `MokSBStateRT` from efivarfs, and `/sys/kernel/security/lockdown`. "On" means 1, 0, absent, and not `none`. The check reads them itself. They never move the badge (SH12).

**UT9. Every published image has its own version.** *(constraint 9)* `system/build-image.sh` sets `org.opencontainers.image.version` to `<base major>.<UTC build date>.<serial>` and `org.opencontainers.image.created`. The serial is the commit count of `HEAD`, so the label is a function of the source (doc_update_delivery.md, UD29). Ordering uses the build time, never the version string.

**UT10. Retention keeps what a machine can still use.** *(constraint 8)* `clean_ghcr.sh` never deletes a system image digest that is tagged `stable` or `latest`, was tagged so in the last 90 days, or is the previous `stable`; nor any `sha256-<hex>.sig`, `sha256-<hex>` or `.att` tag whose digest it keeps: cosign 3 and containers/image write signatures of one digest to two different tags. It treats signature tags as referrers of their image, as `forge/specs/azoth/retention.sh` already does: a signature is never deleted while its digest is kept. Ninety days is an interim number for digests that were never promoted; promoted digests are archived and never deleted (ADR-0081, which sets the support period at five years).

**UT11. The notifier.** `athanor-update-notify`, a user service in the same package: it watches the state file, sends one notification per downloaded digest per user through `org.freedesktop.Notifications` with the actions "Restart to update" and "Later", one after the first boot into a new deployment, and never announces a digest again in a later session: a pending digest stays on the session shield (`doc_bar.md`, BR8). It calls `Apply()`, `GoBack()` and, for a security-class notice, `Postpone()`, and nothing else. It accepts `ActionInvoked` only from the unique name that owns `org.freedesktop.Notifications` and only for an id it holds, because any session process can emit that signal, and a forged one would summon the administrator prompt of `GoBack()` out of nowhere. It restricts itself with Landlock at start as the greeter does (`ensure_single_threaded`, then the ruleset): read access to the state file and its own libraries, and write access to one directory, `$XDG_STATE_HOME/athanor-update-notify`, where it records per user which digests it has announced. *Amended on 2026-10-06 (A2-5, #150):* for a security-class digest it gives the notice of UT13 instead of asking for a confirmation; the notice of UT13 (A2-26, #150; ADR-0082, ADR-0094) offers a bounded "Postpone" and no open-ended "Later".

**UT12. Metered connections.** The check always asks the registry for the digest and build time with `skopeo inspect --config` (UT5), which costs a manifest. It downloads unless NetworkManager's `Metered` is 1 or 3; this desktop reports 4, guessed unmetered, and downloads.

**UT13. Security-class updates apply at the next shutdown** (amendment of 2026-10-06, maintainer decision A2-5 of 2026-10-05, #150). It amends UT6 and UT11 for one class of update, the security class of `doc_kernel_profile.md` D34; feature updates keep the confirmation of UT6 and `doc_shell.md` SH11.

- **The decision:** an update of the security class applies at the next shutdown or reboot the user starts, with a notice and a one-step way back. Nothing reboots by itself, and the update is never forced.
- **Superseded for this class:** SH11's rule that an update is never applied unconfirmed.

*Mechanism decided on 2026-10-06 (maintainer decision A2-26, #150).* After the download the service unlocks the staged deployment (`bootc upgrade --from-downloaded`) without a user request and does not reboot, so that ostree finalizes it at the next shutdown; the state reads `will-apply-at-next-shutdown`, which UT6 today reserves for the instant between its two calls and for a failed re-lock. The notifier tells each user, once per digest, that a security update will apply at the next shutdown or restart; after the first boot into it, the notice of UT11 names the running version and offers `GoBack()`, with its administrator authentication; a digest the user went back from stays held (UT6), whatever its class. The points the earlier text left open are settled by A2-26 (#150):

- **The security-class marker:** the class is a field of the key-signed release attestation, set when the release is signed together with the advisory ids it answers (`doc_pipeline.md`, PQ4, PL31, block PB4b; ADR-0094), and verified by the client; it is not an OCI label. The client verifies the attestation and reads the field before it acts without a confirmation, so an image whose attestation does not verify is of the feature class. An image whose attestation verifies but carries no such field is of the feature class as well (decided on 2026-10-08, ADR-0094).
- **Postpone and opt-out (ADR-0082, ADR-0094, accepted 2026-10-08):** the notice offers one postpone per lineage, in place of the earlier text that forbade any "Later". A lineage is the run of security digests since the last security digest applied on this machine; its budget is one postpone of seven days, also bounded by seven boots, whichever comes first. The days are counted from the first notice, which is independent of sessions and users: the clock starts when the security digest first reaches `will-apply-at-next-shutdown` on the machine, and the service records that time and the boot count in the state of UT7. An active local session user may postpone without an administrator (`allow_active=yes`), because the update still applies within seven days. During the postpone the service re-locks the staged deployment (`ostree admin lock-finalization`), so a shutdown does not apply it, and the state reads `postponed-until <time>`. A newer security digest replaces the staged one and inherits the remaining time of the lineage; it never extends it, and once the budget is used or expired `Postpone()` refuses (`AlreadyPostponed`). The budget resets only when a security digest is applied; `GoBack()` does not reset it. The only way to hold security updates further is the administrator's opt-out switch below. Expiry needs no network: it is evaluated against the machine clock and the boot count whenever the state is evaluated and at the shutdown that would apply, where the service unlocks the deployment and the update applies at that shutdown or at the next reboot the user starts. The postpone is carried by `Postpone()`, the fourth request of UT6.
- **The opt-out switch:** `SetAutomaticSecurityUpdates(b enabled)` (UT6), reached from the trust shield's sheet (`doc_bar.md`, BR6); Settings keeps no updates page. It is per machine, held in a root-owned file under `/var/lib/athanor-update/` written only by the update service, and published in `athanor-trust-state` at schema 2 as `automatic_security_updates: bool` (UT7), with every reader updated in the same change (a silent default on an old reader would drop the shield's persistent warning). Turning it off shows a warning before it takes effect and leaves a persistent warning in the shield while it is off. With it off, the check service downloads and notifies as before but does not unlock a security digest, and UT12 holds the download for every class. Switching it on re-locks a security digest that is already unlocked; switching it off unlocks a waiting one, and the lineage clock starts then if it has not.
- **Soft reboot and metered connections:** "the next shutdown or reboot" includes a soft reboot the user starts (UD37). A security-class update downloads on a metered connection as well (`Metered` 1 or 3), because CRA Annex I, Part I(2)(c) asks for automatic security updates; a feature update keeps UT12.
- **Who triggers the apply:** the check service, on its own after the download: it unlocks the staged deployment in the same service, with no user step and no request, and does not reboot.
- **The relation to UT6's requests:** without the opt-out, the security class does not go through `Apply()`, which stays the confirmed path of the feature class and keeps its re-lock when the reboot is refused. The unlock of the check service is its own step, and `will-apply-at-next-shutdown` describes the state it leaves, as well as the instant UT6 reserves it for. With the opt-out on, a security digest stays downloaded and locked, and `Apply()` installs it like a feature update.
- **After a failed boot:** greenboot does not reboot by itself and the update service holds the digest of a deployment marked bad, whatever its class (`doc_recovery.md`, R5; A2-26, #150); the notifier shows the notice of R5 that the next restart returns to the previous version.

Decided after A2-26 (2026-10-08, ADR-0094): an attestation without the class field is read as the feature class, the side that asks for a confirmation.

## 4. Decisions that are the maintainer's (all three taken on 2026-09-19)

- **D1. A `stable` tag.** Users follow `:stable`; `:latest` stays for testing. A manual workflow runs `system/promote.sh <run id>`, which points `stable` at an already signed digest with `skopeo copy`; the signature is by digest, so it carries. Without it every merge that touches the image asks every user to restart. It also gives UT4's migration a new image name to switch to. A moved tag can only move machines forward, because of the build-time rule of UT5. **Recommended.** `doc_kernel_profile.md` leaves channels to release 1.1; this brings one hand-promoted channel forward. Revised by doc_update_delivery.md UD5: the promotion is automatic after the evidence and a dwell, and the manual run is the override.
- **D2. `athanor-secure-boot` leaves the image.** It cannot own its bus name, so it has never answered a call, and UT8 replaces its one reading. **Recommended.** Nothing in the repository calls that name. Retiring means the binary, its unit and its bus name leave; the TPM sealing script and unit, the rollback check and the `systemd-pcrphase-sysinit` drop-in were first kept and then removed too (issue #148, decision A2-10, D42), so the package is gone and `verify.py shipped` fails if those units return. The alternative is a bus policy file and a review of what the service claims to attest.
- **D3. Who generates and holds the cosign key:** the maintainer, offline, as with the Secure Boot and module keys. The agent never sees the private key.

### Key succession (maintainer decision A2-18, 2026-10-05, #160)

The goal: the project can be continued by someone other than the maintainer, and no machine stays pinned to an old `:stable` forever. This section names where each key lives, by name only; no key material is described or stored here.

**Where the keys live.**

| Key | Public half | Private half |
|---|---|---|
| Image signature (cosign, UT2) | `system/keys/athanor-image-1.pub` (key 1, signs the transitional release, removed one release after the first image signed with key 2) and `system/keys/athanor-image-2.pub` (key 2, the rotation key that signs from then on; `docs/operations/secrets.md` section 4.1), both shipped under `/usr/share/athanor/keys/` | the secrets named in UT2 in the `signing-images` environment of the repository (the `signing` environment until the key rotation of `docs/operations/secrets.md` section 4.1 ends); a copy in the custody backup of `docs/operations/secrets.md` section 2 (ADR-0084) |
| Secure Boot (`SECUREBOOT_SIGNING_KEY`) and module signing (`MODULE_SIGNING_KEY`) | the certificates enrolled through the MOK and compiled into Azoth (`doc_kernel_profile.md`, section 9) | the `signing-kernel` environment (D43); a copy in the same custody backup |

The `signing-kernel` and `signing-images` environments each have a required reviewer (D43); once the image signing job is back in `signing-images` at the end of the rotation of `secrets.md` section 4.1, and until the 1.0 tag, `signing-images` runs without one (ADR-0098 item 6). The keyless signature of CI needs no key and no succession.

**Who signs `:stable` in the maintainer's absence. Decided for the single-maintainer phase by ADR-0084 (2026-10-07): option 2 below, revisited when a second maintainer joins.** `:stable` moves only through the promotion workflow `promote-stable.yml` (D1), automatic after the evidence and the dwell or run by hand as the override (doc_update_delivery.md, UD5), which holds no signing key: it points `stable` at a digest the image signing job already signed. The signing key is held by the `signing-images` environment, whose reviewer is the maintainer today. The options considered:

1. **A second named reviewer for the signing environments and a second GitHub account with write access.** Cheapest; the project continues only while that person is trusted with the key's use, not its content.
2. **A sealed letter and a backup of the keys held by others**, opened only on the maintainer's death or loss of access. Covers the case where GitHub access is lost too. The custody model of ADR-0084 (two LUKS2 USB sticks, a sealed letter, and a separate holder of the passphrase; `docs/operations/secrets.md` section 2) is this option for the content of the keys.
3. **No succession for the key: stop signing.** The last `:stable` stays valid until its expiry (below), then machines show the notice and stay on the last good deployment. It needs no trust in a third party, but ends updates.

No second named human reviewer exists as of 2026-10-06 (ADR-0062), so in the maintainer's absence signing stops until the drives of the custody model reach the successor (`docs/operations/secrets.md` KC4, KC8); until then signing stays stopped, which is the effect of option 3. Options 1 and 3 stay recorded as what a second maintainer, or a decision to stop signing, would change. Any additional automated check on the signing environments is a signing decision for the maintainer and is not recorded here.

**Expiry of the stable manifest. Decided 2026-10-06 (#160).** A machine that has not seen a `:stable` promotion for a bounded time must say so (a notice in the updates view, with a reason from the closed list of the trust state) instead of showing "up to date" indefinitely. The bound: 180 days since the build time of the newest promoted digest, longer than the 90-day move to a new Fedora (`README.md`, support window) so a late release does not raise a false alarm. This is the image-side counterpart of the manifest expiry and minimum version that `doc_kernel_profile.md` D41 asks of update manifests; neither is implemented yet.

Found on the way and since resolved: `athanor-backup` guarded its methods with `org.athanor.backup.*` actions that no `.policy` file declared, so polkit denied every call. It is now a root command with no D-Bus interface and no polkit action (commit `e66ad6d9`). `verify.py polkit` still does not look at the `org.athanor.*` namespace.

## 6. Acceptance

On the dev VM, with a throwaway key pair:

1. An image with both signatures is downloaded by the timer with no user action; the state reads `downloaded`; a poweroff boots the old version.
2. `Apply()` from the active session reboots into the new version with no password; from an SSH session it asks for administrator authentication. With a reboot inhibitor held, or with nothing downloaded, it refuses and nothing is unlocked. `busctl` cannot reach any other interface or member on the name.
3. After the reboot the state reads verified, with the reason `signature`; with `/etc/containers/policy.json` replaced by a permissive file it reads not verified, `policy-not-in-force`.
4. The same image without its key-based signature, and one signed with another key, are refused; the state reads `refused`, the error code `policy`, and no registry text appears in the file.
5. `GoBack()` asks for administrator authentication from every kind of session, boots the previous digest, and the next three checks do not download the held digest; a newer digest is offered.
6. An image that ships a second public key and is signed with the first is accepted, and so is the next one, signed with the second.
7. A fresh install from the ISO reads not verified, `media`, until the migration has run, and verified, `signature`, after it, with no update in between.
8. The migrated desktop follows the signed reference and keeps updating.
9. With the tag pointed at an older signed digest, the check publishes `older-than-booted` and downloads nothing. A deployment switched to a repository outside the policy reads `reference-out-of-scope`. A valid signature object copied from another of our repositories reads `no-signature`.
10. The recovery command of UT2 moves a machine to a new key with the old one removed.
11. `verify.py polkit`, `verify.py shipped` and the unit tests of `athanor-trust-state` pass; `systemd-analyze security` reports both services below an exposure the plan states.
12. An image whose only signature is a cosign 3 bundle is refused, with the state `refused` and the error code `policy`.
13. With the tag moved back to the digest the user left, three checks download nothing, although `bootc upgrade --download-only` run by hand would stage it.
14. Both bootc calls succeed under the units' own hardening, run as the units run them.
15. With the policy in force, `podman pull` from another registry, `podman load` and `podman build` work as before.

The checks of the mechanism decided by A2-26 (#150) follow.
