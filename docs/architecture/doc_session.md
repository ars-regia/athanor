## 1. Context

- **What binds this document.**
  - `doc_shell.md`: SH1 (the replacement rule), SH3 (of COSMIC only cosmic-comp stays), SH8 (the crash-loop protection of five failures in ten minutes on `CLOCK_BOOTTIME`, `doc_shell.md:130`).
  - `doc_shell_standard.md` ST5: recovery within 1 s of a `SIGKILL`, and the start of bar and dock within 1.5 s of the compositor's start.
  - `doc_lock_and_prompts.md` LP2, LP10, LP11 and LP12: the lock and the polkit agent are user units, the lock is never given up, the agent also serves `org.gnome.keyring.SystemPrompter`.
  - `doc_session_daemons.md` SD4, SD5, SD7, SD8, SD10, SD17, SD18 and SD22: the idle daemon, its inhibitors, the broker, the application units, autostart, the daemons' units, their failures, and the retirement order of COSMIC's components.
  - `doc_languages.md` LN6 and LN7 (`LANG`, `LANGUAGE`, the `LC_*` variables) and `doc_accessibility.md` AX3, AX5 and AX9 (the screen reader, its gate, `XCURSOR_*`).

- **How a session starts today** (branch `shell-specs` at `da940ab8`, read 2026-10-06).
  1. greetd runs `athanor-session` as the user (`forge/specs/athanor-system-config/SOURCES/usr/bin/athanor-session:2-4`).
  2. It stops whatever a previous session left in the user manager: `systemctl --user stop athanor-session.target` and `reset-failed` (`athanor-session:11-14`).
  3. It exports `XDG_CURRENT_DESKTOP=Athanor:COSMIC`, `XDG_SESSION_TYPE=wayland` and `XDG_DATA_DIRS` with `/usr/share/athanor/cosmic-defaults` first (`athanor-session:18,19,25`), and runs `athanor-usbguard-hook unlock` (`:29`).
  4. It execs `cosmic-comp` with `/usr/bin/athanor-desktop` as the compositor's client, under `systemd-cat -t athanor-session` (`:33`).
  5. `athanor-desktop` reads the session class from logind (`forge/specs/athanor-system-config/SOURCES/usr/bin/athanor-desktop:29-33`) and imports `WAYLAND_DISPLAY DISPLAY XDG_CURRENT_DESKTOP XDG_SESSION_TYPE XDG_SESSION_CLASS` into the user manager (`:34`). It supervises `cosmic-greeter` (the locker) and `cosmic-idle` as its own children with a back-off that doubles up to 60 s and never gives up (`:36-102`), and execs `systemctl --user start --wait athanor-session.target` (`:104`).
  6. `athanor-session.target` has `BindsTo=graphical-session.target`, wants and follows `graphical-session-pre.target`, wants `xdg-desktop-autostart.target` and is ordered before it, requires and follows the readiness gate `athanor-desktop.service`, and wants `athanor-skel-sync`, `cosmic-bg`, `cosmic-settings-daemon` and `cosmic-osd` (`forge/specs/athanor-system-services/SOURCES/usr/lib/systemd/user/athanor-session.target:7-24`). Our shell is enabled under it by user presets (`WantedBy=athanor-session.target`, for example `forge/specs/athanor-bar/athanor-bar-1.0.0/data/athanor-bar.service:82`); `system/Containerfile:306-309` asserts the wants links of bar, dock and shelld.
  7. The readiness gate `athanor-desktop.service` is a oneshot with `RemainAfterExit=yes` that waits up to 10 s for a `wayland-info` round trip, with a 15 s start timeout (`athanor-desktop.service:17-23`). It carries no `PartOf=`.
- **How it stops today.** The logout is `systemctl --user stop athanor-session.target` (`athanor-desktop:14`; the bar's power menu calls `StopUnit` on it, `forge/specs/athanor-bar/athanor-bar-1.0.0/src/ui/logind.rs:17,86-92`). The wait returns, `athanor-desktop` exits, cosmic-comp exits with its client, greetd shows the greeter. `graphical-session.target` has `StopWhenUnneeded=yes` and the target binds to it, so it stops once `athanor-session.target` is gone (`/usr/lib/systemd/user/graphical-session.target` of systemd 258.11 on the image, read 2026-10-06), and every unit with `PartOf=graphical-session.target` stops with it.

- **What follows from the facts.**

  - The readiness gate has no `PartOf=`, so after a logout it stays active (exited) for as long as the user manager lives. ## 2. Decisions

**SN1. What this document owns.** The environment of the session and its import list (SN2), the `PartOf=` and `WantedBy=` rule (SN3), the start order (SN4), the stop order (SN5), the crash classes (SN6), the guards' degraded modes and the idle daemon's persisted inhibitors (SN7), crash notices and local reports (SN8), the end state of `athanor-desktop` (SN9) and of `XDG_CURRENT_DESKTOP` (SN10), and the "Needs" graph (SN11); from revision 3, the sessions the greeter offers (SN14), the session on the own compositor (SN15), the default since revision 4, and the gaps it ships with (SN16). Another specification that adds a session unit states its class (SN6) and any `After=` edge it needs by citing this document; it does not edit `athanor-session`, `athanor-desktop`, `athanor-session.target` or `athanor-desktop.service` itself. A change to any of these is a revision of this document.

**SN2. The environment.**

- **Set for the user manager by environment.d,** before it starts any unit: `XDG_CURRENT_DESKTOP=Athanor:COSMIC` from `/usr/lib/environment.d/50-athanor-desktop.conf` (`forge/specs/athanor-system-config/SOURCES/usr/lib/environment.d/50-athanor-desktop.conf:7`), so that a portal activated before the import already finds the desktop name and chooses `athanor-portals.conf`; `XDG_DATA_DIRS` from `60-athanor-cosmic-defaults.conf` (below); and `GTK_IM_MODULE=simple` from `50-athanor-desktop.conf` (LN11). The drop-in and `athanor-session` carry the same value and change together (SN10).
- **Exported by `athanor-session`,** before it execs cosmic-comp, in this order:
  1. `XDG_CURRENT_DESKTOP` (SN10) and `XDG_SESSION_TYPE=wayland`, as today;
  2. `XDG_DATA_DIRS` with Athanor's defaults first, as today, because cosmic-comp is a child of this script and not of the user manager; the user manager gets the same value from `/usr/lib/environment.d/60-athanor-cosmic-defaults.conf` (`forge/specs/athanor-calmo/SOURCES/usr/lib/environment.d/60-athanor-cosmic-defaults.conf`);
  3. after `athanor-first-run apply-handoff` (LN7), `LANG` and `LANGUAGE` from AccountsService (LN6) and the `LC_*` variables of the region (LN7);
  4. `XCURSOR_SIZE` and `XCURSOR_THEME` from the GNOME keys (AX9);
  5. `GTK_IM_MODULE=simple` while no input-method engine is enabled (LN11).
- **The import list.** `athanor-desktop` imports into the user manager exactly: `WAYLAND_DISPLAY DISPLAY XDG_CURRENT_DESKTOP XDG_SESSION_TYPE XDG_SESSION_CLASS LANG LANGUAGE LC_NUMERIC LC_TIME LC_MONETARY LC_PAPER LC_ADDRESS LC_TELEPHONE LC_MEASUREMENT XCURSOR_SIZE XCURSOR_THEME` and, while the input method is enabled, `XMODIFIERS QT_IM_MODULES QT_IM_MODULE`, which `athanor-session` then exports (LN11). A variable the session did not set is not imported, so an unset `LANGUAGE` leaves the manager's value alone.
- **Never imported** (settled 2026-10-08) `XDG_DATA_DIRS` (environment.d covers the manager), `XDG_SESSION_ID` (units find their session through logind, LP2), `XDG_ACTIVATION_TOKEN` (one per launch, BR2), `DBUS_SESSION_BUS_ADDRESS` (the manager's own).
- **Removed at the end.** The readiness gate gains `ExecStop=` that runs `systemctl --user unset-environment` over the same list except `XDG_CURRENT_DESKTOP`, whose value is static and comes from environment.d as well (unsetting it would leave a portal activated between two sessions without a desktop name), so a unit started after the logout and before the next login never inherits a dead display. The list lives in one file read by both `athanor-desktop` and the gate, so the two never diverge.
  - Needs: LN6, LN7, LN11, AX9.

**SN3. One binding rule.**

- **`PartOf=graphical-session.target`** (settled by the maintainer on 2026-10-08, reversing LP2). A2-20 (#156) decides that there is one binding rule; the target it names is this document's choice, and it is the one every session unit shipped today already uses (section 1). It applies to every user unit Athanor ships for the session, the readiness gate included, and for every application unit the broker creates. This is the convention of systemd.special(7) ("Such services should have `PartOf=graphical-session.target`") and of the upstream units the session runs, such as `xdg-desktop-portal.service`, so one rule covers ours and theirs and one stop transaction stops them all. `athanor-session.target` keeps `BindsTo=graphical-session.target`, so the session stops when either target does.
- **`WantedBy=athanor-session.target`** in `[Install]`, enabled by a user preset, for every unit the session starts eagerly. A D-Bus-activated unit (`athanor-osd`, the portal backend) has no `[Install]` section.
- **Every unit that connects to the compositor** has `After=` and `Requisite=athanor-desktop.service`, as the bar, the dock and the launcher do today. A headless unit (shelld, sessiond, broker) has neither, so D-Bus activation works before the gate.
- **Rejected: `PartOf=athanor-session.target`.** The logout is a stop job on `athanor-session.target` (section 1), and a unit `PartOf=` that target stops in that job's transaction. `graphical-session.target` stops later, in a transaction of its own, once nothing needs it (`StopWhenUnneeded=yes`), and that transaction stops every unit `PartOf=graphical-session.target`, upstream ones such as `xdg-desktop-portal.service` included. `After=` orders two stops only when both units are shut down together (systemd.unit(5)), so a unit bound to `athanor-session.target`, shut down with the logout's own job while the units bound to `graphical-session.target` are still running, is not held back by its edges to them. Bound as LP2 writes it, the lock and the agent would stop before the applications and the portal frontend, the reverse of SN5. With one binding every unit stops in the second transaction and SN5's edges hold. This reverses LP2's text; the lock and the agent are not built yet, so no shipped unit changes.

**SN4. The start order.** Each edge is an `After=`; a `Wants=` is named where the edge must also pull the unit in.

- **The guards are ready when they serve.** `athanor-lock`, `athanor-polkit-agent`, `athanor-idle`, `athanor-broker` and `athanor-a11y-gate` are `Type=notify` or `Type=dbus` and report ready only once they lock, are registered with polkit, hold their timers, own their name or listen, so an `After=` edge to them means what it says.
- **The start threshold of ST5 holds** with these edges: the bar now waits for two more units. If it does not hold on the reference machine, the edge is kept and the guard's start is made faster; ST5 is not relaxed (ST2).
  - Needs: LP2, LP11, AX5, SD8, SD10.

**SN5. The stop order.** When two units with an ordering dependency are both shut down, systemd applies the inverse of the start order: a unit with `After=` on another is stopped first; units with no ordering between them stop simultaneously (systemd.unit(5), `After=`). Every session unit is shut down with `graphical-session.target` (SN3), so the edges of SN4 give a partial order, and only that order is guaranteed:

- an application unit stops before the broker, the portal frontend, the polkit agent and the lock, which are still there while it saves its work;
- a shell surface stops before the lock and the polkit agent, so a session that ends while locked never shows its content; the bar stops before `athanor-shelld`;
- every unit that connects to the compositor stops before the readiness gate, which unsets the imported environment (SN2);
- `athanor-autostart.service` stops before the broker; Orca stops before the a11y gate.

Units with no edge between them (an application and the bar, the wallpaper and sessiond, the guards among themselves) stop in parallel. An edge is added here only when a stop needs a unit that would otherwise be gone.

The stop of each unit is bounded by the manager's default stop timeout. An application that does not exit within it is killed; this is the declared cost of ending a session.

**SN6. Crash classes.** Every session unit Athanor builds belongs to one class, and its unit file says which in a comment that cites this rule. The exceptions are named after the table.

| Class | Members | Policy | Never |
|---|---|---|---|
| **Guards** | `athanor-lock`, `athanor-idle`, `athanor-polkit-agent` (with the `SystemPrompter`), `athanor-broker` (A2-20, #156); `athanor-sessiond` and `athanor-a11y-gate` (maintainer decision 2026-10-06 (#156)) | `Restart=always`, `RestartSec=100ms`, `RestartSteps=5`, `RestartMaxDelaySec=30s`, `StartLimitIntervalSec=0`; after 60 s of healthy run the program sends `RESTART_RESET=1` (below); a degraded mode while down (SN7) | given up; a guard restarts for as long as the session lasts |
| **Surfaces and their services** | `athanor-bar`, `athanor-dock`, `athanor-shelld`, `athanor-launcher`, `athanor-osd`, Settings, the overview, the control center, `athanor-wallpaper`, `athanor-update-notify`, `athanor-a11y` (the watcher) | `Restart=on-failure`, `RestartSec=100ms`, `StartLimitBurst=10` over `StartLimitIntervalSec=600`; the program's own SH8 counter decides its degraded state after five failures in ten minutes on `CLOCK_BOOTTIME` | a second, different counter |
| **Activated helpers** | the portal backend `xdg-desktop-portal-athanor` | no `Restart=`: the next D-Bus call activates it again; systemd's default start limit cuts a tight loop and expires, so a later call succeeds | a give-up that lasts the session |
| **Session steps** | `athanor-desktop.service`, `athanor-skel-sync.service`, `athanor-appearance-reset.service` (`doc_session_daemons.md` SD16, amended 2026-10-15, #473) | oneshot, no restart; the gate's failure fails the target and so the login, which greetd reports | a restart |

- **Why sessiond and the gate are guards** (maintainer decision 2026-10-06 (#156)). sessiond reports every other crash (SN8) and holds the USBGuard notice; a reporter that gives up hides every later failure. The gate fails closed (AX5): while it is down no screen reader reaches the bus, which for a blind user is a session that cannot be used.
- **The back-off resets only on request.** In systemd 258 the restart counter that `RestartSteps=` reads is flushed only by a start that is not an automatic restart (`src/core/service.c:2988-2990`, tag `v258`), by `reset-failed` (`:5262`), or by the notification `RESTART_RESET=1`, new in 258 (`:4981-4988`; `man/sd_notify.xml:379-387`). It is not reset by a healthy run, as `athanor-bar.service:20-22` already notes for the surfaces. A guard that crash-looped once would otherwise wait 30 s at every later crash of the session, and ST5's 1 s recovery would fail. So every guard sends `RESTART_RESET=1` through `sd_notify` once it has run for 60 s since its last start, the healthy-run threshold of `athanor-desktop:44-49` and `:81` (30 s ceiling and reset on request settled 2026-10-08). The manager accepts the message only from a unit whose `NotifyAccess=` allows it: `Type=notify` sets `main` when it is unset (systemd.service(5)), and with `Type=simple`, `exec` or `dbus` the default is `none`, so every guard unit is `Type=notify` or sets `NotifyAccess=main` explicitly. The lock's first restart stays at 100 ms (LP10).
- **Exceptions.** COSMIC's units are named below. `athanor-launcher.service` keeps `RestartSec=1s` with `RestartSteps=5` and `RestartMaxDelaySec=60s` (`athanor-launcher.service:23-25`) until SN13 step 1 puts it on its class's values. `athanor-ime.service` (LN11) runs `ibus-daemon`, which has no failure counter of its own: it takes the surfaces' unit values without the SH8 counter, and sessiond's notice comes at its start limit (SN8). `athanor-compositor.service` (SN15) has no `Restart=`: Wayland clients do not survive their compositor, so a restart would bring back a session with every window gone; its end ends the session instead, through the script that waits on it (SN15).
- **COSMIC's units and children** keep their policies until they leave (SD22, OD15): `RestartSec=2s` in the three units, and `athanor-desktop`'s supervisor, which already never gives up, for cosmic-greeter and cosmic-idle.

**SN7. Degraded modes of the guards, and the idle daemon's inhibitors.**

| Guard | While it is down |
|---|---|
| lock | cosmic-comp keeps the defunct lock: every output stays dark and locked, and the new instance takes the lock over (LP10) |
| idle | no automatic blank, lock or suspend; the lock before sleep is the lock's own and still works (SD18); the inhibitors come back with the restart (below) |
| polkit agent | polkit finds no agent for the session (fallback off, LP11); what the caller then receives is polkitd's (section 4, question 3); the session never falls back to another agent |
| broker | launches fail closed with the caller's toast (SD7); running applications are unaffected |
| sessiond | a blocked USB device stays blocked; inserted drives queue in udisks; no crash notice is shown until it is back, and it then reports what the manager recorded meanwhile (SN8) |
| a11y gate | readers cannot connect; Orca is restarted after the gate (SN4) |

- **No guard locks the session because it failed** (settled 2026-10-08: the compositor keeps the defective lock, LP10, so a screen already locked stays locked). A crash loop with a 30 s ceiling would lock the user out every 30 s. The notice of SN8 tells the user instead.
- **The idle daemon keeps its inhibitors across a crash** (A2-20, #156), as `athanor-shelld` keeps its unread notifications (ST5):
  - At every change it writes its table to `$XDG_RUNTIME_DIR/athanor-idle/inhibitors.json`, mode 0600, through a temporary file and a rename: for each inhibitor its cookie, the unique bus name of its owner, its application id, its kind (idle or suspend only) and its reason. The directory is the unit's `RuntimeDirectory=` with `RuntimeDirectoryPreserve=yes`, so it survives a restart and leaves with `$XDG_RUNTIME_DIR` at the end of the login.
  - At start it restores each entry whose owner still has its unique name on the bus (`NameHasOwner`); unique names are never reused on a bus, so a present name is the same client. Other entries are dropped, each with one journal line at info. New cookies continue above the highest restored one, so an `UnInhibit` after the restart finds its inhibitor.
  - A file that does not parse is removed, the event logged at warning, and the daemon starts with no inhibitor.
  - Needs: SD4, SD5.

**SN8. Crash notices and local reports** (A2-24, #156). Core dumps stay off; `athanor-sessiond` tells the user and keeps a report the user can attach to "Report a problem" (A2-19, #161).

- **The source is the user manager,** not files the units write. sessiond subscribes to the manager and, for each unit of the table in SN6, takes `Result`, `NRestarts`, `ExecMainCode`, `ExecMainStatus` and `InvocationID` from the `PropertiesChanged` signal sent when the unit enters `SubState=auto-restart` or `failed`: the next run overwrites them within `RestartSec=`, so they are captured from the signal, never read afterwards. A failure is a run whose `Result` is not `success`. If a signal is lost or coalesced, the manager's own journal entries for the failure (`UNIT_RESULT`, `EXIT_CODE`, `EXIT_STATUS` and the invocation id) are the record sessiond reads instead (section 4, question 2). Rejected: reading the SH8 records of each unit's runtime directory, which only the programs with a counter write.
- **The notice,** through `org.freedesktop.Notifications`, at most one per unit per session: at the first failure of a guard; at the fifth failure in ten minutes of a surface or service (SH8's point); when an activated helper reaches its start limit. It names the component in the user's words ("The screen lock stopped unexpectedly and was restarted") and offers "Report a problem". When the failing unit is `athanor-shelld`, which serves `org.freedesktop.Notifications`, the notice cannot be shown at that moment: sessiond still writes the report, and raises the notice once the name is owned again (shelld is a surface-class unit and restarts within 100 ms). If `athanor-shelld` reaches its start limit and the name is not owned again in the session, sessiond keeps the undelivered notice (the report is already on disk) as a marker file in that same crash-reports directory, so that SD17's single write directory holds, and raises it at the next session start, once the name is owned.
- **The report.** For every failure sessiond writes `$XDG_STATE_HOME/athanor/crash-reports/<UTC time>-<unit>.txt`, mode 0600, through a temporary file and a rename: the unit, the image version from `/usr/lib/os-release`, the time, `Result`, the exit code or signal, `NRestarts`, and the last 50 journal lines of the failed invocation (`_SYSTEMD_INVOCATION_ID`). It keeps the 20 most recent reports and deletes older ones. Nothing is sent anywhere: the "Report a problem" flow shows the report to the user, who decides whether to attach it.
- **sessiond's confinement** (SD17) gains one write directory, `$XDG_STATE_HOME/athanor/crash-reports`, and read access to the user's journal.
  - Needs: SD1.

**SN11. The "Needs" lines and the dependency graph.**

- **The format.** A dependency of one requirement on another is a line of its own, inside the requirement, that begins with `Needs:` (after an optional list marker), followed by requirement identifiers separated by commas and a final full stop: `Needs: LP2, SD4.` An identifier is one to three capitals and a number, defined in exactly one specification of `docs/architecture/` as the bold head of a requirement (`**LP2.`). The line belongs to the nearest requirement head above it. It means: the requirement above cannot be built before the named ones are.
- **What `scripts/verify.py docs` checks:** that every `Needs:` line is inside a requirement and parses; that every identifier it names is defined exactly once; that no requirement needs itself; and that the graph has no cycle, naming one when it does. It reports the number of requirements and edges as a note.
- **Prose dependencies** written before this revision ("Needs the lock of ...", SD22) are not lines of this format and are not read. Each specification converts them at its next revision; until then the graph holds only what this document declares.

A value that is empty, `n/a` or `(unset)` means unset, and its variable is unset in the manager with `systemctl --user unset-environment`, which also removes a value a killed session left. The script then imports SN2's list less `WAYLAND_DISPLAY` and `DISPLAY`, which the compositor sets, the second for the X11 display on which it starts xwayland-satellite (`doc_own_stack.md` section 3). Every command of steps 3 to 5, the reads of logind and `locale1` and each `set-environment`, `unset-environment` and `import-environment` included, runs as the condition of an `if`, so that `set -e` does not end the script: a failure hands the sign-in off as step 7 does, with the failed command as the cause;
  6. starts the locker and the idle daemon through the session's supervisor (below), one background job, and keeps its pid from `$!` in `sup`; the exit handler of step 3 kills it and stops the two scopes before its other `systemctl` calls, so that a hand-off never leaves a supervisor that would start a second locker beside cosmic-comp's;
  7. runs `systemctl --user start --wait athanor-compositor.service` as an asynchronous command, keeps its pid from `$!`, and waits for that pid alone with the `wait` builtin, as `wait "$pid" || status=$?`, so that a start that failed, whose status is non-zero, reaches the test below rather than ending the script under `set -e`; a bare `wait` would also wait for the supervisor of step 6. A shell runs the trap of a signal only after a foreground command has completed, but a trapped signal makes `wait` return at once, with a status above 128, and the trap runs next (bash(1), SIGNALS; POSIX.1-2024, Shell Command Language, 2.12, "Signals and Error Handling"), so greetd's `HUP` or `TERM` reaches the handler without waiting for the compositor. The command starts the compositor and, through its `ExecStartPost=`, the session, and returns once the compositor's unit is inactive again (systemctl(1), `--wait`), whatever the cause: a start that failed (no `READY=1` within `TimeoutStartSec=`, a readiness gate or target that failed), a crash or a kill, a stop at logout. This is the only start of the compositor, so a compositor that has died is never started again in the same session (SN6). When the wait returns, the script tests the marker: a marker absent means a session that never started, because the compositor exited, crashed or did not send `READY=1` within `TimeoutStartSec=`, or the readiness gate or the target failed. Then the script runs its exit handler itself, resets its traps with `trap - EXIT HUP TERM`, since a signal left ignored stays ignored across `exec`, logs the cause under `athanor-compositor-session` at priority `warning` with the unit's `Result=` and `ExecMainStatus=`, and runs `exec /usr/bin/athanor-session` (SN14); `exec` runs no `EXIT` trap, so the handler does not run twice. A marker present means a session that started: the script exits, and the exit handler ends the rest. The marker, not the target's state, since a logout may stop the target before the compositor ends, and not the target's `ActiveEnterTimestampMonotonic`, which the manager forgets when it unloads the inactive target between two sessions. A signal from greetd during the wait reaches the handler, which exits, and never the hand-off.
- **Why the script waits on the compositor.** The session must end when the compositor ends, and it can end on its own: a crash, a `SIGKILL`, a GPU removed. `PropagatesStopTo=` would not do it: systemd.unit(5) applies it to stop jobs, and a main process that exits by itself queues none. Waiting on the target would not either: the target stays active when the compositor dies. The unit whose end must end the session is the one waited on, which covers a crash and a logout alike. Rejected: a runtime drop-in `BindsTo=athanor-compositor.service` with `After=` on the target under `$XDG_RUNTIME_DIR/systemd/user/athanor-session.target.d/`. It works (systemd.unit(5), `BindsTo=`: a unit bound to another that "suddenly enters inactive state" is stopped too, and with `After=` the bound unit "strictly has to be in active state"), but a drop-in left by a session killed before its handler would make the next cosmic-comp session's target require the compositor, and the runtime directory outlives a session while the user has another one open. Whether cosmic-comp's exit ends cosmic-comp's session, the second entry and the target of every hand-off, is section 4, question 1; this revision does not rely on it for the default.
- **Why the session starts from the compositor's unit.** `ExecStartPost=/usr/bin/systemctl --user start athanor-session.target` runs once the compositor has sent `READY=1` (systemd.service(5), `ExecStartPost=`), so the gate's probe and every unit after it meet a compositor that serves. `systemctl start` waits for the target's job and exits non-zero when it fails, a gate that fails or times out included; then "the unit is considered failed" (systemd.service(5), `ExecStartPost=`), the compositor is stopped and the script's wait returns. A session that fails to start ends the compositor's unit as a compositor that dies does, and step 7 tells the two apart by the marker: a second `ExecStartPost=/usr/bin/touch %t/athanor-compositor-session.started` creates it, and runs only once the first has succeeded, since a failed command of `ExecStartPost=` skips the rest (systemd.service(5)); `%t` is `$XDG_RUNTIME_DIR` in the user manager (systemd.unit(5), specifiers). The gate has no `After=athanor-compositor.service`: "the execution of ExecStartPost= is taken into account for the purpose of Before=/After= ordering constraints" (systemd.service(5)), so the gate would wait for the compositor's start, which waits for the gate, until `TimeoutStartSec=`. Rejected: the script starts the compositor, then the target, then waits on the compositor with a second `start --wait`; a compositor that died between the two would be started again.
- **`athanor-compositor.service`,** a user unit of the compositor's package: `Type=notify`, `ExecStart=/usr/bin/athanor-compositor --drm`, and the two `ExecStartPost=` above; the compositor sets `WAYLAND_DISPLAY` in the user manager once its socket listens, then sends `READY=1` (SN13 step 6). `TimeoutStartSec=60s`. systemd arms the start timeout anew for each command it spawns (systemd `v258`, `src/core/service.c:1763`, with the timeout passed for `ExecStart=` at line 2507 and for `ExecStartPost=` at line 2402), so the compositor has 60 s to send `READY=1` and its `ExecStartPost=` another 60 s. That command returns when the target's job is done, and a target is ordered after the units it wants (systemd.target(5), default dependencies), so it waits for the session's whole start: the gate, at most 15 s (`TimeoutStartSec=15`, `athanor-desktop.service`), with `athanor-shelld` (10 s), `athanor-appearance-reset` (15 s) and `athanor-skel-sync` beside it, then the bar and the dock, at most 20 s each and in parallel (`TimeoutStartSec=20s`): 35 s along the longest bounded chain. `athanor-skel-sync` is a oneshot without a timeout (systemd.service(5), `TimeoutStartSec=`: disabled by default for `Type=oneshot`), which copies `/etc/skel` at an account's first sign-in; the 25 s beyond 35 s are the margin for it and for a slow first sign-in, a VM drawing with llvmpipe included. cosmic-comp's session has no such bound: cosmic-comp is the child of `athanor-session`, not a unit, and `athanor-desktop` waits on the target without a timeout (`athanor-desktop:107`), so a slow start only shows the desktop later. The own compositor's session has one because a `Type=notify` unit always has a start timeout (the manager's `DefaultTimeoutStartSec=`, 90 s, when the unit sets none), and this one is chosen so that a compositor that hangs before `READY=1` is stopped rather than kept on a black screen, and the sign-in passes to cosmic-comp's session (step 7). `TimeoutStopSec=5s`: on a start timeout systemd sends `SIGTERM` and, if the compositor has not ended `TimeoutStopSec=` later, `SIGKILL` (`service.c:4402`, `:2256` and `:4491`, for a unit without `ExecStop=` and with the default `TimeoutStopFailureMode=terminate`); a stop from the handler or at logout takes the same path. A compositor that never sends `READY=1` and that `SIGKILL` ends therefore holds the screen for at most 65 s, plus the time greetd takes to start the greeter; a process that survives `SIGKILL` (uninterruptible sleep, a GPU removed) adds the final `SIGTERM` and `SIGKILL` periods, `TimeoutStopSec=` each (`service.c:4499-4505`). `PartOf=graphical-session.target` (SN3): the bar's logout stops `athanor-session.target` (`logind.rs:17,86-92`), `graphical-session.target` stops once unneeded (section 1), the compositor with it, and the script's wait returns. No ordering edge puts the compositor after its clients, so the stop of `graphical-session.target` stops it in the same transaction as the bar, the dock and the applications, with no order between them (systemd.unit(5), `After=`): a client may lose its display before its own stop. A Wayland client that loses its display exits; acceptance item 10 checks that a logout leaves no unit failed and no core dump. An edge would order the compositor before `graphical-session.target`, whose start waits for the compositor's `ExecStartPost=`, which waits for the target's. `Slice=session.slice`; `NoNewPrivileges=yes` (`verify.py services`, TM8); no `[Install]`, so only the script starts it and the default session never does; no `Restart=` (SN6). It inherits the manager's environment when it starts, so it reads the `XKB_DEFAULT_*` values set in step 5, which give the keymap when the user has no `xkb_config` of LN9's store (`doc_own_stack.md` decision 27): Smithay's `add_keyboard` builds its keymap from an empty `XkbConfig` in a context with no flags (Smithay `023b78b`, `src/input/mod.rs:603-608`, `src/input/keyboard/xkb_config.rs:5-7`), and libxkbcommon then takes each empty name from `XKB_DEFAULT_LAYOUT`, `XKB_DEFAULT_VARIANT` and `XKB_DEFAULT_OPTIONS` unless the context was created with `XKB_CONTEXT_NO_ENVIRONMENT_NAMES` (`xkbcommon.h` of libxkbcommon 1.13.2, lines 455-459, 784-786 and 807). It takes the seat through libseat's logind backend from the unit, outside the session's scope (section 4, question 10; section 6, item 8).
- **When the script itself is killed.** A `SIGKILL` of the script runs no handler. greetd ends the session when the script ends, and the greeter returns. Without lingering, the user manager stops once the user has no session left, and the compositor with it. With lingering (loginctl(1), `enable-linger`: the user manager is kept around after logouts), `athanor-compositor.service` stays active without its logind session, whose devices logind takes back when the session closes, so the greeter's compositor can take the GPU (acceptance item 15 checks it); the user's next sign-in stops it, in `athanor-compositor-session`'s step 1 or in `athanor-session`'s cleanup (below). What a restart of greetd does to a running session is the same for both sessions and outside this revision: if it ends the script with `HUP` or `TERM`, the handler runs; if it kills it, the case above applies.
- **The locker and the idle daemon** (revision 4; section 6, item 10). cosmic-greeter in locker mode and cosmic-idle run under the own compositor as they do under cosmic-comp, as children of a supervisor inside the logind session, not as units: cosmic-greeter finds its session with `GetSessionByPID` of its parent (`doc_lock_and_prompts.md` section 1), and a child of the user manager has none. The supervisor is `athanor-desktop`'s (`athanor-desktop:39-105`), moved into `/usr/libexec/athanor/session-components`, which `athanor-desktop` and `athanor-compositor-session` source, so that its back-off and its error entry are the same in both sessions: it restarts a component that exits or cannot start, and logs at `err` the fifth failure in a row of runs shorter than 60 seconds (`athanor-desktop:72-102`). The file ships in athanor-system-config with `athanor-desktop`, which the compositor's package requires; the move into it, with both scopes and `athanor-session`'s cleanup of them, is one change inside step 6 of SN13, which cosmic-comp's session takes too. It starts each component with `systemd-run --user --scope --collect --property=TimeoutStopSec=5s --unit=cosmic-greeter-locker.scope` or `--unit=cosmic-idle.scope`: `TimeoutStopSec=5s` sends `SIGKILL` to a component still running 5 s after the stop's `SIGTERM`, in place of the default 90 s that would hold the greeter back; `--collect` unloads a scope whose component failed, so that the supervisor's next start can take the name again; `systemd-run --scope` runs the command in its own process, so the component's parent is still the supervisor inside the session, and the scope gives the component a unit the allow-list can name, which the session's own scope, `session-<id>.scope`, numbered per sign-in, cannot be (section 4, question 12). Under cosmic-comp `athanor-desktop` starts them at once, in the same scopes; under the own compositor the supervisor first waits, every 100 ms as the gate does, for `athanor-session.target` to be active, then reads `WAYLAND_DISPLAY` from the user manager. `session_component`'s `kill -0` of its anchor (`athanor-desktop:73`) runs only when a component has exited, so a script killed with `SIGKILL` would leave the locker and cosmic-idle running against an ended session until the next sign-in, cosmic-idle free to suspend the machine under the greeter. In both sessions `session_components` therefore checks its anchor, the script that started it, with `kill -0` every 200 ms, and the wait for `athanor-session.target` checks it at each of its turns; when the anchor is gone it kills both jobs and, since killing a job leaves its foreground component alive, stops both scopes at once with `systemctl --user stop --no-block cosmic-idle.scope cosmic-greeter-locker.scope`, polls `is-active` every 200 ms until both are inactive, checks once more 1 s later and stops again a scope that a restart in flight created, and exits. `session_components` runs with errexit off, as `session_component` does (`athanor-desktop:52-53`), and tests the status of each `stop` and `is-active`: a `stop` of a scope already unloaded exits non-zero, and a supervisor that died on it under `set -e` would leave the other component running. `session_component` takes the component's name apart from its command, so that its err entry names cosmic-greeter or cosmic-idle and not `systemd-run`. cosmic-idle locks through `loginctl lock-session`, which without an argument calls `Lock` on logind's session `auto` (systemd `v258`, `src/login/loginctl.c`, `activate`), "the caller's own session if they have one, otherwise their user's display session" (`src/login/logind-dbus.c`, `manager_get_session_from_creds`), so the lock reaches the greeted session from the scope; if it does not, cosmic-idle's lock command names the session by `XDG_SESSION_ID` (section 4, question 12). ## 6. The maintainer's decisions and the draft's recommendations (revisions 3 and 4)

**Decided by the maintainer on 2026-10-22:**

1. **No fallback to cosmic-comp** (SN14), *reversed on 2026-10-28 by `doc_own_stack.md` decision 28 (#810, ADR-0132)*: in revision 4 a session that fails before its target is active, a command that prepares it failing, and a user with the magnifier or a colour filter on hand the sign-in to cosmic-comp's session, and a compositor that ends after it, or a failure in SN15's step 1, before anything has started, returns to the greeter (SN14, SN15).
2. **The choice is not remembered** (SN14).
3. **The preview is offered on every installation** (SN14).
4. **The keyboard layout comes from `localectl`**: the system's X11 layout, variant and options, the properties of `org.freedesktop.locale1` that `localectl` sets and shows, set in the user manager before the compositor starts (SN15); a user's own layout and its switch wait for OS5.

**The draft's recommendations, approved as written by the maintainer on 2026-10-22 with this revision.** The text above follows each.

5. **A discriminator only the own compositor's session sets,** `ATHANOR_OWN_COMPOSITOR`, keeps `athanor-control-center-shortcut` out of it, and `XDG_CURRENT_DESKTOP` stays SN10's in both sessions (SN15). *Revision 4:* the variable was `ATHANOR_PREVIEW_SESSION` and kept `cosmic-osd` and `cosmic-settings-daemon` out too; both now run in both sessions, cosmic-osd with its line in the allow-list. The alternative, the shortcut unit in both sessions, writes a binding no compositor of that session reads.
6. **The menu's form:** a menu button beside the password field, shown only when the own compositor is installed (SN14). The alternative: a gear button in a corner of the greeter, as GDM's.
7. **cosmic-comp's entry names what the default lacks** (revision 4; revision 3 named the preview's gaps on the preview's entry): "Magnifier, colour filters, workspace overview and Alt+Tab", because a user who needs one of them otherwise finds no way to it (SN14). The alternative: no line, as GDM's session menu has none.
8. **The compositor as a user unit** (SN15), as ADR-0122's "its unit passes `verify.py services`" reads, against the compositor as the script's child, as cosmic-comp is; subject to section 4, question 10.
9. **The default's entry is plain "Athanor"** and the second's names its compositor, "Athanor on cosmic-comp" (revision 4; revision 3 marked the own compositor's entry as a preview) (SN14). The alternative: both entries named by their compositor, which asks every user a question only the second's users need.

**The draft's recommendations for revision 4, approved as written by the maintainer on 2026-10-28 with this revision.** The text above follows each.

10. **The locker and the idle daemon in scopes, under one supervisor** (SN15): `athanor-desktop`'s supervisor, moved into a file `athanor-desktop` and `athanor-compositor-session` source, runs cosmic-greeter and cosmic-idle in `cosmic-greeter-locker.scope` and `cosmic-idle.scope`, in both sessions. The alternatives: user units, which leave cosmic-greeter without its session, since it reads its parent's; a patch of cosmic-greeter that takes its session from `XDG_SESSION_ID`, a patch to carry until LP18 step 3 retires it.
11. **cosmic-settings-daemon in both sessions** (SN15), since cosmic-osd's headset dialog and the system actions of `doc_osd.md` OD3's keys go through it until OD17. The alternative: kept out of the own compositor's session, which leaves those keys without their actor there.
12. **The session's start read from a marker** (SN15, step 7), `$XDG_RUNTIME_DIR/athanor-compositor-session.started`, which step 1 removes and the compositor's second `ExecStartPost=` creates once the target has started. The alternatives: the target's `ActiveEnterTimestampMonotonic`, which the manager forgets when it unloads the inactive target; `WAYLAND_DISPLAY` in the user manager, which the compositor sets before `READY=1` and which would send a failed readiness gate back to the greeter at every sign-in; the target's state, which a logout may change before the compositor ends; the unit's `Result=`, which does not tell a gate that failed from a compositor that exited.
13. **The hand-off logged, not announced** (SN14): the cause goes to the journal at priority `warning`, and cosmic-comp's session shows no notice. The alternative: a notice in cosmic-comp's session, naming why it started, which the session's notification service would have to be told through a variable of the user manager.
